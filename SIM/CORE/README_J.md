## ベンチが与えるもの

| 部分 | すること |
|---|---|
| `Memory` | コアのメモリ: RAM 1領域(0x8000_0000、64 MB、参照と同じ)の上の疎な4 KBのページで、ELFファイルから読み込む。I$ / D$のポートのモデル(B1、B3)と、のちにAXI4のモデルが読み書きする。`write()` / `write64()`はフックを呼び、HTIFはそれでメモリに届いたものを見る |
| ELF | `load_elf_image()`: ロードするセグメントと、すべてのシンボル(`tohost`、`fromhost`、`begin_signature`、`end_signature`)。LOCKSTEPのものとは別の読み込み: イメージが違えば不一致として見える |
| `Htif` | **終了とコンソールはコミットしたストアから取る**(プログラムの順で、ストアキューとD$に何が残っていても)。**`tohost`はメモリの側で0に戻す**: 0でない値にする書き込みがメモリに届いた次のtickで(mmRISC-2のtb_COREと同じ) |
| `TraceSlot` | コミットのトレースのポート(下)の1 µop。1つか2つの`Commit`の記録にする |
| `Bench` | 各サイクルのスロットを古い順に`commit(slots, n)`へ、サイクルに1回`tick()`。命令ごとのロックステップ(切れる)、ウォッチドッグ(100,000サイクルのあいだコミットなし、サイクルの上限)、**アーキテクチャのメモリ**(ELFのイメージにコミットしたストアを加えたもの: riscv-arch-testのシグネチャはここから書き、ライトバックのD$の後ろのメモリからは書かない)、失敗したときは最後の16コミットを逆アセンブルして出す |

```c++
BenchCfg cfg;  cfg.elf = "test.elf";
Bench b(cfg);                       // b.mem()に読み込む。コアはb.entry()から始める
while (!b.done()) {
    // ... コアの1クロック。メモリのモデルはb.mem()を使う ...
    TraceSlot s[2];  int n = /* コミットのトレースのポートを写す */;
    b.commit(s, n);
    b.tick();
}
printf("%s\n", b.summary("test").c_str());   // PASS / FAIL、終了コード、命令数、µop数、サイクル数、IPC
```

## コミットのトレースのポート

`OOO_CORE`が`ifdef`のもとで(シミュレーション専用、`Plan/CORE_J.md` 3.9)、コミットのスロットごとに(サイクルに2つ、スロット0が古いほう)出すもの。`TraceSlot`のフィールド:

| フィールド | 意味 |
|---|---|
| valid | このサイクルにそのスロットがµopをコミットする |
| `pc`、`insn[0]`、`insn[1]` | µopのpcと命令(圧縮命令は下位16ビット) |
| `pair` | 融合した組: `insn[1]`は`pc` + `insn[0]`の長さにある |
| `trap`、`cause` | `pc`での例外(組にはならない: 例外を出す組は融合を切ってフェッチし直す) |
| `rd`、`rd_fp`、`rd_val` | µopのただ1つのレジスタの書き込み(−1: なし。x0もなしと数える) |
| `wr_first` | 組で、書き込みが前の命令のもの(ALU + 分岐)。そうでなければ後の命令のもの。書き込まずストアでもない前半は`rd_skip`になる |
| `st[0]`、`st[1]` | それぞれの命令のストア: 有効、アドレス、データ、サイズ(ストアの組は両方) |

## 規則

- **`tohost`のポーリング**: コアでは文字のストアがSpikeより遅れてメモリに届くので、`while (tohost);`(`Plan/icount/port/minilib.c`)が多く回る。LOCKSTEPは`tohost`と`fromhost`のロードにコアの値を参照へ与え(2026-10-29に追加、`SIM/LOCKSTEP/README_J.md`)、参照も同じループを回る。
- **`tohost`のラインをD$に残さない**(B3): 本物のライトバックのD$では文字のストアがD$に残り、コアはそれをいつまでも読み返す。B3でD$とともに行う: ベンチは`tohost`のラインをコアにとってキャッシュしない領域にする(D$のアダプタがそのロードとストアをメモリへ送る。`ifdef`のもとでのベンチのパラメータ)。それまではポートのモデルがメモリに直接書く。
- **アーキテクチャのメモリはアドレス変換なしで成り立つ**(Phase 1): ストアは仮想アドレスでコミットする。プログラムが変換を入れたとき(`rv64si-p-dirty`)、代役はこれを比べない。

## 代役のテスト(2026-10-29)

代役は2つ目のSpikeで、ベンチのメモリの上を、コアがするように走る:

- `Memory`からフェッチしロードする(ベンチのELFの読み込み)。
- `tohost`と`fromhost`のページは代役にとってデバイスである: そこへのストアは、ストアキューとD$の後ろにあるように、キューで0〜24サイクル待ってから`write()`で`Memory`に届く。そこからのロードは、キューにある新しいバイトを先に取る(ストアからロードへのフォワーディング)。
- コミットはトレースのポートを通る: サイクルに0、1、2スロット。組の書き込み1本の規則が許すところで、2命令を1スロットに融合する。

| 確認 | 起こるべきこと |
|---|---|
| 期待値 | 参照だけ(`Lockstep::step_ref`)を終了まで: 終了コードとコンソール |
| そのまま | ロックステップつきのベンチが通り、期待どおりの終了コードとコンソール。アーキテクチャのメモリが代役のメモリと等しい(`tohost`は除く) |
| 比較なし | 同じことをロックステップなしで |
| 壊したもの | ポートの1スロットの1フィールドを壊す(13種類: レジスタの値、レジスタ番号、書き込みの欠落、pc、命令、2つ目の命令、もう片方の書き込み、ストアのデータ、ストアの欠落、組の分割、トラップの原因、スロットの欠落、スロットの入れ替え)。終了のスロットより前で: ロックステップの不一致になる |
| ウォッチドッグ | (最初のファイル)途中でコミットが止まる: 「コミットなし」で終わる。そのままのサイクル数の半分の上限: 「終了なし」で終わる |
| HTIFだけ | 文字のあとにその上へ4バイトの終了、`fromhost`は`tohost`ではない、上位のワードを先にストアしたときの終了コード、`tohost`がtickで0に戻り、それより前には戻らない |

`./run_standin.sh`: `SIM/LOCKSTEP/run_selftest.sh`のプログラム(riscv-testsの`-p-` 175本と、g14のCoreMarkの2ビルド)、それぞれポートの壊し13個。

| 結果 | |
|---|---|
| そのまま、比較なし | 177本すべてが、参照と同じ終了コードとコンソールで通る。メモリも等しい(変換を入れる`rv64si-p-dirty`では比べない) |
| 終了コード | 0でないのは参照でもそうなるものだけ: `ma_data`、`amocas_*`(`SIM/LOCKSTEP`と同じ) |
| ポートの壊し | 2,019個すべてを検出。282個は当てはまらなかった(たとえば終了の前にストアやトラップのないプログラム) |
| `tohost`のポーリング | CoreMarkは使用中の`tohost`を3,667回(g14 -O2)と6,715回(g14 sf + -flto)読んだ: それぞれSpikeだけなら走らない2命令。ロックステップはそれについていく |
| ウォッチドッグ、HTIFだけ | 通る |
| 融合した組 | µopの12〜14 %(CoreMark: 2.77M中379k、2.54M中306kスロット) |

結果は`results/standin.txt`にある。

## バグ注入(`mutate.py`)

`bench.cc`と、`tohost`のロードについての比較器の規則(`lockstep.cc`)への18の変更。それぞれ作り直して、riscv-tests 4本とCoreMarkの1ビルドで走らせた: **18個すべてを検出**(`results/mutate.txt`)。この注入で2つのことがわかった:

- HTIFが応えたあとにアーキテクチャのメモリの`tohost`を0に戻していたのは冗長だった。比較は`tohost`のワードを除くので(削除した)。
- 「応えたあとにコミット側の`tohost`を消さない」が生き残った。ここのプログラムは、文字のあとに`tohost`の一部だけを書くことをしないため。今は`standin.cc`のHTIFだけの確認がこれを見る。

## B1: フロントエンドだけ(`tb_front`、2026-10-29)

Verilatorの`OOO_FRONT`(フェッチ、FTQ、復元、フェッチバッファ、スキッド、デコード、D1 / D2のグループのレジスタ)が、ベンチの`Memory`から`ICacheModel`(ミス8 %)を通してフェッチし、Spikeの実行を本当の経路とする。ベンチがD2とバックエンドを演じる:

| 部分 | すること |
|---|---|
| D2 | グループのレジスタから1サイクルに0〜2命令を取る(takenと予測されたものは1つまで: その先はターゲットの配列から)。本当の経路では、それぞれがSpikeの次の命令でなければならない(pc、ビット、長さ、最後のパーセル)。デコードのillegalはSpikeがそうトラップするところだけ。CSR / FP / システムの種類がビットのとおり(デコードがスロット0でしか出さない種類) |
| 解決 | 予測した次のアドレスをSpikeのものと比べる: 予測ミスは2〜7サイクル後にリダイレクト(復元: ブロック、最後のパーセル、結果、call / return、ランダムなALUポートで)。そのあいだD2は誤った経路を取り、その分岐のいくつかをランダムに解決する(TAGEの更新に届いてはならない)。トラップ、SYSTEMの命令、FENCE.Iはコミットでリダイレクト(フラッシュ) |
| コミット | 順に、D2の4〜10サイクル後、1サイクルに2つ。ストアは`Memory`へ(FENCE.Iは新しいコードを見る)。FTQはOOO_CTRLのようにpopする(1サイクルに1つ。フラッシュで残りは捨てる) |
| つなぎをそのまま | **TAGEの更新すべて**: popするブロックのメタデータがそのpushが書いたとおりで、実行したスロットとその結果がベンチが本当の経路で解決したとおり。**復元すべて**(R + 1)が、そのブロックのpushが書いたもの(ライン、履歴、スロット、RASのスナップショット)を読み返す。サイクルRにI$への要求がない。予測を損なうだけの誤りもこれで見える |
| オプション | `-full`: I$のミスなし、D2は毎サイクル2つ取る(フロントエンドが出せる量)。`-lag n`: D2のnサイクル後にコミット(2以上: 分岐はコミットの前に解決する)。`-mpki-max x`: 1000命令あたりの予測ミスがxを超えたら失敗。`-v`: 種類ごとの予測ミスと、ブロックのpushからその更新までにpushされるブロック。`FRONT_BYPC=1`: 予測ミスの多い条件分岐 |

`./run_front.sh`:

| 実行 | 結果 |
|---|---|
| riscv-testsの`-p-` 175本、2シード | すべてSpikeの順にフェッチ・デコードされて終了まで行く |
| CoreMark g14 -O2 / sf + -flto | 通る。TAGEの更新(1.74 M回)と復元をすべて確認 |
| 出せる量(`-full`) | 1サイクルに1.51 / 1.56命令。予測ミスはすべてD2の2〜7サイクル後に解決 |
| 予測ミスした条件分岐 | 6,582 / 5,742(`-full`で8,426 / 6,106)。モデル: 4,772 / 4,177 |

モデルはTAGEをすぐに更新する。ここではブロックの更新はそのpop、つまり最後の命令のコミットのあと、予測の6.4〜6.6ブロック後に来る。それは差の小さな部分で、大半はフェッチの停止で変わるTAGEの履歴の遅れである(`Plan/CORE_J.md` 5.3、D-17)。

## B1のバグ注入(`mutate_front.py`)

フロントエンドのつなぎへの35の変更(OOO_FRONT: クレジット、回復、復元と更新のフィールド、結果、ターゲットの配列、pc、スキッド、グループのレジスタ。FTQの先頭の読み出しと空きの数。フェッチバッファの空きの数)。それぞれ作り直して、riscv-tests 8本と、1000命令あたり予測ミス2.3の上限つきのCoreMarkで走らせた: **35個すべてを検出**(`results/mutate_front.txt`)。最初の注入では4つ残った: RASのスナップショットのスライスとcallのラインは予測を損なうだけで、CoreMarkはそのいくつかをまったく要しない(ポインタのスライス: returnの予測ミス59 → 275、上限の内)。サイクルRにフェッチを止めないことは、見えるものを何も変えない(FTQの復元とバッファのフラッシュもRにある。死んだI$への要求はミスのときにI$をふさぎうるだけ)。今はベンチがこれらをそのまま確かめる: 復元と更新のそれぞれを、そのブロックのpushが書いたものと照合し、RにI$への要求がないことを見る。
