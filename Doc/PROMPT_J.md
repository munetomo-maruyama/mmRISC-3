**Claude Codeの回答**

ホワイトペーパー、前回の検討メモ、mmRISC-2 の BENCH.md / TIMING.md の実測値をもとに、戦略を [STRATEGY_J.md](../Doc/STRATEGY_J.md)(英語版は [STRATEGY.md](../Doc/STRATEGY.md))にまとめました。

#### 要点

**1. 目標は「命令数 × IPC」に分けて考えると厳しさが分かります**
mmRISC-2 の `-O2`(Zba/Zbb)は、CoreMark 1回あたり 318.6k 命令でした(実測)。この命令数のままだと、必要な IPC は次のとおりです。
- 5.0/MHz:IPC 1.59
- 6.0/MHz:IPC 1.91

2命令幅の上限は IPC 2.0 なので、**`-O2` で 6.0 は2幅では現実的ではありません**。そこで目標を「`-O2` で 5.0、最大最適化で 6.0」と置くことを推奨します。前回メモの見込み(約 4.9/MHz)はこの目標に届かないので、設計の重心を変える必要があります。

**2. 最大の敵は分岐予測ミスです**
現状のミスは 1000 命令あたり 13 回です(実測)。OoO でミス1回を約 10 サイクルとすると、損失は1000命令あたり 130 サイクルになります。5.0/MHz で損失に使える予算は 128 サイクルしかないので、これだけで予算を使い切ります。優先して効かせたいのは次の3つです。
- TAGE 系の予測器を BRAM で大きく持つ(CoreMark は毎回同じ入力なので、長い履歴が効きやすい)
- 50MHz の余裕を段数削減に使い、ミス1回のペナルティを 10 サイクル以下にする
- 短い前方分岐の述語化(SFB)で、ミスそのものを消す

**3. IPC 2 の壁は、幅を広げる以外の方法で越えます**
Arty でコアに使えるのは約 3万 LUT です。OoO エンジン側に残るのは約 1.5 万で、NaxRiscv RV64(整数のみで約 1.8 万)より少ないため、デコード幅 3 はほぼ入りません。代わりに次で補います。
- マクロ命令融合
- SFB
- 命令数の削減(コンパイラと拡張命令)
- FPU は CoreMark に効かないので縮小し、浮いた LUT を整数側に回す

**4. 「測ってから作る」ために、Phase 0 で性能モデルを作ります**
- Spike で CoreMark のトレースを取り、C++ のトレース駆動モデルを作ります。
- このモデルで mmRISC-2 の CPI 1.103 を再現できるよう校正してから、幅・予測器・融合を比べます。
- 予測 CoreMark/MHz と LUT 予算が数字で出た時点で、マイクロアーキテクチャを凍結します(ゲート G0)。

**5. 開発順は CoreMark 先行です**
まず整数 OoO コアだけを作り、シミュレーションで CoreMark 目標に到達させます。その後に MMU / FPU / Linux を足します。後から壊れないように、非投機化と精密例外の受け口は最初の仕様から入れておきます。正しさの確認には、Spike とのコミット単位の比較を初日から使います。

**現実的な見込み**:`-O2` で 4.5〜5.0、最大最適化で 5.0〜5.5 です。ここまでは推定で、Phase 0 で検証します。最大最適化で 6.0 以上は、融合・SFB・命令数削減のすべてが効いた場合の上振れと位置づけています。

文書の §8 に、ご判断いただきたい点(D1〜D6:目標の扱い、幅、FPU、周波数、Ethernet、リポジトリ)を推奨付きで並べています。

GitHub は認証済みで、`mmRISC-3` という名前はまだ空いています。作成すれば、mmRISC-2 と同じ形(Apache-2.0、main / dev、README は英日)で初回コミットして push します。

#### 今回新しく分かったこと(資源の実測)

mmRISC-2 のビルド結果に、配置後の階層別使用量の実測レポートが残っていたので、それを使いました。

- **見積りが外れていた点**:LiteX の周辺回路は 11〜13k LUT と見積もっていましたが、実際は **4.8k LUT** でした。コアに使える分は約 34.6k LUT に増えます。
- **FPU が最大のブロック**:FPU はコア全体の 27%(**8.8k LUT**)を占めていました。
  - CSR・MMU・乗除算器・FPU など、OoO に関係なく必要な部分だけで 21.7k LUT あります。
  - そのため、OoO の本体に残るのは約 12.9k LUT です。NaxRiscv の整数コア(約 18k)より少なく、**FPU を小さくするかどうかが資源配分の最大のレバー**になります。
  - Doc/STRATEGY の資源予算の章には、この訂正を追記しました。

#### 主な検討項目と課題・対策

| 項目 | 課題 | 対策 |
|---|---|---|

- **TRACE の見立てを一つ訂正します。** 「taken 分岐のたびに1サイクル空くと −19%」は、フェッチと dispatch を直結した限界モデルの見積りでした。16バイトのフェッチをバッファで切り離すと、この空きはほぼ吸収されます。uBTB をなくしても −0.9% で、効くのはフェッチ幅の方でした(8バイトにすると −3.8%)。ISSUES の 3.2節にもこの訂正を注記しました。
