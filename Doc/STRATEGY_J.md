# mmRISC-3 開発戦略(CoreMark最優先)

- 作成日: 2026-10-23
- 前提資料: `Plan/PRESTUDY_MMRISC2_J.md`(2026-10-13の検討メモ)、mmRISC-2のホワイトペーパー、`LitexSystem/docs/BENCH.md`、`TIMING.md`
- 位置づけ: 方向性を固めるための戦略。数値のうち「実測」とあるものはmmRISC-2の記録、それ以外は見積りで、Phase 0で検証する

---

## 0. 結論の要約

1. **目標を「命令数 × IPC」に分解すると、要求の厳しさがはっきりする。** mmRISC-2の`-O2`(Zba/Zbb)はCoreMark 1回あたり**318.6k命令**(実測)。この命令数のままでは、5.0/MHzに**IPC 1.59**、6.0/MHzに**IPC 1.91**が必要。2命令幅の上限は2.0なので、6.0は理論限界の96%で、現実的ではない。
2. 前回の検討メモは「天井は約1.6倍(約4.9/MHz)」と見ていた。今回の目標はそれを超えるため、**メモのたたき台(控えめなOoO)のままでは届かない**。設計の重心を「CoreMarkのCPIスタックを潰すこと」に置き直す。
3. 最大の敵は**分岐予測ミス**。mmRISC-2のCoreMarkは1000命令あたり13回のミス(実測)。OoOでミス1回を約10サイクルとすると、それだけで1000命令あたり130サイクルを失い、5.0/MHzの予算(後述128サイクル)を使い切る。**予測器(TAGE系、BRAM)と浅いパイプラインが最優先**。
4. IPC 2の壁を越える手段は3つ: (a)**マクロ命令融合**(2デコード枠で最大4命令)、(b)**短い前方分岐の述語化(SFB)**で予測ミス自体を消す、(c)**コンパイラと拡張命令で命令数を減らす**。デコード幅3は、Arty A7-100TのLUT予算(後述)ではほぼ入らない。
5. 進め方の原則は mmRISC-2で確立した「**測ってから作る**」。RTLを書く前に、**トレース駆動の性能モデル**を作り、mmRISC-2の実測CPIで校正したうえで構成を決める(Phase 0、Gate G0)。
6. 開発順は**CoreMark先行**: まず整数OoOコアをシミュレーションでCoreMark目標に到達させ(M-mode、ベアメタル)、その後にMMU / FPU / デバッグ / Linuxを載せる。ただしLinuxに必要な非投機化・精密例外の「受け口」は最初から設計に入れる。
7. 現実的な見込み(要検証): `-O2`で**4.5〜5.0/MHz**、最大最適化で**5.0〜5.5/MHz**。**最大最適化で6.0以上は、融合とSFBと命令数削減がすべて効いた場合の上振れ**と位置づける。Phase 0のモデルで、この見込みを数字で確定させる。
8. **2026-10-24改訂(サイクルモデルの結果、`Plan/MODEL_J.md` 6章)**: OoO 2幅は融合なしでも`-O2` 6.07、最大最適化 6.57、悲観的な構成で5.61 / 6.05。**作者の指示により「融合構成」(4命令デコード、ALU + ALUの連結までの融合)を基準とする**(基準7.06 / 7.59)。融合した組が書くレジスタを1本に限ると6.75 / 6.90に下がるので、組あたり2本の書き込みを前提に、そのコストをOOC合成で確かめる。構成は4章の表の右の列。

## 1. 目標の分解

### 1.1 CoreMark/MHz、命令数、IPCの関係

CoreMark/MHz = 10^6 / (1回あたりのサイクル数) = 10^6 × IPC / (1回あたりの命令数)

| ビルド | 1回あたり命令数 | mmRISC-2(実測) | 5.0/MHzに必要なIPC | 6.0/MHzに必要なIPC |
|---|---|---|---|---|
| `-O2`、Zba/Zbb | 318.6k(実測、SIM_SYS) | 2.794/MHz、CPI 1.123 | **1.59** | **1.91** |
| 最大最適化(sf)、Zba/Zbb | 294.5k(実測、Spike) | 3.034/MHz | 1.47 | **1.77** |
| `-O2`、GCC 14.2、Zba/Zbb/Zbs/Zicond | 311.9k(実測、Spike) | — | **1.56** | 1.87 |
| 最大最適化(sf + `-flto`)、GCC 14.2、同上 | 281.0k(実測、Spike) | — | 1.40 | **1.69** |

命令数の測定の詳細は`Plan/ICOUNT_J.md`(2026-10-24)。GCC 14.2 + Zicondで、必要IPCは`-O2`の5.0で1.56、最大最適化の6.0で1.69に下がった。

- 2命令幅で持続的に出せるIPCは、良くできた設計でも1.3〜1.6程度が相場(NaxRiscv RV32 2デコードの5.02/MHzも、この範囲と考えられる)。
- **`-O2`で6.0は2命令幅では狙わない**。`-O2`は5.0、最大最適化で6.0を目標とする。

### 1.2 IPC予算(CPIスタック)の例: `-O2`で5.0/MHz

1000命令あたりのサイクル数で、使える予算は628サイクル。理想の2命令/サイクルが500なので、**ロスに使えるのは128サイクルだけ**。

| 項目 | 予算例(1000命令あたり) | mmRISC-2の状況(実測) |
|---|---|---|
| 理想(2命令/サイクル) | 500 | — |
| 分岐予測ミス | 40(ミス4回 × 10サイクル) | ミス13回、1回約5サイクル(8段インオーダー) |
| フロントエンドのバブル(taken分岐、I$ミス) | 30 | I$ミス0.49回 |
| データ依存(load-use、乗算、直列の依存鎖) | 45 | load-use 2.0%、乗算待ち2.6% |
| 構造的な詰まり(ポート競合、ROB / IQ満杯) | 13 | — |
| **合計** | **628 → IPC 1.59** | CPI 1.123 |

この表から決まること:
- **予測ミスは1000命令あたり4回以下**が必要(現状の1/3)。CoreMarkは毎回同じ入力を処理するので、長い履歴を持つ予測器が学習しやすい。TAGE系をBRAMで大きく持つのが割に合う。
- **予測ミス1回のコストは10サイクル以下**。50MHz固定の20nsを、段数の削減(=ペナルティの削減)に使う。
- **taken分岐でバブルを出さない**フロントエンド(0バブルのnext-line予測)が必要。

### 1.3 測定条件の固定(最初に決める)

性能目標を議論する前に、比較の条件を固定しておく。mmRISC-2と同じ条件を引き継ぐ。

| 項目 | 方針 |
|---|---|
| 測定場所 | ボード上、Linux上、50MHz(mmRISC-2のBENCHと同じ`bench.sh`) |
| `-O2`の定義 | `-O2`のみ。`-march=rv64imafdc_zicsr_zifencei_zba_zbb_zbs_zicond`(**Zicondを含む。ハードもZicondを実装する**。2026-10-24決定) |
| 最大最適化の定義 | CoreMarkの実行規則の範囲で任意のオプション(ソースは変更しない)。使ったオプションをすべて記録 |
| コンパイラ | **GCC 14.2(Debian 13、ボード上のgccと同じ)に固定**(2026-10-24決定、根拠は`Plan/ICOUNT_J.md`) |
| ビットストリーム | Linux動作版と**同じビットストリーム**で測る(CoreMark専用の構成は作らない) |

## 2. 性能を決めるレバー(CoreMarkに効く順)

| 順位 | レバー | 内容 | FPGAでのコスト |
|---|---|---|---|
| 1 | 分岐予測の精度 | TAGE(4〜6テーブル、長い履歴)+ ループ予測、BTBとPHTをBRAMへ | BRAM中心、LUTは小 |
| 2 | 予測ミスのペナルティ | 50MHzの余裕で段を統合。目標: 分岐の実行から正しい経路の命令の実行まで10サイクル以下 | 段が減るとFFも減る |
| 3 | SFB(短い前方分岐の述語化) | 「1〜2命令を飛び越す分岐」を条件付き実行に変換し、予測ミスを消す | 小(デコードとALU) |
| 4 | フロントエンド帯域 | 16B/サイクルのフェッチ、FTQによる分離、0バブルのnext-line予測、RVCアライナ | 中 |
| 5 | マクロ命令融合 | `lui+addi`、`auipc+jalr`、`slli+srli`、`add+load`など。融合率はトレースで実測してから選ぶ | 小〜中(デコーダ) |
| 6 | load-useの短縮 | D$ヒット2サイクル + ヒット予測による投機的wakeup、ストアからロードへのフォワード | 中 |
| 7 | 依存の短絡 | ALUの1サイクルwakeup-select、乗算の1〜2サイクル化(DSP48) | 中 |
| 8 | 命令数の削減 | Zicond / Zbs、コンパイラとオプション(融合しやすい命令列を出す`-mtune`) | ハードは既存 |
| 9 | メモリ依存の投機 | 古いストアのアドレス未確定でもロードを出す(store-set簡易版) | 中〜大。モデルで効果を確認してから |

**2026-10-24追記**: トレース解析(`Plan/TRACE_J.md` 4章)とサイクルモデル(`Plan/MODEL_J.md` 6.4節)の結果、順位は次のとおり改める: 1 予測器(TAGE-S)、2 融合と4命令デコード、3 load-use 2サイクル、4 ストアからロードへのフォワーディング、5 フェッチ幅16バイトとdispatchとの分離。SFBは対象外。予測ミスのペナルティ(段数)とuBTBは、OoOではほとんど効かない。

実行ユニットを増やすと、すぐ収穫逓減に入る(NaxRiscvの知見)。**CoreMarkではユニットの数より、予測と遅延の短さが効く**。

## 3. 資源予算(Arty A7-100T)

| 項目 | 値 |
|---|---|
| デバイス | XC7A100T-1: LUT 63,400、FF 126,800、BRAM 135、DSP 240 |
| mmRISC-2 Rev.02 | LUT 79%、スライス93%(実測)。スライスの逼迫が配線遅延の主因だった |
| 実用上限 | LUT 80〜82%(約51k) |
| LiteX SoC(LiteDRAM / LiteEth / SD / UART) | 約1.1〜1.3万LUT(推定、Phase 0で実測) |
| L1 / L2 / MMIO | 約9k LUT(mmRISC-2の値から推定) |
| **コアに使える分** | **約3万LUT**(FPU、MMU、CSR、デバッグ込み) |

mmRISC-2のうちOoOと無関係に必要な部分(CSR約3.3k、MMU約5k、FPU+FRF約6k、MDU約1.1k、デバッグ)だけで約1.5万LUT。**OoOエンジン + フロントエンド + LSUに残るのは約1.5〜1.6万LUT**。NaxRiscv RV64(整数のみ)がコア全体で約1.8万LUTなので、**かなり厳しい**。

**2026-10-24追記**: mmRISC-2 Rev.02の階層別の実測で、LiteXは4.8k LUT、FPUは8.8k LUTと分かった。上の見積りは`Plan/ISSUES_J.md` 2章で訂正している(コアに使える分は約34.6k、OoO関係に残る分は約12.9k)。

ここから決まること:
- **デコード幅3は入らない前提**で設計する(2幅 + 融合 + SFBでIPCを稼ぐ)。
- **FPUはCoreMarkに効かないので、LUTを整数側に回す**。検討メモの案3(マルチサイクルFPU)か案4(インオーダーのサイドパイプ)を第一候補とする。Debian(lp64d)のためにF/Dは残す。
- 大きな表はBRAM / LUTRAMへ(予測器、ROBペイロード、PRF、RAT)。FFで組まない(mmRISC-2でBTBをFF→LUTRAMにして3,060 LUT / 7,936 FFを削った前例がある)。
- PMPを16 → 8エントリ、トリガ4 → 2など、Linuxに不要な分を削る候補を用意する。

## 5. 「測ってから作る」: Phase 0の性能モデル

### 5.1 なぜ先にモデルか
- 2幅でどこまで届くか、融合とSFBがどれだけ効くかは、**CoreMarkの命令列を使って測れば数日で答えが出る**。RTLで試すと1つの選択に1〜2週間かかる。
- mmRISC-2では、シミュレーションの仮定の誤り(メモリが即答する)で「速くなる」と誤判定した経験がある(I$プリフェッチ)。**モデルはmmRISC-2の実測で校正してから使う**。

### 5.2 内容
1. **命令トレースの取得**: Spike(lock-step検証にも使うので、ここで導入する)でCoreMarkのコミットトレースを取る。`-O2` / 最大最適化 × GCC 13 / 14 / 15 × `-march`の組み合わせで、**命令数**をまず表にする(これだけで必要IPCが決まる)。
2. **トレース駆動のサイクルモデル**(C++): 幅、ROB / IQ / PRFのサイズ、予測器(gshare / TAGE、サイズ)、ペナルティ、load-use、融合の組、SFB、メモリ依存の扱いをパラメータにする。
3. **校正**: インオーダー8段の設定で、mmRISC-2のCoreMark CPI 1.103(SIM_SYS)と予測ミス率5.4%を±3%以内で再現させる。
4. **設計空間の探索**: パラメータをスイープし、CoreMark/MHzへの寄与を表にする。
5. **資源との突き合わせ**: NaxRiscv RV64をLiteXでArtyに実装して実測(LUT、Linuxでの性能)、mmRISC-2の階層別utilizationをRev.02で取り直す。

### 5.3 後々の使い道
- RTLの**性能の参照**になる: RTLのCoreMarkサイクル数がモデルから外れたら、性能バグとして調べる(mmRISC-2のdecision 82のような0.8%の損失を見つける仕組み)。

## 6. 検証戦略

mmRISC-2の資産(SIM_CORE / SIM_SYS / SIM_BIOS、riscv-tests、バグ注入)に、OoO固有の仕組みを**最初から**加える。

| 手段 | 目的 |
|---|---|
| **Spikeとのコミット単位lock-step比較** | 命令ごとの正しさ(RVFI相当のコミットトレースI/Fを最初に設計する) |
| ランダム命令列(riscv-dvまたは自作) | 依存の密度を上げ、リネーム・リカバリの穴を突く |
| 例外・割り込みの注入 | 予測ミス中の割り込み、投機経路上のページフォールト |
| Konata形式のパイプライン表示 | OoOのデバッグ効率 |
| 性能モデルとのサイクル比較 | 性能バグの検出 |
| バグ注入 | リネーム、フリーリスト、チェックポイント、LSQに注入し、検出力を確認 |
| コミットトレースのリングバッファ(BRAM) | ボード上のデバッグ(ILAを置く余裕はない) |

## 7. フェーズとゲート

| Phase | 内容 | ゲート(完了条件) |
|---|---|---|
| **0** | リポジトリ立ち上げ、測定条件の固定、命令数の表、性能モデルと校正、設計空間の探索、NaxRiscvの実測、資源予算 | **G0**: マイクロアーキテクチャ仕様の凍結。予測CoreMark/MHzとLUT予算を数字で示す。目標に届かない場合は、ここで目標か構成を見直す |
| 1 | 整数OoOコア(2幅、M-modeのみ、ベアメタル)、Spike lock-step、riscv-tests(rv64ui/um/uc + Zb系) | **G1**: シミュレーションでCoreMarkがモデルの±5%。Vivadoでコア単体(OOC)のLUTと50MHzを確認 |
| 2 | 特権 / CSR / MMU / 例外 / デバッグ / FPU(縮小版)、非投機化一式 | **G2**: SIM_BIOSでLinuxのプロンプト、全テストPASS、バグ注入全検出 |
| 3 | LiteX統合、タイミング、ボードでLinux(BusyBox、Debian 13) | **G3**: 120分ストレステストPASS、ボードでのCoreMark測定 |
| 4 | 性能の詰め(予測器の拡大、融合の追加、メモリ依存投機など、モデルで効果を確認したものから) | **G4**: 目標の達成、またはやめどころの判断(mmRISC-2と同様、見込み数%未満のテーマは切る) |

**Phase 1をCoreMark先行にする理由**: 最優先の指標で、最も速い反復(シミュレーション)を回せる。リスクは「後からLinux対応を足すと壊れる」ことなので、ROB先頭での直列化、精密例外、MMIOロードの非投機化の受け口はPhase 1の仕様に含める。

| D2 | 幅 | 2 µop幅 + 融合 + SFBで固定。3幅はG0で資源が大きく余った場合のみ再検討 | 推奨どおり(SFBはトレース解析で外した。`Plan/TRACE_J.md`) |
| D3 | FPU | マルチサイクル縮小版またはインオーダーのサイドパイプ(LUTを整数側へ) | **当初はパイプラインのFPU(mmRISC-2のFPU_PIPE)で進める**。論理規模の状況で再検討する。**G0(2026-10-24、`Doc/UARCH_J.md` 5章): mmRISC-2の多サイクルのFPUはパイプラインのものより大きかった(9,757と9,060 LUT)ので、FPU_PIPEを残す。手段は内訳(C1)のあとのC2 / C3** |
| D4 | 周波数 | 50MHz固定。CoreMark/MHzが指標なので、周波数の余裕は段数削減に使う | 50MHz固定 |
| D5 | Ethernet | Linux構成として残す。LUTが足りない場合の削減候補の1番目 | **残す**。論理規模の削減は別の案で行う(`Plan/REDUCE_J.md`) |
| D6 | リポジトリ | mmRISC-2と同じ形(Apache-2.0、main / dev、文書は英日2言語) | 推奨どおり |

**G0(2026-10-24)**: 条件付きで通過。決定は`Doc/UARCH_J.md` 9章にある。原則として、mmRISC-2 Rev.02の命令セットを維持する。命令を減らす削減はしない(Zbcは残す)。

## 9. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| LUTが入らない | 構成の縮小 | Phase 0で予算化、G1でコア単体を合成、FPU縮小、PMP等の削減 |
| 2幅でIPC 1.6に届かない | 目標未達 | G0で早期に判明させる。融合とSFBの効果をモデルで先に確認 |
| -1グレードで50MHzが閉じない | 段の追加でペナルティ増 | wakeup-selectを早期にOOC合成で評価、ALU 2サイクル化(性能約15%減)は最後の手段 |
| OoOのLinux固有バグ(MMIO、A/D更新) | ボードで原因不明の停止 | 非投機化の一覧を仕様化、SIM_BIOS、例外注入 |
| 性能モデルの仮定違い | 誤った選択 | mmRISC-2の実測で校正、RTLとのサイクル比較を継続 |
