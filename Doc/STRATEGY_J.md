## 0. 要約

1. **FPGAを大きくする。** Arty A7-100TのXC7A100Tを、**Digilent Nexys VideoのXC7A200T-1SBG484C**に替える。古いデバイスに入れるための削減が、アウトオブオーダーにする意味である性能を削っていた。
2. **目標**: `-O2`で**6.0 CoreMark/MHzを余裕をもって超える**、50 MHzで。そのうえでBusyBoxとDebian 13をmicroSDスロットJ3から起動し、Ethernet(RTL8211E)と、Pmod JAのJTAG / cJTAGを使う。
3. **2命令幅では余裕をもって届かない**: すべての手を打ってもモデルで6.07(融合ありで6.37)で、RTLはモデルより約6 %低い。**提案は3命令幅のコア**(完全なALU 3つ + LSU、4発行、IQ 16、ROB 32、LQ / SQ 12、チェックポイント8、TAGE M): **モデルで7.17、RTLで約6.7**。
4. **限界は論理規模ではなく50 MHzになる。** チップは134,600 LUTのうち約84k(62 %)の見積もり。XC7A200Tの速度グレードは同じで、2命令幅のコアでも+0.159 nsしかない。
5. **3つのステップ**(5章): コア、ボード、Linux。**ボードの立ち上げは、動くと分かっているCPUのmmRISC-2で**、ボードが届きしだい、コアと並行して始める。

## 1. 方針を変える理由

今のコアから見たモデルのCoreMark/MHz(`Plan/model/g200t.sh`、`results/g200t.txt`。目標を測るビルドの`g14 -O2`):

| 構成 | モデル、`-O2` | RTLの見込み(× 0.94) |
|---|---|---|
| 2026-11-02のコア(2命令幅、ROB 24、IQ 10、LQ / SQ 8、機能を絞ったALU1) | 5.805 | 5.50(実測) |
| 2命令幅、ROB 48 / IQ 16 / LQ、SQ 12 / チェックポイント8を1つずつ | 5.81〜5.85 | — |
| 2命令幅、融合以外のすべて | 6.072 | 5.7 |
| 2命令幅、すべて + 融合2 | 6.368 | 6.0 |
| **3命令幅、ほかの大きさは今のまま** | **6.693** | 6.3 |
| **3命令幅、提案(4章)** | **7.170** | **6.7** |
| 提案 + ストアをアドレスとデータに分ける | 7.324 | 6.9 |
| 提案 + ストアの分割 + LSUポート2つ | 7.504 | 7.1 |
| 4命令幅、参考 | 8.413 | 7.9 |

- 2命令幅では大きさはほとんど効かない: 幅そのものが限界になっている。古い予算の下では見えなかったこと。
- × 0.94は、今のRTLのモデルに対する比(5.50 / 5.805、5.92 / 6.322、5.32 / 5.668)。
- G0bの削減(`Doc/UARCH_J.md` 6.3のL1〜L7)は、効くものから戻せる。

## 2. 目標と測り方

| 項目 | 決まり |
|---|---|
| 目標 | `-O2`: **6.0 CoreMark/MHzを余裕をもって超える**。作業上の目標は**RTLで6.5、ボードで6.2** |
| どこで測るか | ボード上、Linux上、50 MHz、Linuxを動かすビットストリームで(`Plan/STRATEGY_A100T_J.md` 1.3と同じ) |
| コンパイラ | GCC 14.2(Debian 13)。`-O2 -march=rv64imafdc_zicsr_zifencei_zba_zbb_zbs_zicond` |
| シミュレーション | 本物のキャッシュとDDR3の遅延モデルをつけた`OOO_CPU`、Spikeとのロックステップ |

mmRISC-2はシミュレーションからボードで約2 %失った(CPI 1.103から1.123)。そのためボードで6.2にはRTLで6.5。

## 3. XC7A200Tの資源

| | XC7A100T(Arty A7-100T) | **XC7A200T(Nexys Video)** | 比 |
|---|---|---|---|
| LUT | 63,400 | **134,600**(33,650スライス) | 2.12 |
| ブロックRAM | 135タイル(4,860 Kb) | **365タイル**(13,140 Kb) | 2.70 |
| DSP | 240 | **740** | 3.08 |
| CMT | 6 | 10 | |
| 速度グレード | -1 | **-1(同じ)** | |
| DDR3 | 256 MiB、16ビット | **512 MiB**、16ビット、ボードは800 MT/s | |

チップ全体(物理LUT。実用上の上限は80 %のまま、**107.7k**):

| 部分 | LUT | 根拠 |
|---|---|---|
| EthernetつきLiteX SoC | 5.3k | mmRISC-2の4,826(MII)。RGMIIとDRAMのクロックの乗り換えは見積もり |
| コアの外: L1キャッシュ、L2、デバッグ、MMIO、DMA、アービタ | 12.6k | mmRISC-2の実測 |
| 残すコアのブロック: CSR、MMU、MDU、FPU、FPレジスタ | 21.7k | mmRISC-2の実測 |
| **アウトオブオーダーの部分、提案** | **約44k**(40k〜48k) | `Doc/UARCH_J.md` 4.5。今の2命令幅は実測27.0k |
| **合計** | **約84k、62 %** | モデルが次に挙げるものに約24k残る |

ここから言えること:

- `Plan/REDUCE_J.md`のグループA(トリガ、PMP、D$のバッファ、TLB)は**もういらない**: mmRISC-2のブロックは元の大きさのままで、HPMカウンタも4つに戻す。
- ブロックRAMに余裕があるので、大きなTAGEや、Linuxに効くと測れれば512 KBのL2も置ける。
- **限界はタイミングになる。** XC7A200Tは速くならず、3命令幅は、+0.159 nsのコアにバイパス元、広い選択、レジスタファイルのポートを足す。今は面積をタイミングに使える(タグの複製、判定のレジスタ化)。

## 4. 提案するマイクロアーキテクチャ

関門S1-A(5章)で、D1のグループの境目を入れたモデルに照らして確定する。

| 項目 | 今(2026-11-02) | **提案** | 理由 |
|---|---|---|---|
| フェッチ、デコード | 16 B、1サイクルに4命令 | 同じ | 3命令幅では6命令と32 Bの効きは小さい(3.7 %) |
| **デコードとリネームの間** | 空のときだけ補充するグループレジスタ | **デコード済み命令のキュー** | 3命令幅で今の決まりだと2サイクルに3 + 1 µopになる(`Plan/CORE_J.md` 5.19) |
| **リネーム、ディスパッチ、コミット** | 2 | **3** | 一番大きな効果(+15 %) |
| **ALU** | ALU0は完全、ALU1は機能限定 | **完全なALU 3つ**、それぞれ分岐も | L7は1.6 %と引き換えのLUT削減で、今はLUTがある |
| LSU | 1ポート、ロードかストア1つ | 同じ。2ポートは次の候補(+4 %) | |
| 発行 | 統合10、1サイクルに3 | **統合16、1サイクルに4** | |
| ROB、レジスタ | 24、64本 | **32**、64本 | 32 + 32で足りる |
| LQ / SQ、チェックポイント | 8 / 8、6 | **12 / 12、8** | |
| 予測器 | TAGE S、uBTB 8 | **TAGE M、uBTB 16** | ブロックRAMがある |
| 乗算 | パイプライン + CORE_MDU、書き込み枠を共用 | 同じ、書き込み枠は専用 | |
| ロードから使用まで | 2サイクル | **2サイクル(必須)** | 3にすると10 %失う(6.42) |
| 融合 | オフ(`FUSE_KINDS` 0) | **オフのまま**。幅のあとで削除か復活を決める | 3命令幅では効きが小さく、比較が入らない(`Plan/OOC_J.md` 27.5) |
| FPU、MMU、デバッグ | まだコアにない | mmRISC-2のものを元の大きさで | ステップ1 |
| 周波数 | 50 MHz | 50 MHz | 作者の決定 |

### 4.1 4命令幅にするか

(作者の質問、2026-11-02。)**言葉の注意**: 今のコアは1サイクルにリネーム2、発行3(ALU 2 + LSU)。提案は**すでに4発行**(ALU 3 + LSU)で、リネーム3。4発行でディスパッチ2のコアは6.04しか出ない: 効くのはリネームとディスパッチの幅である。下の「4命令幅」は、リネーム、ディスパッチ、コミットが4のこと。

| 構成 | モデル`-O2` | RTL(× 0.94) | OoO部分の見積もり | チップ | 幅のほかに必要なもの |
|---|---|---|---|---|---|
| **3命令幅、提案** | **7.17** | **6.7** | 44k | 84k、62 % | |
| 3命令幅、LSU 2ポート | 7.46 | 7.0 | 50k | 92k、68 % | 2ポートのD$ |
| 4命令幅、ALU 3 + LSU、提案の大きさ | 7.22 | 6.8 | 48k | 88k、65 % | ほとんど得がない |
| 4命令幅、ALU 4 + LSU、IQ 24、ROB 48 | 7.45 | 7.0 | 56k | 96k、71 % | フェッチが制限する |
| 4命令幅、ALU 3 + LSU 2 | 7.75 | 7.3 | 60k | 102k、76 % | 2ポートのD$ |
| 4命令幅、ALU 4 + LSU 2 | 7.83 | 7.4 | 64k | 106k、79 % | 2ポートのD$ |
| 4命令幅、ALU 4 + LSU、デコード6、32バイトフェッチ | 7.97 | 7.5 | 65k | 105k、78 % | 32バイト幅のI$ |
| **4命令幅、ALU 4 + LSU 2、デコード6、32バイトフェッチ** | **8.60** | **8.1** | **73k** | **115k、85 %** | 両方。**80 %を超える** |

(4命令幅の見積もりは、3命令幅と同じブロックごとの拡大から出したもので、より粗い。書き込み6、読み出し9のレジスタファイルは実測で5,299 LUT、+1.769 ns。)

- **面積だけなら可能**: 4命令幅はXC7A200Tに上限の約106kまで入る。全部入りは入らない。
- **4命令幅だけではあまり効かない**(+0.7〜3.8 %): 16バイトと4命令のデコード、1つのLSUポートが限界になる。効かせるのは広いフェッチと2つ目のLSUポートで、それぞれが大きな作業になる(I$、プリデコード、フェッチバッファ。2ポートのD$)。
- **本当の問題は面積ではなく50 MHz**: リネームの依存の比較は1サイクルに1個から6個に、バイパスは3元から6元に、選択は3ポートから5か6ポートになる。2命令幅のコアで+0.159 ns。測らないと分からない。
- **おすすめ**: 目標に余裕をもって届く3命令幅を先に。ただし**幅はパラメータにする**(手順1.4)、大きさも。S1-Bのあとは測った効果の順に、**LSU 2ポート(+4 %)、次にW = 4**、32バイトフェッチと、50 MHzが保てる限り進める。今3を選んでも4を閉ざさない。
- **今すぐできる安い測定**: `synth_ooo.bat OOO_IQ 20.0 1 N=24`で24エントリのキューが見える(今の3ポートで)。

## 5. 作業の順序

### ステップ1: コアとそれに伴うもの

| # | 作業 | 終わる条件 |
|---|---|---|
| 1.1 | D1の境目とキューを入れたモデル。RTLとモデルのほかの違い(`Plan/CORE_J.md` 5.12) | **関門S1-A**: 構成の確定、モデルで`-O2` ≥ 7.0 |
| 1.2 | `synth_ooo.tcl`を新しい品種に(済み)。今の`OOO_CPU`をXC7A200Tで合成し、大きなデバイスでの時間とタイミングを見る | 比較の基準ができる |
| 1.3 | D1bの補充の決まりをデコード済みキューに替える。融合のRTLの扱いを決める | 単体テスト。2命令幅のCoreMarkが悪化しない |
| 1.4 | 幅をパラメータに: リネーム、DS、ROB、IQとペイロード、レジスタファイル、制御、コミット、トレース、ロックステップ、各ブロックのテスト。まずW = 2でサイクルを変えずに、次にW = 3 | 両方の幅で全テスト |
| 1.5 | 完全なALU 3つ、バイパス、書き込みポート。IQ 16、ROB 32、LQ / SQ 12、チェックポイント8、TAGE M、uBTB 16を1つずつモデルと比べて | 各段階のサイクルがモデルと合う |
| 1.6 | 各段階のタイミング: `OOO_CPU`の単体合成 | ずっと50 MHzを保つ |
| 1.7 | 本物のI$(mmRISC-2のものを16バイト幅に)とL2。`OOO_CPU`でCoreMark | **関門S1-B**: 本物のキャッシュでRTLの`-O2` ≥ 6.5、50 MHz、テストとバグ注入がきれい |
| 1.8 | 割り込み、MMU(Sv39)、FPU、デバッグ、PMU。F / D / Sのアーキテクチャテスト。シミュレータでLinux | **関門S1-C**: シミュレーションでLinuxのプロンプト |

### ステップ2: 周辺とボード

ボードが届いたら**ステップ1と並行して**始める。一番実績のあるCPUから新しいCPUへ進む: LiteXの標準SoC、mmRISC-2、mmRISC-3。問題はボードか周辺のものと切り分けられ、新しいコアを疑わなくてすむ。

| # | 作業 | 終わる条件 |
|---|---|---|
| 2.0 | **LiteX自身のターゲットをそのまま**(`Doc/BOARD_J.md` 2): 100 MHzのRocket、SDとEthernet。Vivadoの実行にボードはいらない: **ボードが届く前にできる** | ボードで: BIOS、DDR3-800のメモリテスト、SD、TFTP。Artyの`LitexRocket`のように参照としてRocketでLinux |
| 2.1 | mmRISC-2のものからこのリポジトリに`LitexSystem/`を作り、CPUのラッパーをLiteXのターゲットに載せる。CPUはmmRISC-2。制約 | ボードでLiteX BIOSのプロンプト |
| 2.2 | JEDECの範囲内のDDR3(`Doc/BOARD_J.md` 4): LiteXは100 MHzのまま、CPUは50 MHzでクロックの乗り換えを通す | 512 MiBのメモリテスト |
| 2.3 | J3のmicroSD(`SD_RESET`、タイミング制約)。RTL8211EとのRGMII | SDカードからBIOSが起動。1 Gb/sでTFTPとDHCP |
| 2.4 | JAのJTAG / cJTAG、スイッチとLED(`Doc/BOARD_J.md` 7、8) | 4つの組み合わせで`jtag_check.tcl` PASS |
| 2.5 | ボードの立ち上げの記録。DRAMの遅延を測り、シミュレーションのメモリモデルに返す | |
| 2.6 | mmRISC-2をmmRISC-3に替える(S1-Cのあと)。チップ全体のタイミングを50 MHzで | **関門S2**: mmRISC-3でボードのBIOS |

### ステップ3: Linux

| # | 作業 | 終わる条件 |
|---|---|---|
| 3.1 | OpenSBI、デバイスツリー(512 MiB、新しいCSRの配置)、LiteEth / LiteSDCardのドライバを入れたカーネルの設定 | J3からBusyBoxまで起動 |
| 3.2 | LinuxのEthernet(DHCP、ping、TFTP、NFSかssh)、MACアドレス(固定かEEPROMから) | RTL8211Eで通信 |
| 3.3 | 第2パーティションにDebian 13。ボード上のgcc | ボード上でCoreMarkをビルド |
| 3.4 | Linux上のCoreMark。120分のストレステスト(メモリ、Ethernet、SDを同時に) | **関門S3**: `-O2`で6.0を余裕をもって超える、ストレステストPASS |

### 依存関係

- ボードの発注が最初(`Doc/BOARD_J.md` 10): ステップ1には不要だが、ステップ2、3に必要で、納期が長い可能性がある。
- 2.5のDRAMの遅延は1.7に返す。2.6にはS1-Cが必要。3.1は2.4のあとmmRISC-2で始められるので、新しいコアが来る前にカーネル、デバイスツリー、SDカードのイメージを確かめられる。

## 6. 検証

種類は変わらない: 命令ごとのSpikeとのロックステップ、riscv-arch-test、全ブロックとつなぎへのバグ注入(`SIM/OOO_UNIT`、`SIM/CORE`)、モデルとのサイクル比較。新しいこと: 幅がパラメータのあいだ各テストを両方の幅で。ステップ2のボードの確認はまずmmRISC-2で。

## 8. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| 3命令幅が50 MHzで閉じない | 幅を減らすかパイプラインを伸ばす | 1.5の各段階で測る。今は面積でタイミングを買える。2命令幅のコアも作れるまま(幅はパラメータ) |
| 3命令幅でRTLがモデルからさらに離れる | 余裕がなくなる(6.5には7.17の × 0.91が必要) | 関数ごとのサイクル比較(`Plan/CORE_J.md` 5.12)。ストアの分割とLSU 2ポートを予備に(+2〜5 %) |
| モデルの4命令のグループが別のフロントエンドの限界を隠している | 見積もりが高すぎる | RTLの前に1.1でモデルに入れる |
| 幅の作り直しが大きい | 時間。全ブロックとテストが変わる | まずW = 2でサイクルを変えずに、次にW = 3 |
| ビルドが長くなる | 繰り返しが遅くなる | 1.2で基準を取る。コアは単体合成で。ここではVivadoはWindowsのx86エミュレーションで動く |
| ボードの懸念 | `Doc/BOARD_J.md` 10 | |
