## 1. 結論

1. **性能: 目標を余裕をもって満たす**。G0の構成で、**`-O2`で6.56 CoreMark/MHz、最大最適化で6.80**(目標は5.0と6.0超)。悲観的なパイプライン(各部に1段ずつ足し、ロード使用を3サイクルにする。すべて同時)でも5.85 / 6.14。
2. **マイクロアーキテクチャを凍結する**(3章)。
   - 2幅のアウトオブオーダー、4命令デコードと融合(組あたりソース2本まで・書き込み1本まで)
   - uBTB 16 + TAGE-S、ROB 24、発行キュー12、物理レジスタ64本(書き込み3 / 読み出し6)
   - 2段連結のALUポート2つ、LSU 1つ(LQ / SQ 12)、チェックポイント6
   - G0の前の構成からの変更(ROB 32 → 24、発行キュー16 → 12、チェックポイント8 → 6)は −0.4% / −0.6%で、約1k LUTを減らす。
3. **予算はまだ閉じない**。
   - 必要量: Vivadoで測ったブロック(15.3k LUT。G0の変更を入れて約14.0k)と、まだ書いていないブロック(フロントエンド、デコード、ROB、LSUなど。見積り9.3k〜14.5k)で、**23.3k〜28.5k**。
   - 入る余地: **16.4k〜17.9k**(上限52k、mmRISC-2のほかのブロック、`REDUCE_J.md`のグループA)。
   - **超過は5.4k〜12.1k、中央で約8.8k**。
4. **D3(FPU): 前提が誤っていた**。mmRISC-2では、多サイクルのFPU(`CORE_FPU`、9,757 LUT)の方が、パイプラインのFPU(`FPU_PIPE`、9,060)より大きかった。多サイクル版も部分積をすべて一度に作っていたためである。「多サイクルに戻せば数k空く」には根拠がない。FPUで使える手段は、内訳の測定(C1)のあと、乗算器の共有(C2)と、まれな演算を小さな反復ユニットに移すこと(C3)で、1.5k〜3k。これから測る。
5. **超過の埋め方**(6章)。
   - 融合、Ethernet、上限に触れずに使える手段(Linux側の選択肢、FPU、小さな構造3つ(それぞれ −0.3〜−0.7%)、非対称ALU)で、約3.6k〜4.8k(FPUの分は2026-10-25にC1で測定)。見積りの下の端は埋まるが、中央は埋まらない。
   - 残る選択は、融合レベル2(−3.4% / −0.7%、約 −1.2k)、上限54k(+2k、タイミングのリスク)、最後に融合なし(−7.8% / −4.3%)かEthernetなし。
6. **G0の判定(案): 条件付きで通過**。性能とマイクロアーキテクチャはここで決める。予算は、フロントエンド、デコード、ROB、LSUを書いて測ったところ(どのみちPhase 1の最初の作業)で、**G0b**として改めて確かめる。FPUの内訳(C1)は作者が並行して測る。手段は6章の順に使う。
7. **G0b(2026-10-26、推奨どおり決定、6.3)**: 制御を除くすべてのブロックを実測し、超過は10.1k / 11.5k / 12.8k。新しい手段が見つかり(チェックポイントを6に戻す、コミットでのリプレイのトラップで10エントリの発行キューが損なしになる、まれな種類を1スロットでデコード)、すべての手段をモデルで測った。推奨: 何も失わない手段(3.1k)、トラップと10エントリ(1.9k、+0.2%)、L4〜L6(1.2k)、モデルでよければL7、融合レベル2、そして上限54kとPMP / HPMなしをG1で決める予備に: 中央で約+0.25kの余裕、CoreMark 6.25 / 6.70。

## 2. 目標と予測性能

目標(`STRATEGY_J.md` D1): `-O2`(Zba / Zbb / Zbs / Zicond、GCC 14.2)で5.0 CoreMark/MHz、最大最適化(sf + `-flto`)で6.0超。`Plan/model/results/g0.txt`より:

| 構成 | `-O2` | 最大最適化 | mmRISC-2の条件(g13 -O2 zb) |
|---|---|---|---|
| G0の前(ROB 32、発行キュー16、チェックポイント8) | 6.59 | 6.84 | 6.36 |
| **G0** | **6.56** | **6.80** | 6.35 |
| G0、悲観的なパイプライン | 5.85 | 6.14 | 5.69 |
| G0 + 小さな損失の手段3つ(6.2) | 6.45 | 6.75 | 6.28 |
| 同上、悲観的 | 5.65 | 5.97 | 5.53 |
| G0でALU + ALUなし(融合2) | 6.34 | 6.75 | 6.16 |
| G0で融合なし(2命令デコード) | 6.05 | 6.51 | 5.90 |
| 同上、悲観的 | 5.51 | 5.97 | 5.40 |
| G0 + 組あたり書き込み2本(W5、最初に買い戻す候補) | 6.87 | 7.40 | 6.64 |

- どの行も`-O2`の目標を満たす。最大最適化の目標(6.0超)を外すのは、ALU + ALUの余裕を持たない悲観的な行だけ(5.97)。**つまり、パイプラインが遅くなっても「6.0超」を守っているのは融合である**。
- 守らなければならないもの(G0からそれぞれ単独で): ロード使用2サイクル(3サイクルで −7.9%)、TAGE-S(gshareで −14.5%)、SQからのフォワーディング(なしで −4.3%、`MODEL_J.md`)、発行からEXまで1段(もう1段で −1.1%)。
- モデルの限界(`MODEL_J.md` 6.5)はそのまま当てはまる(誤ったパスの影響なし、LSUの再実行は理想化)。G1でRTLとモデルの差が±5%以内かを確かめる。

## 3. 凍結するマイクロアーキテクチャ

### 3.1 パイプライン

| ステージ | 仕事 |
|---|---|
| F0 | 次のフェッチアドレス: uBTB(G0bのL5から8エントリ、部分タグ)で1サイクル。F2と後段からのリダイレクトが優先 |
| F1 | I$の読み出し(ブロックRAM)、TAGE-SとBTBの読み出し(ブロックRAM) |
| F2 | I$のウェイ選択、プリデコード(RVCの境界、分岐とjalのターゲット)、TAGE-S / BTB / RASによる上書き(食い違えばF0へリダイレクト、2サイクルの損失)。16バイトをフェッチバッファへ(`OOO_FETCH`、`Plan/OOC_J.md` 14章) |
| D1 | フェッチバッファ(8パーセルの窓)から最大4命令を取り出し、RVCを展開してデコード |
| D2 | 融合(4命令 → 2 µop)、リネーム(RAT、フリーリスト、busy、チェックポイント) |
| DS | dispatch: 発行キュー、ROB、LQ / SQ、ペイロード |
| IS | wakeup-select(レイテンシ1のwakeupと合わせて1サイクル) |
| RR | レジスタファイルの読み出し(6ポート) |
| EX | バイパスと、ALUとそのあとの分岐の比較(融合レベル2、6.7) / アドレス計算 / 分岐の解決 |
| (M) | ロード: D$のアクセス。結果は発行の2サイクル後に後続へ(ヒットを予測して起こす) |
| WB、CM | レジスタファイルへの書き込み(3ポート)。ROBの先頭から1サイクルに2 µopコミット |

分岐予測ミスの損失はEXからEXまで10サイクル(D-15: フェッチは解決の1サイクル後に、FTQからの履歴とRASで再開する、`Plan/OOC_J.md` 21。EXから直接リダイレクトすれば9)。タイミングはモデルを基準とする(`fe_depth` 3、`dec_depth` 2、`iss_to_ex` 2、D-15から`redirect` 2、`override_at` 2)。

### 3.2 フロントエンド

| 項目 | 仕様 |
|---|---|
| フェッチ | 1サイクルに16バイト(整列)。takenの転送のあとは次のブロックから |
| フェッチバッファ | `OOO_FBUF`: 16バイトのブロックを丸ごと4つ、LUTRAMに(G0bのL6の2ブロックは、測って小さくならず戻した、6.10。手順2で16パーセルの輪に代えて決めた、`Plan/OOC_J.md` 13.1)。先頭のブロックと次のブロックにかかる8パーセルの窓。デコードへ1サイクルに最大4命令。ブロックをまたぐ32ビット命令は窓の中で扱う |
| uBTB | `OOO_UBTB`: **8エントリ**(G0bのL5。前は16)、全連想、12ビットの部分タグ、ブロック内で最初にtakenの当たりを並列に選ぶ、ラウンドロビンで置き換え、リターンはRASの先頭から |
| TAGE-S | `OOO_TAGE`: ブロックRAMで作れる形の、フェッチブロック単位のもの(手順2で決めた、`Plan/OOC_J.md` 14.1): フェッチアドレスと履歴で引く1024行のタグつきの表が4つ。各行に、ブロックの1つ目・2つ目・3つ目の条件分岐のための方向カウンタが3つ。ベースはパーセルごとの2ビットカウンタ。履歴はスロットの分岐1つにつき1ビット。ブロックの4つ目の分岐は非takenと予測する(CoreMarkにはない)。コミットでFTQを通して更新。モデルの分岐ごとのTAGEに比べて約 −0.2% / −0.5% |
| BTB、RAS | `OOO_BTB`: 間接ジャンプだけのもの(ブロックRAMに256行、フェッチアドレスで読む)。分岐とjalのターゲットはプリデコード(`OOO_PREDEC`)が、リターンのターゲットはRASが出す。`OOO_RAS`: LUTRAMに16エントリ。回復のために、各ブロックがポインタとpushで上書きされるエントリを持つ |
| FTQ | `OOO_FTQ`: 8エントリ、フェッチブロックごとに1つ: 更新と回復のためのPC、次のアドレス、予測の状態(LUTRAM)。フロントエンドはブロックあたり312ビットの状態(TAGE 270、RAS 42)と、コミットでの更新のためのスロットの分岐の結果を要する。FTQはコアの組み上げで広げる(`Plan/OOC_J.md` 14.2)。3つ目の読み出しは復元のもの(`OOO_FERS`、`Plan/OOC_J.md` 21) |

### 3.3 デコードと融合

| 項目 | 仕様 |
|---|---|
| 幅 | 1サイクルに4命令をデコードし、2 µopを出す |
| デコーダ | `OOO_DEC`: スロットごとに、mmRISC-2の`CORE_DECOMP` + `CORE_DEC`を変えずに使い(`RTL/CPU/CORE`)、融合、発行キュー、ROBが要るフィールドを導く(`Plan/OOC_J.md` 16章) |
| 融合 | `OOO_FUSE` **LEVEL 2**(G0b D-14、6.7。ALU + ALUはやめた): lui + addi、auipc + x、slli + srli、ALU + ロード(アドレス)、ロード / ストアのペア、ALU + 分岐。古いスロットから貪欲に、プログラム順で隣り合う命令どうし |
| 制限 | 組が読むレジスタは2本まで(`SRC2`)、書くのは1本まで(`W1`)。なので、融合した分岐のもう一方のオペランドは、その2本のどちらか(またはx0) |
| 融合しない場合 | `no_fuse`: シングルステップ、トリガーが有効なとき、組の中で例外が起きたあとの再フェッチ(3.8) |

### 3.4 リネーム

`OOO_RENAME`: 1サイクルに2 µop、それぞれソース2・デスティネーション1。物理レジスタ64本(タグ6ビット)、RATはフリップフロップ、フリーリスト32、busyは発行キューの6本のwakeupのタグで消す(`Plan/OOC_J.md` 20: 書き戻しで消すと、そのあいだにリネームされたµopがwakeupを逃す)。組の中の依存を扱い、チェックポイントは6つ(RATから1サイクル遅れて写す、`Plan/OOC_J.md` 10.1)。チェックポイントを取るのは、条件分岐かjalrを含むµop(jalは後段で予測ミスにならない)。チェックポイントの復元は、そのリネームから2サイクル以上あとで、パイプラインがそれを保証する。

**2026-10-25に追加(`Plan/OOC_J.md` 11.4)**: 全フラッシュ(例外、割り込み、直列化)はコミット状態へ戻る。それには、コミットした状態のRAT(32 × 6ビット、コミットで書く)と、フリーリストのコミット済みの先頭が要る。リネームに足す(約0.3k LUT)。

### 3.5 dispatch、ROB、発行キュー

| 項目 | 仕様 |
|---|---|
| DSレジスタ | リネームとディスパッチのあいだ: 2つのµopは一緒に出るか出ないか(`OOO_CTRL`)。ペイロード(`OOO_DSREG`)は、発行キューの前のサイクルのwakeupのタグでソースのreadyビットを更新し続けるので、ここで待つµopはwakeupを逃さない(`Plan/OOC_J.md` 20) |
| ROB | 24 µop。ペイロードは番号の偶奇でバンクを分けたLUTRAM(それぞれ書き込み1ポート。µopの長さとフェッチブロックも)、完了・例外・リプレイのビットはフリップフロップ。1サイクルに2つコミット |
| 発行キュー | `OOO_IQ`: 統合、**10エントリ**(G0b D-12、6.5)、ソース2・デスティネーション1、古い順(age matrix)、1サイクルに3発行、wakeupバス6本、エントリは発行で空く(ミスしたロードはコミットのあとにリプレイ、3.7)。エントリごとのブランチマスク(6ビット: 復元は分岐より若いµopを捨てる、`Plan/OOC_J.md` 18)。ペイロードはLUTRAM(`OOO_IQPL`: 書き込みポート1つのバンク2つとライブ値表。DSで`disp_entry`へ書き、RRで読む。`Plan/OOC_J.md` 17.1) |
| ポート | P0: ALU0 + MUL / DIVと複雑なALUの操作、P1: ALU1(加減算、slt / sltu、論理、分岐。先に選ぶ、6.12)、P2: LSU |
| **dispatchの規則**(wakeupがこれに頼る) | レイテンシ2のµop(乗算)は「ALU0のみ」。「どのALUでも」のµopはレイテンシ1。LSUのµopがレジスタを書くのはロードだけ |
| 物理レジスタ | `OOO_PRF`: 64 × 64、書き込み3 / 読み出し6、書き込みバンクごとのLUTRAM + LVT |

### 3.6 実行

| 項目 | 仕様 |
|---|---|
| ALUポート | P0とP1に`OOO_ALU2`: P0はフルの`OOO_ALU`(RV64I、Zba、Zbb、Zbs、Zicond。加算器とシフタを1つずつ共有)、P1は絞ったもの(加減算、slt / sltu、論理。G0bのL7、6.12)。それぞれに分岐の比較(単独、または融合でALUの結果とs1、s2、0のどれか)。ソース2つ、バイパスも2つ(6.7) |
| ソース | µopあたり2本(`OOO_ALU2`の3本目のソース入力はPhase 1で外す。2段目はres1、s1、s2、imm2から取る) |
| バイパス | EXのALUの前: レジスタファイル、自分の結果、もう一方のALUポート、ロード |
| MUL / DIV | mul / mulw: P0のパイプラインの乗算器(`OOO_PMUL`、D-16の案A、`Plan/OOC_J.md` 24): レイテンシ2、1サイクルに1つ、DSP 10。mulh*、clmul*、除算: mmRISC-2のCORE_MDUを変えずにP0の後ろに(`OOO_MDUP`、`Plan/OOC_J.md` 23)、一度に1つ、外から答える(書くときに`ext_*`でwakeup) |
| 分岐 | ALUの横にターゲットの加算器。予測ミスでチェックポイントを復元し、F0へリダイレクト |
| FPU | mmRISC-2のFPU_PIPE(D3: まずパイプライン)。専用のポートの後ろに置き、ROBのタグでフラッシュする(`REDUCE_J.md` E4) |

### 3.7 LSUとメモリ

| 項目 | 仕様 |
|---|---|
| LSU | 1サイクルにロードかストア1つ。ロード使用2サイクル(ヒットを予測)、ミスなら再実行 |
| 順序 | 保守的なメモリ依存: ロードは、それより古いストアのアドレスがすべてわかってから発行する(モデルで損失なし) |
| LQ / SQ | **8 / 8**(G0bのL4。前は12 / 12)。SQからのフォワーディング(同じアドレスとサイズ)。ストアはコミットのあとでD$に書く |
| D$ | mmRISC-2のもの(ノンブロッキング、MSHR 2)を、タグ付きの要求・応答のアダプタの後ろに置く(`OOO_DCAD`、`Plan/OOC_J.md` 17.2): D$はロードのヒットをステージ1で出し(`d_hit_now`、加えた唯一の出力、ミスの下でも)、LSUのMに渡す。ほかの答えは順に来て、LQのエントリごとのフィルとして渡す。LQのエントリが新しい要求を出すと古い答えは捨てる(やり直したロードに古い値を渡さない) |
| ミスアライン | mmRISC-2と同じくトラップ |
| ブロック | `OOO_LSU`(2026-10-25、`Plan/OOC_J.md` 11): LQ / SQ、フォワーディング、発行キューのための`lsu_st_known`、予定のサイクルに結果を出せないロードの`ld_cancel`、遅れた結果、D$のアダプタのための`dc_kill`(`OOO_DCAD`では不要) |
| **後続の止め方**(2026-10-26に決定、D-12、6.5。それまでは`Plan/OOC_J.md` 15章の選択的なリプレイ) | **コミットのあとのリプレイ**: `ld_cancel`を出したロード(ミス、待ち)は、あとで印つきで完了する(`cmp_ld_rp`)。ROBはそれをコミットして空になり、フロントエンドは次の命令から取り直す(`replay`、`replay_pc`)。その間に予想で動いたものは捨てる。ロード自身は1回しか実行しない。マスクも残すエントリもなく、ユニットはそのために何も捨てなくてよい(予測ミスではブランチマスクで捨てる、`Plan/OOC_J.md` 20)。モデルで+0.2% / +0.2%。ミスしたロードのたびに、取り直しとミスの下の仕事を払う(ミスの多いコード: Linux) |

### 3.8 コミット、例外、融合した組

- 例外と割り込みは、ROBの先頭で、µopの境目で受ける。組は1つのµopとしてコミットし、`minstret`とPMUは2と数える。
- **融合した組の中の例外**(たとえばALU + ロードのロードのページフォールト): 組を捨て、そのグループを融合なしでフェッチし直す。2つの命令が1つずつ実行されるので、`mepc` / `mtval`とレジスタは正確になる(組の書き込みは1本なので、前半の結果は書かれていないことがある)。
- デバッグの停止とシングルステップはコミットで受ける。シングルステップ中とトリガーが有効なときは融合しない。
- **作った**(`OOO_TRAP`、`Plan/OOC_J.md` 22): 先頭が発行済みの非投機のµopのあいだは割り込みを取らず(その効果は起きている)、割り込みは先頭の例外に勝つ。組の取り直しは2命令がコミットするまで融合を切る。mtvalは報告されたいちばん古い例外のtval。MRETのリプレイはmepcから取る。

### 3.9 ROBの先頭でしか実行しないもの(非投機のリスト)

| 種類 | 扱い |
|---|---|
| CSR命令(`fcsr`、`satp`、カウンタを含む) | 先頭で直列に実行する: 先頭でだけ発行する(`ns_ok`つきの`OOO_IQ`、`Plan/OOC_J.md` 19)。書き込みはコミットのあとのリプレイの印つきで完了し、後続のµopは取り直す |
| ECALL、EBREAK、MRET、SRET、WFI | 先頭で(ECALL / EBREAKはデコードでの例外。MRETとWFIは`OOO_SYS`: MRETはmepcへのリプレイの印つきで完了し、WFIはmieで割り込みが保留になったら完了) |

| AMO、LR、SC | 先頭で、ストアキューを空にしてから |
| キャッシュしないメモリ(MMIO)からのロード | 変換のあとにわかる。先頭まで待ってから実行 |
| ストア | D$(またはMMIO)へはコミットのあとだけ |
| ページテーブルの探索 | 投機的に走ってよい: A / Dビットをハードウェアで書かない(mmRISC-2と同じSvade) |
| `fflags` | コミットで積算 |
| 割り込み、デバッグ要求 | 先頭のµopの境目で |

### 3.10 mmRISC-2から流用するもの

L1 / L2キャッシュ(D$はアダプタつき)、MMU(TLB、PTW、PMP)、CSR、デバッグ(Sdtrig、デバッグモジュール)、MDU、FPU_PIPE、LiteXへの組み込み、SIM_BIOS、バグ注入の方法。`REDUCE_J.md`のグループAは、これらを持ってくるときに入れる。

## 5. D3: FPU

- 作者の決定(2026-10-24): まずパイプラインのFPU(mmRISC-2のFPU_PIPE、SoCの中で8,815 LUT)で始め、論理規模の状況で再検討する。
- **再検討でわかったこと**: mmRISC-2は両方のFPUを単体で測っている(`CPU_FPU/README.md` 4章、2026-10-09)。多サイクルの`CORE_FPU`は9,757 LUT、パイプラインの`FPU_PIPE`は9,060。多サイクル版も部分積をすべて1サイクルで作っており、パイプライン化でステートマシンの選択回路が消えた。**多サイクルのFPUに戻しても空かず、0.7k増える**。以前の推奨の「数k」は、存在しない幅の狭い反復型FPUを前提にしていた。
- 残る手段(`REDUCE_J.md`のグループC)。決める前に測る:

| # | 手段 | LUT | 内容 |
|---|---|---|---|
| C1 | FPUの内訳 | — | FPU_PIPEを乗算、加算、桁合わせ、正規化、丸め(963、実測)、変換、除算 / 平方根に分けてOOC合成する。**作者のVivadoで、今** |
| C2 | MDUとFPUで乗算器を1つにする | 0.5k〜1k(とDSP 16)。**C1で測ると約0.3k**(乗算は大部分がDSP) | MUL / DIVとFPUを同じ発行ポートに置く。乗算のスループットが落ちる(CoreMarkは1000命令に30回の乗算) |
| C3 | FMA / 加算 / 乗算はパイプラインのまま、変換、比較、符号操作、分類は小さな反復ユニットへ | 1k〜2k。**C1で測ると約0.7k〜0.9k**(P2の862と変換の後半340を置き換える分) | C1しだい。まれな浮動小数点演算が遅くなる。CoreMarkには影響なし |
| C4 | 新しい幅の狭い反復型FPU | 数k | 新しい設計と新しい検証が要る。浮動小数点の性能が大きく落ちる。推奨しない |

- **推奨**: FPU_PIPEを基本のまま残す(検証済みで、Linuxもこれで動いている)。C1を今行い、G0bでなお超過していればC2とC3を使う。

- バグ注入: 173件中171件を検出。M77とM86(2ブロックをpopしたときの、Bの次のブロックの開始)は、2ブロックでは等価: 3つ目のブロックはありえない。4ブロックでは検出される。L6が4に戻るかもしれないので、RTLは一般のままにする。

### 6.11 L7をモデルで測った: 非対称なALU(2026-10-27)

**モデル**(`Plan/model/ooo.h`のオプション`alu_split`。`g0b.sh` → `results/g0b.txt`): 2つのALUポートはひとまとめだった(どちらもどのALU µopでも、MUL / DIVも取る)。`alu_split` 1はALU0とALU1を分け、MUL / DIVとシステムはALU0だけ(RTLのとおり)。2はさらに複雑なALUの操作をALU0だけにする(L7: シフト、Zba、Zbb、Zbs、Zicond。トレースの`sub`による)。単純なµopはALU1を先に取る。3は同じで、単純なµopがALU0を先に取る。融合した組は、そのALUの部分が複雑なら複雑とする。

| 構成 | `-O2` | 最大の最適化 | 悲観 |
|---|---|---|---|
| 決めた組み合わせ(コミットでのトラップ、発行キュー10、L4、L5、融合レベル2) | 6.279 | 6.710 | 5.548 / 5.971 |
| 同じでALU0 / ALU1を分ける(`alu_split` 1) | 6.279 | 6.710 | |
| **+ L7、単純なµopはALU1を先に**(2) | **6.260(−0.3%)** | **6.695(−0.2%)** | 5.521 / 5.949(−0.5% / −0.4%) |
| + L7、単純なµopはALU0を先に(3) | 5.882(−6.3%) | 6.264(−6.6%) | |

- **ALUポートを分けるだけなら損はない**: MUL / DIVをALU0だけにしても(RTLのとおり)、ひとまとめのモデルと同じ数になる。
- **L7は、単純なµopがALU1を先に取れば −0.3% / −0.2%**、**ALU0を先に取ると −6%**: 複雑な操作はALU命令の30%(g14 -O2で全体の16.5%: シフト5.2%、Zba 5.2%、Zbb 3.0%、Zbs 1.6%、Zicond 1.5%)で、ALU0で単純なものの後ろに待たされる。なのでL7では、発行キューは**ポート1を先に**選び(準備のできたいちばん古い単純なµop)、次にポート0(残りのうちいちばん古いもの)を選ぶ。今はポート0が先。選択の深さは変わらない(一方のあとに他方)。
- **規模**: ポートのALUはVivadoで801 LUT(6.8)。加減算(ワード形も)・論理・比較だけのALUはYosysで165 LUT、フルは2,174(フルのVivado / Yosysの比は0.37): Vivadoが同じように出れば、ALU1で**約−0.5k〜−0.65k**。6.8の−0.3k〜−0.5kより多い。
- **RTLでは**: デコードが複雑なALUの操作を「ALU0だけ」(ポート1、MUL / DIVと同じ)にする(複雑なALUの部分をもつ融合した組も)。発行キューの選択の順を逆にする。ALU1の`OOO_ALU2`は、加減算・論理・比較に絞った`OOO_ALU`にする(D-14でパラメータ`FULL`は空いている)。
- **D-13によれば**(損が約1%以下ならL7)採ることになる。
