# ARTY A7-100Tでのdual issue / out-of-order RV64GCコア実現に関する検討メモ

- 対象: mmRISC-2(single issue / in-order / RV64GC)の後継として、同一ボードでdual issue / OoOのRV64GCコアを作り、Linuxを動作させる
- 作成日: 2026-10-13
- 位置づけ: 課題の洗い出しと対策・妥協案の整理(数値の多くは粗い見積りで、実測による確認が前提)
- 経緯: mmRISC-2の開発中(Rev.01の時点)に行った事前検討。2026-10-24に`Doc/mmRISC-OoO_検討メモ.md`から本ファイルへ移した(内容は当時のまま)。mmRISC-3の方針は`Doc/STRATEGY_J.md`が優先する。英訳は`PRESTUDY_MMRISC2.md`

---

## 0. 結論の要約

1. 現状のmmRISC-2でFPGAはほぼ埋まっている(LUT 74.0%、スライス86.2%)。このためOoO化は「論理を追加する」のではなく、「何を削ってOoOに回すか」という**資源の再配分**の設計になる。
2. FPGA向けに割り切ったOoO(NaxRiscv RV64構成)は、コア単体で約18k LUTの実例がある。ただしFPUとZb系を含まない数字である。
3. ArtyはスピードグレードR-1である。**50MHzに据え置き**、周波数の余裕をパイプライン段数の削減(=LUT/FFの節約)に回すのが得策。
4. Linux動作上の急所は性能部品ではなく、**副作用を持つ操作の非投機化**(MMIOロード、CSR、AMO、PTWのA/D更新など)。
5. 最大の分岐点は**FPUの扱い**(FP専用リネーム/整数・FP統合PRF/マルチサイクルFPUへの縮小)。
6. 性能の期待値: CoreMark/MHzの天井は約1.6倍。Linuxのカーネル負荷では実効1.2〜1.4倍程度と見込む。性能そのものより、設計資産・題材としての価値が大きい。
7. 進め方: **NaxRiscv RV64をArtyで実測** → **1-wide OoOでLinuxをブート** → 2-wide化 → 投機的ロードとMSHRの多重化 → FPU・予測器の強化。

## 1. 現状(mmRISC-2 Rev.01)の資源状況

| 項目 | 値 |
|---|---|
| 動作周波数 | 50MHz(WNS +0.664ns) |
| LUT | 46,928 / 63,400(74.0%) |
| スライス | 86.2% |
| BRAM | 108.5 / 135タイル(L2 256KB込み) |
| 性能 | 2.786 CoreMark/MHz(-O2、Zba/Zbb)、最適化時3.025、1.496 DMIPS/MHz |
| パイプライン | 8段 in-order(IF1/IF2/FQ/ID/EX/MR/MA/WB) |
| キャッシュ | L1 I$/D$ 各16KB(4way、64B)、D$はnon-blocking・write-back、L2 256KB |

### 見立て
- 実質的な制約はLUT 74%よりも**スライス86%**の方。配線混雑を考えると、実用上限はLUT 80〜85%程度。
- 追加で使えるのは**5〜8k LUT程度**しかない。
- BRAMにはまだ余地があり、L2の縮小でさらに空けられる。LUT → BRAM/LUTRAM/DSPへの移し替えが基本戦略になる。

### 最初にやること(Phase 0)
`report_utilization -hierarchical` で、現状を次の単位に分解する。予算配分の議論はすべてこの数字から始まる。

- コア(フロントエンド / EX / LSU / CSR / PMU)
- FPU(FPU_PIPE)
- MMU(TLB / PTW / PMP)
- L1キャッシュ、L2キャッシュ
- デバッグ(DTM / DM / トリガ)
- LiteX(LiteDRAM / LiteEth / SD / UART / CSRバス)

あわせてDSP48の使用数も確認する(240個のうち未使用分は乗算器や加算器の受け皿になる)。

## 2. 規模の相場観:NaxRiscv

FPGA向けOoO RISC-Vとして最も近い実例。LiteXに統合済み。

| 構成 | CoreMark/MHz | DMIPS/MHz | LUT | FF | BRAM | DSP | Fmax(Artix-7 -3) |
|---|---|---|---|---|---|---|---|
| RV32 2デコード / 3発行 / 2リタイア | 5.02 | 2.93 | 13.3k | 10.3k | 12 | 4 | 155MHz |
| RV32 ALU1本(分岐を共有パイプへ) | 4.44 | 2.71 | 12.1k | 9.9k | 12 | 4 | 148MHz |
| RV32 1デコード / ALU1本 | 3.35 | 1.70 | 10.8k | 9.7k | 12 | 4 | 155MHz |
| RV64(2×Int + 1×LSU/MulDiv/CSR) | 4.94 | 2.94 | 17.9k | 12.5k | 12 | 16 | 137MHz |

RV32構成の主なパラメータ:
- 64bitフェッチ、2デコード、3発行、2リタイア
- 32エントリの共有発行キュー
- 物理レジスタ64本
- LQ/SQ 各16
- ロードヒット予測(load-to-use 3サイクル)
- I$/D$ 16KB/4way
- BTB 512、GSHARE 4KB、RAS 32

### 読み取れること
- FPGA向けに割り切ったOoOなら、コア単体は20k LUT前後に収まりうる。
- ただしNaxRiscvの数字は**FPU・Zb系なし**。mmRISC-2相当のISA(RV64GC + Zba/Zbb/Zbs/Zbc/Zicond/Zicboz、Sstc、Sscofpmf、Sdtrig)に揃えると、相応に増える。
- 数字はスピードグレード-3でのもの。Artyの-1では137MHz → 概ね100MHz前後に相当する。50MHz狙いなら周波数に余裕がある。
- NaxRiscvの開発メモにある知見:
  - 分岐予測なしのOoOは非常に性能が悪い
  - ストアデータを発行キューで待たせない構成は、誤ったロード投機を減らす
  - ALUを2サイクルレイテンシにしても性能影響は約15%
  - 実行ユニットを増やすとすぐに収穫逓減に入る

## 3. OoO化で増える部分と、FPGA向けの抑え方

| ブロック | 何が重いか | FPGA向けの対策 |
|---|---|---|
| 物理レジスタファイル | 多ポート(2-wideで4R2W以上) | **実は安い**。RAM64M(1W3R LUTRAM)を使い、書き込みポートごとにバンクを分け、LVT(Live Value Table)で選択する。64本×64bitでも数百LUT。**FFで組まないことが最重要** |
| 発行キュー | wakeupのタグ比較CAMとselect(優先選択) | 分散キュー(ALU用 / MEM用 / FP用で各8前後)。非collapsingにして年齢はage matrixで管理。依存行列方式のwakeupもLUT向き |
| リネーム | RAT読み出しポート、グループ内依存検出、分岐リカバリ | RATはLUTRAM。チェックポイントは2〜4個に絞り、溢れたらROBウォークで戻す。全分岐スナップショットはFFが爆発するので避ける |
| ROB | エントリ数×情報量 | 24〜32エントリ。PCは各エントリに持たず、フェッチブロック単位のFTQに置く。ペイロードはLUTRAMかBRAMへ |
| LSQ | ロード/ストアのアドレスCAM、順序違反検出 | **初期版は保守的なメモリ依存解析**(古いストアのアドレスが確定するまでロードを発行しない)。LQの違反検出とリプレイが不要になる。ストアフォワーディングは同一アドレス・同一サイズのみ |
| バイパス網 | 64bit幅×ソース数×オペランド数 | 実行ユニット数を絞る |
| RVC込みの2命令フェッチ | 命令境界の判定、32bit命令のフェッチブロック跨ぎ | 16bitパーセル単位のフェッチバッファを置き、I$にプリデコードビットを持たせて境界判定を前段へ移す。地味だが手間のかかる箇所 |
| 分岐予測ミスの回復 | ペナルティの増大(10サイクル超)、GHR・RASの修復 | GHRとRASのTOPポインタをチェックポイントで保存。予測器自体はBRAMで強化する |

### PRFの規模感(参考計算)
- RAM64M 1個(4 LUT)で 64エントリ × 3bit、3R1W
- 64bit幅にはRAM64Mが22個 = 88 LUT(3リードポート分)
- 4リードポート → 2組で約176 LUT
- 2ライトバンク → 約352 LUT
- LVTと出力の2:1 mux(64bit×4ポート)を合わせても、**合計1k LUT未満**

### タイミングの急所
- **wakeup-selectループ**(依存命令を連続発行するための1サイクルループ)
  - 50MHzなら1サイクルで通る可能性が高い
  - 閉じなければALUの2サイクルレイテンシに逃げる(性能影響は約15%)
- リネームのグループ内依存検出(2命令間の依存をRAT読み出しとバイパスで解決する)
- 2-wideコミット時のフリーリスト更新

## 4. Linux動作のための非投機化

OoO化でLinuxが動かなくなる典型は、性能部品ではなく**副作用の扱い**。原則として以下はROB先頭まで待ってから実行し、必要に応じてパイプラインをフラッシュする。

| 対象 | 扱い | 備考 |
|---|---|---|
| **デバイス領域(MMIO)へのロード** | PMAで非キャッシュ領域と判定したら投機発行を禁止し、先頭で実行 | LiteXのUART/SD/Ethernetのレジスタは読むだけで状態が変わる。忘れると「たまにUARTの文字が欠ける」系の、非常に追いにくいバグになる |
| MMIOへのストア | コミット後に発行(ストアは元々コミット後に実行) | posted uncached storeを入れる場合は順序保証に注意 |
| CSR命令全般 | 先頭で実行し、後続をフラッシュ | 頻度が低く、性能はほぼ無関係 |
| SFENCE.VMA / FENCE.I / WFI | 先頭で実行し、フラッシュ | FENCE.IではI$とフェッチバッファも無効化する |
| ECALL / EBREAK / MRET / SRET | 先頭で実行し、フラッシュ | |
| AMO / LR / SC | 先頭で実行 | 既存D$のAMO/LR-SC機構を流用できる |
| **PTWのA/Dビット書き換え** | 投機中のPTWは読み出しのみ。A/Dの更新が必要なら先頭まで待つか、ページフォールトにする(Svade的な扱い) | 投機的な更新が許される範囲は特権仕様の該当節で要確認 |
| 例外・割り込み | コミット時に受け付ける | 精密例外 |
| fflags / frm | fflagsはコミット時に累積。frmの書き換えはCSR扱いで直列化 | |
| デバッグのhaltとステップ実行 | ROB先頭で処理。ステップ実行は「1命令コミットしてフラッシュ」 | 既存のDebug Spec 1.0実装をほぼ流用できる |
| トリガ(Sdtrig) | 照合結果をROBに載せ、コミット時に発火 | 投機パスで誤発火させない |
| PMUのイベント | コミット系と投機系のイベントを区別する | `perf`の解釈に影響する |
| DMAのコヒーレンス | 既存のD$経由方式をそのまま使う | LSQ内の投機ロード値との整合に注意(保守的なLSQなら問題が起きにくい) |

## 5. 妥協・削減の候補(効果の大きい順)

### A. FPUの扱い(最大の分岐点)

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 案1:FP専用リネーム | FP用のRATとPRF(48本程度)、小さなFP発行キュー。既存の9段FPU_PIPEを実行ユニットとして使う | 正攻法。FP性能を維持できる | RAT・フリーリスト・PRFが2系統になる |
| **案2:整数とFPのPRF統合** | RV64Dではf0-f31も64bitなので、アーキテクチャレジスタ64本を1つのRATと1つのフリーリストで管理する | リネーム関連の論理が1系統で済む | FMAの3ソース読み出しでポートが増える(FP側だけ別バンクで読む構成も可能) |
| 案3:マルチサイクルFPUへ縮小 | 9段FMAパイプラインをやめ、旧CORE_FPU相当に戻す | LUTを大きく削減できる。Linuxの体感にはほぼ影響しない | FP演算性能は大きく低下する |
| 案4:FPはインオーダーのサイドパイプ | ROBで順序だけ管理し、FPの発行はインオーダー | OoOのコストを整数側に集中できる | FP命令と整数命令の依存で詰まりやすい |

FDIVとFSQRTはどの案でも反復型のままでよい。

### B. 実行ユニットの非対称化
- ALU0:フル機能(Zba/Zbb/Zbs/Zicond、分岐、64bitバレルシフタ、clz/ctz/cpop)
- ALU1:加減算・論理・比較・(必要なら)分岐のみ
- MUL/DIVとZbc(クラインレス乗算)はどちらかのポートに相乗りさせる
- 乗算はDSP48に完全に寄せる

### C. LUTからBRAM / LUTRAM / DSPへの移し替え
- BRAMへ:BTB、gshareのPHT、ROBペイロード、TLBの2段目(ROADMAPにある2段目TLBとも整合する)
- LUTRAMへ:小さな全連想TLB(部分比較と組み合わせる)、RAT、PRF、FTQ
- 予測ミスペナルティは10サイクル超に伸びるので、予測器はBRAMで強化する(gshare → 小型TAGE)のが割に合う

### D. SoC側・デバッグ・観測機能の削減

| 対象 | 削減案 | 効果 |
|---|---|---|
| L2キャッシュ | 256KB → 128KB | BRAMが約30タイル空く(LUTはほぼ変わらない) |
| LiteEth | 開発中は外し、SDのみでブート | LUT数k |
| PMU | イベント26種を絞り、カウンタ数を削減 | 64bitカウンタとイベント選択の論理は合計すると無視できない |
| デバッグトリガ | 4個 → 2個 | 比較器の分 |
| PMP | 8エントリから削減 | 比較器の分(OpenSBIの挙動は要確認) |
| Zbc | 外すか、MDUと共用 | 小〜中 |
| LiteXのCSRバス | 不要な周辺を外す | 小 |

### E. 周波数を50MHzに据え置く
- スピードグレード-1でOoOのタイミングを詰めるより、段数を減らしてLUT/FFを節約する方が、このボードでは得。
- LiteDRAM側のクロックドメインとの関係は現状の構成を踏襲する。

## 7. 期待性能

- NaxRiscv RV64のCoreMark 4.94/MHzが一つの目安。mmRISC-2の最適化時3.025/MHzに対して**約1.6倍が天井**。
- Linuxのカーネル負荷はメモリ律速の比率が高い。L2ヒット14サイクル、L2ミス31サイクル(いずれもL1ミス時)のレイテンシをOoOで隠すには、D$が複数のミスを同時に出せることが前提。
- 実効的な向上は**1.2〜1.4倍程度**と見込む。
- 8段インオーダー + gshareで既に良い性能が出ているので、OoOの相対的な伸びは小さめになる。

## 8. 検証戦略

### 既存資産の流用
- SIM_CORE / SIM_SYS / SIM_BIOS(Linuxブート)、riscv-tests、バグ注入の仕組み

### OoO固有の追加
| 手段 | 目的 |
|---|---|
| コミット時のSpikeとのロックステップ比較 | 命令単位で正しさを確認する(RVFI的なコミットトレースI/Fを最初から設計しておく) |
| riscv-dvによるランダム命令列 | ハザード密度を上げ、リネームとリカバリの穴を突く |
| 例外・割り込みの注入テスト | 分岐予測ミス中の割り込み、投機パス上のページフォールトなど |
| Konata形式のパイプライン可視化 | OoOのデバッグ効率を大きく上げる |
| LSQ専用のランダムテスト | ストアフォワーディング、MMIO、AMO、DMAとの競合 |
| バグ注入 | リネーム、フリーリスト、チェックポイントに注入し、テストの検出力を確認する |

### 実機デバッグ
- ILAを置くLUTやBRAMの余裕はないはず。
- **コミットトレースを溜めるリングバッファ**(BRAM 1〜2個)をコア内に持ち、JTAG経由で読み出す仕組みを最初から入れておく。

## 9. 段階的な進め方

| Phase | 内容 | 完了条件 |
|---|---|---|
| 0 | 現状の階層別utilization取得、予算策定 | ブロック別LUT/BRAM/DSPの表 |
| 1 | **NaxRiscv RV64(FPU付き)をLiteXでArty A7-100Tに実装し、実測する** | 収まるか、LUT数、Linux上の性能。「Arty 100TでOoO RV64GCはどこまで現実的か」の上限値になる |
| 2 | 1-wide OoO(リネーム、ROB、発行キュー、保守的LSQ、非投機化一式) | Linuxブート、ストレステストPASS |
| 3 | 2-wideのデコード / リネーム / コミット、RVCアライナ | Linuxブート、CoreMark/MHzの向上を確認 |
| 4 | 投機的ロード(ストア待ち予測ビット)、ストアフォワーディング、MSHR多重化 | カーネル負荷のCPI改善 |
| 5 | 余った資源の範囲でFPU強化、予測器のTAGE化 | 資源と性能のトレードオフ確定 |

NaxRiscvの1デコード構成でもCoreMark 3.35/MHzが出ている。Phase 2の1-wide OoOで正しさの土台を固めることには十分意味がある。

## 10. 撤退ライン(収まらない場合)

| 代替案 | 規模増 | 期待性能 | 備考 |
|---|---|---|---|
| デュアルイシューのインオーダー(U74型) | +20〜30% | 1.2〜1.3倍 | 現行の8段パイプラインと分岐予測の資産が最も活きる |

| 1-wide OoOで止める | 小〜中 | NaxRiscv 1デコード相当 | 設計資産としての価値は残る |
