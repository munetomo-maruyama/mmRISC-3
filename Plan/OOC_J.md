# Phase 0-4: 融合構成のRTLブロックと、単体合成(OOC)の準備

- 実施日: 2026-10-24
- 目的: `ISSUES_J.md` 5章の手順3。融合構成(`Doc/STRATEGY_J.md` 4章)の中で、1サイクルに閉じる必要があるループと、構成を決めるコストを持つブロックをRTLで書く。単体で検証し、規模とタイミングを測る。タイミングの確定は作者のVivadoで行う
- 作業ファイル: `RTL/CPU/OOO/`(RTL)、`SIM/OOO_UNIT/`(単体テストとバグ注入)、`FPGA/OOO_OOC/`(VivadoのOOC合成、Yosysの見積り)

---

## 1. 結論

1. **融合構成の6ブロックをRTLにし、単体テストとバグ注入で検証した**。ブロックは2段ALU、融合、発行キュー、リネーム、物理レジスタ、uBTB。Verilatorの`-Wall`でlintは0件、6本の単体テストはすべてPASS、わざと入れた21件のバグはすべて検出された。
2. **融合のRTLはモデルどおりに組を作る**。CoreMarkの命令列を4命令の窓で流すと、`-O2`でモデルの組の99.99%(415,297 / 415,337)、最大最適化で411,999 / 412,000を作った。µop / 命令もモデルと同じ0.867 / 0.853。4命令の窓の端と、ロード / ストアのペアを静的なオフセットで判定することによる損失はない。
3. **テストで見つかったもの**:
   - RTLのバグ1件: リネームのチェックポイント番号が、無効なµopの要求でも進んでいた。
   - 書き方の問題: 実行時の値で添字を選ぶ表を、packedの多次元配列で書いていた。Yosysでは数万LUTの論理になっていた。表を配列にし、レジスタファイルのバンクを書き込みポートごとの配列にして直した(リネーム 57k → 9.2k、発行キュー 47.7k → 15.6k、レジスタファイル 94k → 4.9k + LUTRAM、YosysのLUT数)。
   - テストの穴1件: x0がゼロを返すかを、メモリの初期値0に頼って見逃していた。リセットのない状態をすべてランダムな値で始める方式にして塞いだ。
4. **最大の発見: レジスタファイルのポートが、資源の最大の項目になる**。融合した組がソース3本・書き込み2本を使うと、読み出し8〜9・書き込み5〜6ポートになる。Yosysの見積りではLUT + LUTRAMで1.7万〜1.9万となり、OoO本体の予算(16〜18k)をそれだけで使い切る。モデルで振ると、**融合する組をソース2本までに制限しても−1.7% / −1.1%**(読み出し6ポートで済む)。書き込みを1本までにすると−4.4% / −9.1%と高くつく。
5. **推奨(G0で確定)**: 融合する組はソース2本まで(読み出し6ポート)。書き込みは5ポート(組あたり2本)を基本とし、Vivadoでレジスタファイルが重すぎれば3ポート(組あたり1本)に下げる。どの組み合わせでも、モデルでは`-O2` 6.6〜6.9、最大最適化 6.9〜7.5で目標を超える。
6. **Vivadoの結果(7章)**:
   - 発行キュー、リネーム、融合は50MHzで1サイクルに閉じた。
   - 2段ALUは −0.70 ns、uBTBは −24.5 nsで閉じなかった。
   - レジスタファイルは、バッチの誤りで実行されていなかった。
   - **規模は、測ったブロックだけでOoO部分の予算の約2倍あった**。
   - 判断: ALU + ALUの融合は残す。そのうえで、ALUを書き直し、2段目の操作をCoreMarkに現れる操作に絞る(損失0)。uBTBは16エントリで並列の選び方にする。ソース2本までの制限は確定。
   - 書き込みポート数は、レジスタファイルを実行し直して決める。→ **書き込み3ポート**(物理LUT 4,942、5ポートは8,350)で確定し、5ポートはG0で予算に空きができたときの買い戻し候補とした(7.4)。
7. **判断の反映(8章)**: ALUを書き直して2段目を絞り(OOC_ALU2はYosysで8,225 → 約4.6k)、融合にソース2本まで・書き込み1本まで・2段目の印を入れ(CoreMarkでモデルと組の数が一致)、uBTBを16エントリの並列の選び方にした(5,041 → 約2.3k)。単体テストはすべてPASS、バグ注入34件はすべて検出。Vivadoでの確認待ち。
8. **発行キューとリネームの作り直し(10章)**: µopあたりソース2・デスティネーション1、物理レジスタ64本にした。Yosysでリネーム約9.0k → 3.2k、発行キュー約15.5k → 5.0k。チェックポイントは1サイクル遅れて写す方式にした(性能の損失なし)。Vivadoでは、ALU(3,133、+0.51 ns)、uBTB(910、+5.10 ns)、融合(215)、発行キュー(3,143、+5.07 ns)、リネーム(2,267、+8.91 ns)がすべて閉じた。レジスタファイルは64本で2,503(96本の約半分)。測ったブロックの合計は15,304で、OoO部分の予算(16k〜18k)の中に入った(ROB、LSU、デコードなどはまだ含まない)。

## 2. 作ったブロック

| ブロック | 内容 | 主なパラメータ |
|---|---|---|
| `OOO_ALU` | 整数ALU: RV64I + Zba / Zbb / Zbs / Zicond(mmRISC-2のCORE_EXUと同じ操作と符号) | — |
| `OOO_ALU2` | 発行ポートのALU: フルのOOO_ALUと絞ったOOO_ALU(8章)の2段直列(融合したALU + ALUを1サイクル)+ 分岐の比較(単独、またはALU + 分岐で1段目の結果と) | — |
| `OOO_FUSE` | デコードした4命令から次の2 µopを作る(古い順に貪欲に組む) | `LEVEL`(1〜3)、`SRC2`(8章) |
| `OOO_IQ` | 統合発行キュー: ソース3(10章で2、デスティネーション1)、2入 / 3出、wakeup-select 1サイクル、age matrix、レイテンシ2と外部のwakeup | `N`=16、`TAGW`=7(10章で6) |
| `OOO_RENAME` | 2 µop / サイクル、ソース3・デスティネーション2(10章で2・1)、RAT、フリーリスト、busy、組の中の依存、チェックポイント | `NREG`=96(10章で64)、`NCKPT`=8 |
| `OOO_PRF` | 96 × 64、書き込みバンクごとのLUTRAM + LVT | `NW`、`NR` |
| `OOO_UBTB` | 全連想のnext-line予測、1サイクルで次のフェッチアドレス | `NE`=32(8章で16、部分タグ`TW`=12) |

OOC合成のための登録ハーネス(`FPGA/OOO_OOC/rtl/OOC_WRAP.sv`)は次のとおり。`OOC_ALU2`は、結果レジスタからバイパス(5入力)を経て2段ALUに戻る1サイクルのループをそのまま作る。`OOC_FUSE`、`OOC_PRF`、`OOC_RENAME`は入出力をフリップフロップで挟む。

## 7. Vivadoの結果と判断(2026-10-24)

作者のVivadoで`synth_ooo.bat`を実行した結果(`FPGA/OOO_OOC/output/<top>/summary.txt`、`timing_reg2reg.rpt`、`utilization.rpt`)。50MHz(20ns)、OOC、配置配線後。

### 7.1 結果

| ブロック | LUT(Vivado) | FF | レジスタ間の余裕 | 論理段数 | Yosys比 | 判定 |
|---|---|---|---|---|---|---|
| OOC_ALU2 | 7,879 | 705 | **−0.696 ns** | 25 | 0.96 | 閉じない、大きい |
| OOC_FUSE | 172 | 158 | +10.606 ns | 11 | 0.83 | 閉じる |
| OOC_RENAME | 6,098 | 2,830 | +4.793 ns | 9 | 0.67 | 閉じる、大きい |
| OOO_IQ | 6,200 | 1,056 | +2.370 ns | 16 | 0.40 | 閉じる、大きい |
| OOO_UBTB | 3,132 | 2,648 | **−24.524 ns** | 65 | 0.62 | 閉じない |
| OOC_PRF(5構成) | 4,942〜14,271 | 946〜1,668 | +1.77〜+6.23 ns | 0〜1 | 0.64〜0.84 | 閉じる(7.4) |

- **LUTは物理LUT**(階層別の使用率レポートの「Total LUTs」、LUTRAMを含み、1つのLUT6_2に入った2つのLUTは1と数える)。mmRISC-2の予算(`ISSUES_J.md` 2章)と同じ数え方である。`summary.txt`の「LUT」はLUTセルの数で、LUTRAMを含まない。レジスタファイルではこの差が大きい(書き5 / 読み6で3,619と8,350)。`synth_ooo.tcl`は、次の実行から物理LUTも出す。

- **レジスタファイルが実行されなかった原因は`synth_ooo.bat`の誤り**。`vivado`自体がバッチファイルなので、`call`なしで呼ぶと、ループの外の最初の呼び出しのあとで元のバッチが終わってしまう。`call`を付けて直し、レジスタファイルだけを流す`synth_ooo.bat prf`を加えた。
- OOO_IQのWNS(+0.085 ns)は、ハーネスが仮定した入出力の遅延(6 ns ずつ)を含む経路の値で、実際の経路ではない。レジスタ間は+2.37 ns。
- Yosysとの比は0.40〜0.96と、ブロックで大きく違う(`REDUCE_J.md`の0.4〜1.4と同じ傾向)。

### 7.2 2段ALU(OOC_ALU2)

**最悪経路**: 2段目の結果レジスタ → バイパス → 1段目(シフト系、約8.7 ns、バイパス込み) → 2段目の比較(CARRY4 8段) → ファンアウト129で64ビットの選択(min / max) → 結果の選択 → 2段目の結果レジスタ。2段目だけで約10.8 nsかかっている。

**規模**: 1段目のOOO_ALUが4,663、2段目が3,095 LUT。mmRISC-2のCORE_EXU全体(1,670)の2〜3倍ある。OOO_ALUは操作ごとに演算器を別に書いている。加算と減算、比較(slt / min / max)、左右シフトと回転、clz / ctz / cpop がそれぞれ独立なので、そのまま回路になった。

**CoreMarkで融合の2段目に現れる操作**(`Plan/trace`の命令列から、融合した組を数えた):

| ビルド | ALU + ALUの組 | 2段目の操作(多い順) |
|---|---|---|
| `-O2` | 193,884 | bexti、xor、andi、addw、addiw、sh2add.uw、or、srliw、sh1add.uw、zext.h、sext.h、mv、add、subw |
| 最大最適化 | 268,882 | xor、andi、czero.eqz、addw、sh2add.uw、sh1add.uw、srliw、or、sext.h、zext.h、bexti、mv、addiw、subw |

slt / sltu、min / max、clz / ctz / cpop、回転、orc.b / rev8 は、2段目に一度も現れない。1段目には slt と czero.eqz が現れるので、1段目はフルのままにする。

**判断**:

1. **ALU + ALUの融合(chain = 1)は残す**。融合2(ALU + 分岐まで)に下げると −6%になるからである。
2. **2段目の操作を絞る**。残すのは、加減算(.w を含む)、sh1add〜sh3add(.uw を含む)、論理演算(即値を含む)、bext / bexti、zext.h / sext.h / sext.b、czero.eqz / czero.nez、即値シフトだけ。CoreMarkの2段目はすべてこの中に入るので、性能の損失は0になる。融合はこの集合の外の操作を2段目にしない(`OOO_FUSE`に、デコーダーから「2段目に置ける」印を入れる)。
3. **OOO_ALUを書き直す**。CORE_EXUと同じく、加算器を1つにして減算・比較・min / max で共有し、シフタも1つ(ファネルシフタ)で左右シフト・回転・bextをまかなう。比較の結果は加算器のキャリーから取るので、比較と選択の直列もなくなる。目標は、2段で1ポートあたり2.5k LUT以下。
4. タイミングと規模は、書き直したあとでもう一度Vivadoで確かめる。

### 7.3 発行キュー(OOO_IQ)

**判断**:

- **16エントリのwakeup-selectは1サイクルで閉じる**(+2.37 ns、16段)。この方式で進める。
- **規模の6.8kは予算に対して大きい**。8章の手段で4k前後を目標に減らす。手段は、発行するµopの読み出しをone-hotのAND-ORにすること、wakeupのタグバスを減らすこと、キューを分割することである。

### 7.4 レジスタファイル(OOC_PRF)

`synth_ooo.bat prf`で実行し直した結果(LUTは物理LUT):

| 書き / 読み | LUT | うちLUTRAM | FF | レジスタ間の余裕 | 4章の見積り |
|---|---|---|---|---|---|
| 3 / 8 | 6,455 | 4,128 | 1,116 | +6.23 ns | — |
| 5 / 8 | 10,657 | 6,880 | 1,456 | +2.18 ns | — |
| 6 / 9 | 14,271 | 9,288 | 1,668 | +1.77 ns | 約11.5k |
| **3 / 6** | **4,942** | 3,096 | 946 | +2.70 ns | 約4k |
| 5 / 6 | 8,350 | 5,160 | 1,246 | +2.21 ns | 約6.5k |

- どの構成も50MHzで閉じる。最悪の経路は、LUTRAMの書き込みアドレスへの経路(論理0〜1段)。
- 4章の見積りより2〜3割大きい。LUTRAMの量は、書き込みバンクの数と、読み出し3ポートごとの複製の数で決まる。
- 読み出しを8から6にすると、書き込み5で −2.3k、書き込み3で −1.5k になる。ソース2本までの制限(−1.7% / −1.1%)は、これだけで十分に引き合う。

**判断**:

- **融合する組のソースは2本まで、を確定する**。読み出しは6ポート。損失は −1.7% / −1.1% である(5章)。
- **書き込みは3ポート(組あたり1本)にする**。
  - 5ポートとの差は3.4k LUTで、OoO部分の予算(16k〜18k)の約2割にあたる。
  - 性能の差は −4.7% / −8.2%(融合構成の大きさ: ROB 32、IQ 16、LQ / SQ 12、チェックポイント8、uBTB 16、ソース2本までで、6.91 / 7.45 → 6.59 / 6.84)。3ポートでも目標(5.0 / 6.0)を超える。
  - 組の書き込みが1本になると、リネームも発行キューも、µopあたりのデスティネーションが1つで済む。両方とも、その分さらに小さくできる(9章)。
  - **物理レジスタも64本で足りる**。アーキテクチャの32本 + ROB 32 × µopあたり1本で、組あたり2本のときの96本が要らなくなる。64本はLUTRAMの深さ64にちょうど収まり(96本は64 + 32に分かれる)、タグも7ビットから6ビットになる。レジスタファイルはさらに減る見込みで、8.4で測る。
- **5ポートは、G0で予算に空きができたとき、最初に買い戻す候補にする**。1k LUTあたり約 +1.4% / +2.6%(物理レジスタ96本のまま比べた場合)で、残っている選択肢の中では性能の効率が良い。FPUを多サイクルに戻す(D3)などで空きができれば、ここに使う。

### 7.5 リネーム(OOC_RENAME)と融合(OOC_FUSE)

- **リネームは1サイクルで閉じる**(+4.79 ns)。**6.9kと大きい**。内訳(チェックポイント 8 × 32 × 7ビットと復元の選択、フリーリスト、busy)はまだ分けて測っていないので、階層を分けて測ってから減らす。チェックポイントを減らすと、8 → 6で −0.9% / −0.9%、8 → 4で −4.3% / −4.1%(uBTB 16、ソース2本までの条件)。数は8のまま、書き方で減らす。
- **融合は+10.6 ns、186 LUTで問題ない**。

### 7.6 uBTB(OOO_UBTB)

**大きく外した原因**: 当たったエントリのうち、ブロック内で最初に分岐を取るものを選ぶ処理を、32エントリを順に比べるループ(各エントリが、それまでの最良のオフセットと比べる)で書いていた。ツールはこれを32段の直列の比較にした(65段)。

**以前の判断の訂正**: 「uBTBなしでも −0.9%なので、重ければ外す」は融合なしの数字だった。融合ありで後段が速くなると、フロントエンドの比重が上がる。ソース2本までの条件でモデルを振り直すと次のとおり。

| uBTB | `-O2` | 最大最適化 |
|---|---|---|
| なし | 6.61(−4.8%) | 7.35(−2.1%) |
| 4 | 6.78 | 7.45 |
| 8 | 6.87(−1.0%) | 7.47 |
| **16** | **6.92(−0.2%)** | **7.50(−0.1%)** |
| 32 | 6.94 | 7.51 |

**判断**:

- **uBTBは残し、16エントリにする**。
- **選び方を並列にする**。ブロック内の8つの位置ごとに「当たって取る」のORを作り、8ビットの優先選択で位置を決め、ターゲットはone-hotのAND-ORで読む。
- **タグは部分タグ(12ビット前後)にする**。予測はF2で確かめるので、部分タグでよい。
- 規模の目標は1k LUT以下。

## 8. 判断の反映(RTL、2026-10-24)

7章の判断のうち、ALU、融合(ソース2本、書き込み1本)、uBTBの3つをRTLに入れた。発行キューとリネームの削減は、まだ入れていない。

### 8.1 変更

| ブロック | 変更 |
|---|---|
| OOO_ALU | 書き直した。加算器は1つにした(add / sub / sh*addに使い、slt / sltu / min / maxはその桁上げから出す)。シフタはファネルシフタ1つで、右シフト・回転・bextをまかなう。左シフトとrolは、ビットを反転して同じシフタに通す。clz / ctzはバイト単位の木(clzは反転してからctz)、cpopは加算の木にした。結果は演算器ごとのAND-ORで選ぶ。パラメータ`FULL`を0にすると、2段目用に絞った形になる |
| OOO_ALU2 | 2段目を`FULL = 0`にした。分岐の比較は減算1つから作る(符号ありと符号なしの両方) |
| OOO_FUSE | 入力`alu2ok`(ALU + ALUの後半に置ける操作か。デコーダーが出す)と、パラメータ`SRC2`(組のソースを2本までにする)、`W1`(組の書き込みを1本までにする、7.4)を加えた |

## 10. 発行キューとリネームの作り直し(2026-10-24)

7.4の帰結(組のソースは2本まで、書き込みは1本まで)を、発行キューとリネームに入れた。µopあたりソース2つ・デスティネーション1つ、物理レジスタ64本(タグ6ビット)にした。

### 10.1 リネーム(OOO_RENAME)

| | 前 | 今回 |
|---|---|---|
| µop | ソース3、デスティネーション2 | ソース2、デスティネーション1 |
| 物理レジスタ / タグ | 96本 / 7ビット | 64本 / 6ビット |
| RATの読み出し / 書き込み | 6 + 4 / 4 | 4 + 2 / 2 |
| フリーリスト | 64本。1サイクルに4つ取り出し、4つ返す | 32本。2つ取り出し、2つ返す |
| busyを消すwrite-back | 5 | 3(レジスタファイルの書き込みポート) |
| チェックポイント | 8 × 224ビット。µop 0の後とµop 1の後のRATの、どちらかを選んで書く | 8 × 192ビット。RATのフリップフロップから1サイクル遅れて写す(選択なし)。µop 1の取り消し用に11ビット |

**チェックポイントの写し方を変えた**:

- **前の版**: チェックポイントの1,792ビットのそれぞれが、µop 0の後のRATとµop 1の後のRATのどちらかを選んで書いていた。
- **今回**: 組のあとのRAT(次のサイクルにRATのフリップフロップが持っている値)を、1サイクル遅れて写す。全ビットが同じデータを受けるので、イネーブルだけで済む。µop 0のチェックポイントには、µop 1の書き先とその古い対応を持たせておき、復元のときに取り消す。
- **条件**: チェックポイントは、そのµopをリネームした次のサイクルには復元されないこと。パイプラインでは間にdispatch、発行、実行が入るので、必ず満たされる。
  - テストでは、この最短(2サイクル後)で解決する場合を多く入れた(22,916回)。
  - 1サイクル後にも解決させると、テストが失敗することも確かめた(68,492件の不一致)。
- **採らなかった案**: 「1サイクルにチェックポイントは1つまで」。モデルで −1.7% / −2.0%になった(`Plan/model`の`ck1`)。jalにチェックポイントを取らないようにしても変わらない(`ck_jal`。CoreMarkの内側のループにjalはほとんどない)。

### 10.2 発行キュー(OOO_IQ)

| | 前 | 今回 |
|---|---|---|
| µop | ソース3、デスティネーション2 | ソース2、デスティネーション1 |
| wakeupのタグバス | 14(3ポート × 2本 × 今と遅延、外部2) | 6(ポート0の今、ポート1の今、ポート0の遅延、ポート2の遅延、外部2) |
| ソースの比較器 | 16 × 3 × 14 = 672 | 16 × 2 × 6 = 192 |
| 発行したµopの読み出し | 番号に符号化してから選ぶ | 許可(one-hot)のAND-OR |

**バスを減らせる理由**: 次の2つを、dispatchの規則として仕様に入れる。テストのµopもこの規則に従う。

- ポート1(ALU1)が出すのはレイテンシ1だけ。レイテンシ2のµop(乗算)は「ALU0のみ」として出す。
- ポート2(LSU)がレジスタを書くのはロード(レイテンシ2)だけ。ストアは書かない。

## 11. LSU(Phase 1の手順2、2026-10-25)

`Doc/UARCH_J.md` 8章の手順2の最初のブロック。見積りの幅がいちばん大きかったLSU(LQ / SQとフォワーディング)を書き、単体テストとバグ注入で検証し、Vivadoのスクリプトを用意した。

### 11.1 ブロック(`RTL/CPU/OOO/OOO_LSU`)

| 項目 | 内容 |
|---|---|
| パイプライン | E: アドレス計算(base + 即値)、ミスアラインの判定、ストアはSQに書いて完了、ロードはD$に要求。M: D$の応答、SQの検索(同じ8バイトのワードに書く、いちばん若い古いストア)、結果の選択と整列。WB: 結果のレジスタ(後続から見て発行の2サイクル後) |
| LQ / SQ | 12 / 12。dispatchで順に割り当て(1サイクルに2つまで)。LQはコミットで、SQはコミット済みのストアをD$に書いたところで解放。チェックポイント用に、各スロットのあとの末尾を出す |
| フォワーディング | いちばん若い古い一致するストアがロードを覆えば、そのデータ。覆わなければ(一部だけ重なる)、ロードは待ってLQからやり直す |
| 順序 | 保守的: ロードは、古いストアのアドレスがすべてわかってからD$のデータを使う。発行キューがロードを止めておけるよう`lsu_st_known`(LQのエントリごと)を出し、Mでも確かめる |
| ミス | D$の補充(`dc_fill_*`)を待ち、遅れて書き戻す(`wb_late`、wakeupが要る)。書き込みポートが使われているときの補充は1つバッファする |
| 投機的wakeupの取り消し | ポート2のロードが予定のサイクル(WB)に結果を出せないとき、Mで`ld_cancel`とタグを出す。後続をどう止めるか(リプレイの方式)はこのブロックの外で、コアの組み上げで決める(11.4) |
| 回復 | `restore`でチェックポイントの末尾に戻す。`flush_all`はコミット状態へ(LQは空、SQはコミット済みのストアだけ残り、それらは書き出される)。回復のサイクルにMにいたロードは、エントリが残れば待ち状態にしてやり直す |
| D$ | ポートは抽象化した(タグつきの要求と補充、書き込みポート)。mmRISC-2のD$へのアダプタは外。アダプタは`dc_kill`(解放されたLQエントリ)の補充の応答を捨てる(ラインの補充はする) |

**ストアの書き出しは、ロードがEにいるサイクルには行わない**。そのロードはこのサイクルにD$を読み、次のサイクルにSQを探すので、ストアはそのときまだSQにいなければならない(ブロックRAMは読み出し優先なので、同じサイクルに書いたストアは読めない)。

### 11.2 検証(`SIM/OOO_UNIT/tb_lsu.cpp`)

- **テストベンチはLSU以外のコアの役をする**。プログラム順の、ロード・ストア・分岐・そのほかのµopのランダムな列を、いくつかの8バイトのワードに向けて出す(ロードとストアがよくぶつかる)。dispatchは1サイクルに2つまで(キューと24エントリの窓の空きがあるあいだ)、ポート2へはランダムな順に発行する(ロードはたいてい`lsu_st_known`のあとだが、ときどき早めて、LSU自身の待ちを試す)、コミットは順に。D$のモデルは、ヒット / ミスをランダムに返し、数サイクル後に補充し、ストアを受ける(ときどき受けない)。分岐はランダムに解決し、一部は予測ミス(チェックポイントへのrestore)。ミスアラインのアクセスは例外で、先頭に来たら`flush_all`。
- **確かめること**:
  - すべてのロードの値: コミット済みのメモリに、まだコミットしていない古いストアをプログラム順にかけたもの(フラッシュされたストアは入らない)
  - ロードは1回だけ完了する(予定どおりか遅れて。ミスアラインは例外で、書き込みなし)
  - `ld_cancel`は、ポート2のロードが予定のサイクルに結果を出さないとき、そのときに限って立つ
  - ストアはコミットの順に、正しいデータとバイトマスクでD$に届く
  - `lsu_st_known`は、アドレスのわからない古いストアのあるロードには立たない
  - デッドロックがない
- **結果**: 7つのシード(各30万サイクル、計210万サイクル)ですべてPASS。1つのシードで、ロード76,407(うち遅れ21,918)、ストア80,510、取り消し32,432、restore 6,052、flush_all 3,475。
- **テストで見つかったRTLのバグ**(すべて直した):
  1. SQの先頭から数える処理で、`head + k`をインデックスの幅(4ビット)で計算しており、16で折り返していた(キューは12)
  2. 回復のサイクルにMにいたロードが、完了も保持もされず、回復で残る古いロードが完了しなかった
  3. フラッシュされたロードのD$の補充が、同じLQエントリの2つ後の持ち主に取られた(1ビットのエポックが一周して一致した)。`dc_kill`を加えて直した
- **バグ注入**: 11件を加え、すべて検出された(合計50件)。最初の注入で、エポックを外す2件が検出されず、エポックが冗長だとわかったので外した(`dc_kill`、解放したエントリを同じサイクルに再割り当てしないこと、回復のサイクルにEからMへ進めないことで足りる)。ストアの書き出しの制限を外す1件も最初は検出されず、D$のモデルが書き込み優先になっていたテスト側の穴だったので、読み出し優先に直した。

### 12.2 リネームのコミット状態(`OOO_RENAME`)

- コミット状態のRAT(32 × 6ビット、コミットで書く)と、フリーリストのコミット済みの先頭(コミットした割り当てごとに進む)を加えた。
- `flush_all`で、RAT ← コミット状態のRAT、フリーリストの先頭 ← コミット済みの先頭。
- 約束ごと: `cmt_wr`は割り当てのあったµopだけに立つ(x0には立たない。ROBの`disp_wr`はリネームの割り当てから)。

### 12.3 検証

- **`tb_rob.cpp`(新規)**: 参照のROBと照合する。ランダムなµop(ALU / 融合 / ロード / ストア / 分岐 / 非投機 / デコードで見つかった例外)をdispatchし、4つのポートから順不同に完了させる(ときどき例外)。分岐は完了と同じサイクルにALUポートで解決し、一部は予測ミス(2つ同時のことも)。ROBにない番号の完了・解決を混ぜ、トラップやrestoreのサイクルにもdispatchを出す(入ってはならない)。毎サイクル、`rob_avail`と割り当てた番号、先頭と`head_ns`、トラップ(原因、pc)、コミットのすべてのフィールドと数、restoreの番号とチェックポイントを確かめる。4つのシード(各40万サイクル)ですべてPASS。1つのシードで、コミット196,138 µop(命令235,378)、トラップ13,357、restore 12,845(うち2つ同時の予測ミス415)。
- **`tb_rename.cpp`(拡張)**: コミットで参照のコミット状態も更新し(µopは書き戻しのあとでだけコミットする。コアと同じ)、ときどき`flush_all`を入れる。PASS(flush_all 909回)。
- **バグ注入**: ROBに9件、リネームに3件を加えた。最初の実行で4件が検出されず、4つとも冗長な論理だったので外した(12.4)。残る8件はすべて検出(合計62件)。

### 12.4 バグ注入で外した論理

| 論理 | 冗長だった理由 |
|---|---|
| ROB: ROBにない番号の完了を無視する判定 | ROBにないエントリは、割り当てのときにクリアされる。フラッシュしたµopの実行中の分は、各ユニットが捨てる(この判定では捕まえられない) |
| ROB: トラップ / restoreのサイクルのdispatchを止める判定 | 末尾はトラップ / restoreが決めるので割り当てにならず、書き込みは新しい末尾より先のエントリ(割り当てのときにクリアされる)に行くだけ |
| リネーム: コミット状態のRATでx0を除く判定 | `cmt_wr`はx0には立たない(約束ごと) |
| リネーム: `flush_all`でbusyをすべて消す処理 | コミット状態のRATにあるレジスタは、コミットの前に値が書かれていてbusyは0。空いたレジスタのbusyは、割り当てのときに立て直す |

## 13. フェッチバッファとFTQ(Phase 1の手順2、2026-10-25)

手順2の3つ目のブロック。I$(F2)とデコード(D1)のあいだ。どちらも単体テストとバグ注入で確かめ、Vivadoのスクリプトを用意した。PCの生成、I$とのインターフェース、プリデコード、予測器の上書き(TAGE-S、BTB、RAS)は、それらのブロックと一緒に作る。

### 13.1 フェッチバッファ(`RTL/CPU/OOO/OOO_FBUF`)

| 項目 | 内容 |
|---|---|
| 記憶 | パーセルの輪ではなく、**16バイトのブロックを丸ごと4つ**並べるキュー。ブロックはそのままスロットに入れ、使う最初と最後のパーセル(takenのあとはブロックの途中から始まる。予測takenの転送の後半でブロックは終わる)、taken、FTQの番号を添える。データはLUTRAM(書き込み1、読み出し2: 先頭のブロックと次のブロック) |
| 窓 | 8パーセル: 先頭のブロックの今のパーセルから残り、続けて次のブロックの使う部分。taken転送からその飛び先までのあいだのパーセルは、作りからして飛ばされる |
| 出力 | 窓の命令長から(4段の累積)、1サイクルに最大4命令。RVC(1パーセル)か32ビット(2パーセル)。それぞれにビット、RVC、前半のFTQ番号とパーセル、予測taken(後半がtakenのブロックの終わり)、直前の命令にそのまま続くか(融合のため)。後半がまだ来ていない32ビット命令は待つ |
| 入出力 | 1サイクルに1ブロック入れる(空きスロットがあれば`in_ready`)。デコードは先頭から`consume`個を取る。1サイクルに2ブロックまで解放。`flush`(リダイレクト)で空にする |

- **パーセルでなくブロックにした理由**: パーセルの輪(`Doc/UARCH_J.md` 3.2、16パーセル)は、8パーセルを任意の位置に入れるために、すべてのパーセルの前に選択が要る。ブロックのキューならブロックをそのまま書き、選択は出口の窓だけで済む(窓のパーセルごとに8対1の選択が2つ、そのあと4命令の取り出し)。記憶は32パーセルになるが、LUTRAMに入る。
- **制限**: 窓に入るのは2つのブロックだけなので、先頭のブロックも次のブロックも短いとき(次のブロックの始めのほうにtaken転送がある)は、3つ目のブロックがあればそのサイクルにもっと出せた。サイクルモデルはバッファを命令数で数えており、大きさはほとんど効かない(16 → 8で −0.3%、`MODEL_J.md` 6)。

### 13.2 フェッチターゲットキュー(`RTL/CPU/OOO/OOO_FTQ`)

| 項目 | 内容 |
|---|---|
| エントリ | 8。フェッチブロックごとに1つ、F2からそのブロックの最後の命令のコミットまで |
| フィールド | フェッチアドレス、予測した次のアドレス、takenとそのパーセル、予測器の状態32ビット(TAGEのproviderとタグ、履歴。ここでは中身を見ない)。LUTRAM、1サイクルに書き込み1 |
| 読み出し | デコード用に2つ(窓は2ブロックにまたがる。命令のpcはブロックのアドレスとパーセルから)、分岐の解決用に1つ |
| 回復 | `pop`(コミットで1サイクルに2ブロックまで)、`restore`(予測ミス: そのブロックは残し、より新しいものを捨てる)、`flush_all`(空にする) |

### 13.3 検証

- **`tb_fbuf.cpp`(新規)**: 実行のモデル。ランダムなプログラム(パーセルの約4分の1が32ビット命令の始まり)を、ランダムな飛び先へのランダムなtaken転送で走らせ、その流れをフェッチと同じようにブロックに切る(ブロックの終わりまで、またはtaken転送の後半まで。パーセル7から始まる32ビット命令はそこでブロックを終え、次のブロックで終わる。それがtaken転送でも同じ)。ブロックは`in_ready`のときに入れ(ときどき入れない)、デコードは出された命令のうちランダムな数を取り、ときどきフラッシュでまだ取っていない最も古い命令からフェッチをやり直す。毎サイクル、すべてのスロットのビット、RVC、パーセル、FTQ番号、taken、seqと、**出す命令の数そのもの**(窓の中に完全にある命令の数、最大4)を確かめる。9つのシード(各40万サイクル)でPASS。1つのシードで、取った命令708,445、taken転送101,522、ブロックをまたぐ命令17,333、フラッシュ1,313。
- **`tb_ftq.cpp`(新規)**: 参照のキューと照合する。ランダムなpush、pop、キューの中のエントリへのrestore(満杯のときや、折り返しをまたぐときも)、同じサイクルにpopのあるflush_all。毎サイクル、3つの読み出しポート、`push_ready`、`push_idx`を確かめる。4つのシードでPASS。
- **テストで見つかったバグ**: バッファが空のキューからpopしていた(古いブロックの値で決まっていた)、空のキューにブロックが入るときに先頭のパーセルを設定していなかった。どちらも直した。
- **バグ注入**: バッファに11件、FTQに7件。2件が検出されず、どちらも冗長な論理だった(13.4)。残る16件はすべて検出(合計79件)。

### 13.4 バグ注入で外した論理

| 論理 | 冗長だった理由 |
|---|---|
| バッファ: フラッシュのサイクルにブロックを書かない判定 | ポインタはフラッシュで戻るので、ブロックは空いたスロットに入るだけ |
| FTQ: restore / flush_allのサイクルにエントリを書かない判定 | 末尾はrestore / flush_allが決めるので、エントリは新しい末尾より先のスロットに入るだけ |

### 13.5 規模(Yosys)と、Vivadoの実行のお願い

| ブロック | Yosys | G0の見積り |
|---|---|---|
| OOC_FBUF | 1,381 LUT + LUTRAM 176(物理で約1.56k)、FF 359(ハーネス約310を含む) | バッファで1.3k〜1.8k |
| OOC_FTQ | 15 LUT + LUTRAM 224(約0.24k)、FF 329(すべてハーネス) | フェッチの2.0k〜2.8kの内 |

- OOC_FBUFでは、デコードは止まっていなければ出された命令をすべて取るものとした。測る経路は、バッファの状態から窓と命令長を通って取る数へ、そして先頭のポインタとパーセルへ戻るもので、コアにできるループそのもの。
- バッファは見積りの中。`Doc/UARCH_J.md` 4.3のフェッチの行(2.0k〜2.8k)には、まだ書いていないPCの生成、I$とのインターフェース、プリデコードも入る。


|---|---|---|---|---|---|
| OOC_FBUF | **931** | 192 | 323 | **+0.539 ns** | 16 |

- **FTQ**はLUTRAMだけで、余裕も十分。

- **確認**: 単体テスト10本すべてPASS、`tb_fbuf`は9シードでPASS。バッファのバグ注入は新しいコードに合わせ(3件を書き直し、2つ解放したあとの開始パーセルの読み出しにM86を追加)、12件すべて検出(合計80件)。
- **`synth_ooo.bat OOC_FBUF`の再実行をお願いしたい**(規模はほとんど変わらず、余裕は約2 ns増える見込み)。

## 14. フロントエンド(Phase 1の手順2、2026-10-25)

手順2の4つ目のブロック。PCの生成、I$とのインターフェース、プリデコード、TAGE-S、BTB、RASで、F0からフェッチバッファとFTQに入るブロックまで。どれも単体テストとバグ注入で確かめ、フロントエンド全体のVivadoのスクリプトを用意した。

### 14.1 フェッチブロック単位のTAGE-S(先に測った)

モデルのTAGE-S(`Plan/model/tage.h`)は、分岐を1つずつ、その分岐自身のpcで引き、分岐1つにつき履歴を1ビット持ち、すぐに更新する。ハードウェアでは、表はF1でフェッチアドレスだけで読む。プリデコードがブロックの分岐を見つける前で、しかも16バイトのブロックには条件分岐がいくつも入りうる。そこで予測器をブロック単位にした(`Plan/model/tageblk.h`): フェッチアドレスと履歴で行を引いてタグを比べ、行にはブロックの1つ目・2つ目…の条件分岐(「スロット」)の方向カウンタを置く。ベースの表はパーセルごと。インデックスに使う履歴は、まだF1とF2にあるブロックの分だけ遅れる。CoreMarkの条件分岐での測定(`Plan/model/tageblk.sh`、`results/tageblk.txt`):

| 予測器 | -O2 | 最大最適化 |
|---|---|---|
| モデルの分岐ごとのTAGE-S | 0.761% | 0.683% |
| ブロック単位、スロット1 | 2.301% | 2.970% |
| ブロック単位、スロット2 | 0.808% | 1.303% |
| ブロック単位、スロット2、履歴が2ブロック遅れ | 0.863% | 1.412% |
| ブロック単位、**スロット3** | 0.773% | 0.777% |
| ブロック単位、スロット3、履歴が2ブロック遅れ | 0.825% | 0.850% |
| 同じでuカウンタの半減なし | **0.821%** | **0.845%** |

- **スロット3**: 2では、最大最適化のビルドに3つ目の分岐を持つブロックが多く(スロットからあふれる分岐が10,778)、ベースのカウンタだけではうまく予測できない。3にすると、どちらのビルドでもスロットからあふれる分岐はない。
- **履歴**: スロットの分岐1つにつき1ビット(ブロックあたり最大3)。あるブロックがF0にあるとき、F1とF2のブロックはまだその履歴に入っていない。遅れは0〜2ブロックで、フェッチが泡なしで流れているときは2。測ったのはこの場合。
- uカウンタの**半減はしない**(すべての行を走査する必要がある)。効果はなかった。
- モデルに比べて、10反復で予測ミスが+348 / +799。CoreMark/MHzで約 **−0.2% / −0.5%**(1回9サイクル)。

### 14.2 ブロック(`RTL/CPU/OOO`)

| ブロック | 内容 |
|---|---|
| `OOO_PREDEC` | プリデコード(F2): ブロックの命令の境界(開始パーセルから、または前の行から持ち越した32ビット命令の後半のあとから)と、終わりのパーセルごとの制御転送の種類(条件分岐、jal、jalr、call、return)、分岐とjalのターゲット。加算器8つを並列に置き、最初のtaken転送を選んだあとは選択だけで済むようにした |
| `OOO_TAGE` | ブロック単位のTAGE-S(14.1): 1024行のタグつきの表4つ(履歴5 / 12 / 30 / 70、タグ8 / 8 / 9 / 9ビット。行は有効ビット、タグ、uカウンタ、方向カウンタ3つ)と、512行 × 8パーセルのベースの表。すべてブロックRAM。畳み込んだ履歴は70ビットのシフトレジスタのXORで、保存すべき畳み込みレジスタはない。F1でタグを比べ、providerとalternateをF2のために持つ。コミットでの更新は、予測のときに読んだ行(ブロックあたり270ビットのメタデータ)からproviderとalternateを求め直し、スロットごとにSeznecのTAGEに従う。各表への書き込みは1回まで |
| `OOO_BTB` | 間接ジャンプだけのもの(リターンでないjalr / c.jr / c.jalr): ブロックRAMに256行、フェッチアドレスで読み、1行に1つのジャンプ(タグ、パーセル、ターゲット)。解決時に書く |
| `OOO_RAS` | LUTRAMに16エントリ。F2でpushとpopをする。ブロックはポインタとpushで上書きされるエントリを持ち、予測ミスでそれらを戻して、予測ミスした転送自身のpushかpopをする |
| `OOO_FETCH` | `OOO_UBTB`を囲むF0〜F2: フェッチアドレスでのI$への要求、実行中の要求(最大2つ、リダイレクトのサイクルにもう1つ)。F2では、最初にtakenと予測された転送でブロックを終える(分岐: TAGEのスロット、jal: 常に、return: RAS、その他のjalr: そのパーセルのBTB)。次のアドレスがフェッチの進んだ先と違えば、F0をリダイレクトし(2サイクル)、uBTBを学習させる。ブロックはTAGEのメタデータとRASのスナップショットと一緒に出る |

書きながら決めたこと:

- **直接のターゲットはプリデコードから、BTBは間接ジャンプだけ。** 分岐とjalのターゲットは命令のビットの中にあり、I$はそれをF2で出す。加算器8つで表なしに求まる(初回のミスもなく、学習もいらない)。モデルのBTB(無制限、最後のターゲット)は、分岐の初回の予測を止めていただけだった。
- **ブロックの4つ目以降の条件分岐は非takenと予測する。** バグ注入でわかった: そのベースのカウンタは学習されず(更新はスロットだけ)、実際には「常にtaken」になっていた。CoreMarkにはない。
- **I$との約束ごと**(mmRISC-2のICACHEを16バイトに広げて使う): F0で受け付けた要求は、ヒットなら2サイクル後、ミスならもっとあとに、順に答える。次のサイクルに別の要求を受け付けるのは、この要求がヒットするときだけ。TAGEとBTBのF1の結果は、ちょうどこのタイミングのために保持する。受け付けた要求にはすべて答える(killはない): リダイレクトで要らなくなった答えはフェッチが捨てる。要求にはフェッチアドレスをそのまま渡す。
- **クレジット**: フェッチは、フェッチバッファとFTQに、そのブロックと実行中の分の空きがあるときだけ要求する。だから答えが待たされることはない。
- **2つの行にまたがる32ビット命令**は、2つ目のブロックと一緒にプリデコードする(前半を`carry`として持つ)。2つ目は必ず次の行。OOO_FBUFは、それを前半のブロックから出す。
- **uBTBはF2から学習する**: uBTBとF2が食い違ったとき(F2の転送か、uBTBの推測がそれより前にあったときはその推測を弱める)。F2が誤りとした無条件のuBTBエントリ(エイリアス)は弱められず、置き換えられるまで残る。そのたびにオーバーライドが直す。
- **コアの組み上げのために**: FTQは、ブロックあたり312ビットのフロントエンドの状態(TAGE 270、RAS 42)を持つ。更新のために先頭で、回復のために予測ミスしたブロックで読む。さらに、解決時に書くスロットの分岐の結果も持つ(パーセルで対応をとる。2行にまたがる分岐は次のブロックに属する)。32ビットから312ビットにすると、LUTRAMで約+0.2k。回復(予測ミスした転送までのスロットの履歴ビット、RASのpush / pop)は、バックエンドがブロックのメタデータから計算する。

## 15. ミスしたロード: 発行キューでの選択的なリプレイ(2026-10-25)

> **2026-10-26に置き換えた**: コミットのあとのリプレイと10エントリの発行キューに(G0b D-12、`Doc/UARCH_J.md` 6.3と6.5)。選択的なリプレイは実測で+1.4kで、エントリも2つ多く要る。この章は作ったものの記録で、RTLはgitにある(5935e45、7d93d41)。

11.4の未決事項(作業整理のB1)。ロードの後続は、結果がわかる前に起こされる(ロード使用2サイクル)。そのため、LSUがMで、そのロードがWBで結果を出せない(`ld_cancel`: D$ミス、待ち)とわかったら、その見込みで発行したものを取り消さなければならない。

### 15.1 先に測ったこと、作者の決定

- **CoreMarkでの頻度**(生のトレース、16 KB 4ウェイのD$のモデル、32命令の範囲で実行中のストア): 10反復で、**ロードのD$ミスは26回(すべて初回)、実行中のストアとの部分的な重なりは0**(33,914 / 33,168のロードは丸ごとフォワーディング)。保守的な順序付け(`lsu_st_known`)のもとでは、ほかの待ちもない。つまりCoreMarkにはほとんど効かず、効くのはミスの多いコード(Linux)。
- 作者に2つの案を示した: コミット時の再フェッチ(取り消されたロードにROBで印をつけ、コミットのときにそれより新しいものをすべて再フェッチする。約+0.05k LUTで発行キューは変えないが、D$ミスのたびに再フェッチと、ミスの間に進めた作業を失う)と、**発行キューでの選択的なリプレイ**(約+0.7k〜1.2k LUT)。**作者は選択的なリプレイを選んだ。**

### 15.2 設計(`RTL/CPU/OOO/OOO_IQ`)

| 項目 | 内容 |
|---|---|
| ロードのスロット | サイクルcに発行したロードは、スロットc mod 4を持つ(4つ: ロードはwakeupからc + 3まで未決)。c + 3に、そのサイクルのMの`ld_cancel`で決まる: 取り消しか確定 |
| マスク | wakeupのバスは、その値が依存している未決のロードのマスクを運ぶ(ロードは自分のスロットを加える)。各ソースは起こされたときのマスクを持ち、µopはソースのマスクのORで発行する(`iss_ldm`) |
| 残すエントリ | マスクつきで発行したµopは、ロードが確定するまで選ばれない状態でキューに残り、確定したらエントリを空ける。取り消されたら待ちに戻り、そのロードを通して起こされたソースはすべて非レディに戻る |
| 取り消されたロード | キューからは発行し直さない(LSUがLQから試し直し、`ext_*`で遅れて答える)。そのエントリは選ばれないまま、その答えを待つ |
| ディスパッチ | 生産者がキューにいて発行されていない(取り消された、または取り消されたロード)ソースは、リネームが何と言っても非レディ。生産者がまだ確定していないソースは、生産者のマスクをもらう。64本のレジスタにマスクを持たせる表(約1k LUT)の代わりに、キューの12の生産者を見る |
| `ld_cancel`は遅い | LSUのMでサイクルの終わりに出るので、エントリの次の状態にだけ効かせ、そのサイクルの選択には入れない: そのサイクルに取り消されたスロットに頼って選ばれたµopは、発行しなかったものとして戻し、その遅延wakeupも出さない |
| ユニット | `ld_kill`(前のサイクルに取り消されたスロット)と`iss_ldm`: マスクが`ld_kill`に当たるRRかEXのµopは捨てる(書き戻し、完了、分岐の解決をしない。LSUではSQへの書き込みとD$への要求をしない) |

- **1サイクル遅らせてレジスタで決めず、c + 3で決める理由**: ロードに頼って発行したµopのエントリは、ロードが決まるまで残るので、発行キューの空きを使う。モデル(`keep_spec`、15.3)では、c + 4まで残すと −1.1% / −0.5%、c + 3までなら −0.2% / −0.2%。
- **コアの組み上げのために**:
  - すべてのユニットが`iss_ldm`と`ld_kill`で捨てる(上)。LSUのポート2のパイプラインは発行からMまで止まらない(今のとおり)。その`ld_cancel`をそのまま発行キューに入れる
  - リネームのレディビット(`disp_rdy`)はwakeupのバスに従う(タグはブロードキャストからレディ)。リネームとディスパッチのあいだのサイクルのブロードキャストも含む。`tb_iq`はこれを前提にしている。これは以前から必要だった(書き戻しでビットを消すと、wakeupと書き込みのあいだにディスパッチされたµopは、いつまでも起こされない)。取り消しのあとは、キューがそれを正す
  - ロードを`lsu_st_known`までキューに留める配線は、まだこれから(11.1)

### 15.4 検証、規模、Vivadoの実行のお願い

- **`tb_iq`(書き直し)**: 値が使える時刻の帳簿に、値ごとの依存している未決のロードを加えた。ロードの4分の1を取り消す(発行の3サイクル後に`ld_cancel`)。取り消しで、そのロードに依存する値はすべて使えなくなり、それに頼って発行したµop(取り消しのサイクルに発行したものも)は待ちに戻り、ロードは遅れた答えを待つ。確定は集合から外す。リネームのレディビットは、リネームが知っているとおり(wakeupで立ち、取り消しでは戻らない)に与えるので、キューの補正も試される。毎サイクル、すべての発行(古い順、早すぎず二重でない)、そのマスク、`ld_kill`、`disp_ready`(残すエントリと待つエントリ)を確かめる。12シードでPASS。1つのシードで、発行173,765 µop、残したもの73,508、取り消したロード10,988、戻したµop 10,134。

- **ディスパッチで生産者のマスクをもらう代わりに、その確定を待つか?** モデルではほとんど損をしない(−0.06% / 0.00% / −0.14%)。しかしRTLでは、各ソースが生産者のエントリ番号(4ビット)を持ち、確定で解放されるエントリを16対1で選ぶ必要がある。構造から数えると約0.3kで、置き換える対象のマスクのOR(約0.1k)より大きい(Yosysでは2つの変更を合わせて−0.46kで、1つ目の削減をほとんど食った)。採らない。代わりに確定までディスパッチを止める形は安いが、−1.5% / −5.9%かかる。
- **ロードのスロットを4つから3つに。** ロードはwakeupからc + 3まで未決なので、マスクが持つのは直近3サイクルに発行したロードだけ。4つ目は、c + 3に発行したロードが、そのサイクルに決まるスロットを取るためにあった。3つにする代わりに、ロード自身のビットは、それが立つサイクルの決定から外し(決定のあとで、残すマスクとwakeupに加える)、`iss_ldm`からも外す(ロードは自分の取り消しでは捨てられない: LSUが持っている)。マスクのビットがすべて4分の1減る。
- **バグ注入で外した論理**: ロードの遅延wakeupで確定済みのビットを消す処理。スロットが3つなら、ロードの発行のサイクルに確定するビットはロード自身のスロットで、wakeupはどのみちそれを運ぶ。
- **結果**: 発行の流れはサイクル単位で同じ(`tb_iq`の数字が一致)、12シードでPASS。バグ注入は新しいコードに合わせ(M134、M142、M151を付け替え)、発行キューの27件はすべて検出(合計146件)。Yosysは7,288 → **6,172 LUT**(−15%)、FFは975 → 924。15.5で測ったVivado / Yosys 0.68では、16エントリで約4.2k(4,974から)、12エントリで約3.3k。

### 16.1 ブロック(`RTL/CPU/OOO/OOO_DEC`)

- **mmRISC-2のデコーダをそのまま使う。** `CORE_DECOMP`(RVC → 32ビット)と`CORE_DEC`(RV64GC + Zba / Zbb / Zbc / Zbs / Zicond / Zicsr / Zifencei / Zicbozと特権命令)を、mmRISC-2 Rev.02から変えずに`RTL/CPU/CORE`へ持ってきた。命令セットはmmRISC-2のもの(G0で維持と決めた)で、`OOO_ALU`はすでにCORE_EXUの操作の符号を使っているので、CORE_DECの記録をそのまま渡せる。mmRISC-2ではこれでLinuxが起動した。
- `OOO_DEC`は、4つのスロットのそれぞれに1組ずつ置き、コアの残りが要るものを導く:

| フィールド | 使うもの | 内容 |
|---|---|---|
| `cls`、`op`、`rd`、`rs1`、`rs2`、`use_rs1`、`use_rs2`、`imm`[11:0]、`mem_size`、`alu2ok` | `OOO_FUSE` | 種類(ALU、分岐、jal、jalr、整数ロード、整数ストア、MUL / DIV、その他)、モデルの操作の種類(lui、auipc、slli(w)、srli / srai(w)、add(w) / sh*add(.uw) / add.uw、addi(w))、整数レジスタだけ(整数レジスタに書かないときrdは0)、絞った2段目にある操作か |
| `port`、`lat2`、`ext_ans` | 発行キュー | 0 どのALUでも、1 ALU0だけ(MUL / DIV、CSRとシステム)、2 LSU、3 FPU。2サイクルの結果(乗算、整数ロード)。外から起こされる結果(除算、AMO / LR / SC) |
| `illegal`、`nonspec`、`sys`、CSRのフィールド | ROB | 予約されたRVCの符号か知らない命令。先頭でだけ実行するもの(`Doc/UARCH_J.md` 3.9) |
| CORE_DECの記録の残り | 実行 | ALUの操作とオペランド、32ビットの即値、分岐、MDU、メモリのコマンド、FPのフィールド |

- FPのロードとストア、AMO / LR / SC、cbo.zeroは、融合では「その他」(Phase 1にはFPのリネームがなく、それ以外は先頭で実行する)。`op`はニーモニックではなく符号から求める: c.liやmvはaddiとして数える(モデルのトレースではliやmvという名前だった。これで増える組も、W1 / SRC2で制限される)。

### 16.2 検証(`SIM/OOO_UNIT/tb_dec.cpp`)

- **参照**はCORE_DEC / CORE_DECOMPとは別に書いた: 仕様の表(opcode、funct3、funct7)からの32ビットのデコーダ、Spike自身のフィールドの取り出し(`insn_t::rvc_*`)を使うRVCの展開器、`Doc/UARCH_J.md`からの派生フィールド。
- **命令が存在するかは、Spikeで実行して決める**: mmRISC-2の命令セットで作ったprocessor_tを、Mモード・FPU有効で1命令進める。illegal instructionの例外にならなければ存在する。Spikeの逆アセンブラだけでは決められなかった: ISAの指定にかかわらずすべての拡張を知っており(ベクトル、四倍精度、Zfh、暗号)、予約されたRVCの符号も通す。SpikeはVがなくてもベクトル命令を実行するので、その符号は聞かない。CSR命令(CSRが存在するかは実行時の問題)と予約された静的丸めモードも聞かない。

### 17.1 発行キューのペイロード(`RTL/CPU/OOO/OOO_IQPL`)

### 17.2 D$のアダプタ(`RTL/CPU/OOO/OOO_DCAD`)と、mmRISC-2のD$に加えた出力1つ

**両側が合わない。** `OOO_LSU`(11.1)はEでロードをLQのエントリとともに出し、次のサイクルのMでヒットとデータを待つ。ロードにはreadyがなく、ミスのフィルはLQのエントリで受け、ストアはreadyのあるポートで書き出す。mmRISC-2の`DCACHE`は要求をvalid / readyで受け、**要求の順に、早くても要求の2サイクル後に**答える(`d_resp_valid`はレジスタ)。

**D$に出力を1つ加えた**(`RTL/CPU/CACHE`: `DCACHE`、`CACHE_TAG_ARRAY`、`CACHE_DATA_ARRAY`をmmRISC-2 Rev.02から持ってきた。アレイは変更なし): `d_hit_now` / `d_hit_now_data`、ステージ1でのロードのヒットを、見つけたそのサイクルに出す(8バイトの語)。`hit && s1_is_load && s1_can_go`: 要求はいまステージ1を出て、データはリオーダバッファに入る。`s1_fast`と違い、古いものが待っていないことを求めない。その条件は`d_resp_*`の順のためだけのもので、そちらは今までどおり順に答える(アダプタはその写しを捨てる)。これでLSUは**ミスの下でのヒット**を得る。

| 項目 | 内容 |
|---|---|
| 要求 | 1サイクルに1つ: (1) Eのロード、その語の8バイトの読み出し。(2) EでD$が受けなかったロード(保留)。(3) 書き出し中のストア(バイトマスクを大きさと位置にし、データを下へずらす)。LSUはEにロードがあるサイクルにはストアを書き出さない。保留のロードがある間はストアが待つ |
| 物理アドレス | 受けられたときに要求のアドレスをレジスタに取る(`d_req_paddr`。Phase 1には変換がない)。`d_req_cancel`は0 |
| Mでの答え | `dc_hit` = 前のサイクルにLSUのEのロードをD$が受け、かつ`d_hit_now` |
| フィルでの答え | D$の順どおりの答え。すぐLSUに渡すか、LSUのフィルのバッファがふさがっている間はLQのエントリごとに持っておく(データはLUTRAM) |
| 順のキュー | 8エントリ(D$の`ROB_DEPTH`、それ以上は受けない): ロードかストアか、LQのエントリ、答えがまだ要るか |
| 保留のロード | LQのエントリごとに、ビットと語のアドレス(LUTRAM)。Eから何も来ないとき、番号の小さいものから送る |
| 捨てる答え | Mでヒットしたロードの答え。または、**同じLQのエントリが新しい要求を出した**とき(そのエントリに持っていた答えと保留の要求も) |

- **新しい要求で古い答えを捨てる理由**: Mで終わらなかったロード(アドレスのない古いストア、部分的な重なり、回復)はLSUがやり直し、その間に古いストアがD$に入ることがある。古い答えは(順なので)先に来て、そのストアを含まない。新しい要求を待っているエントリに渡せば、古い値になる。
- **LSUの`dc_kill`は使わない**: 同じ規則が、ロードがD$にある間に解放されたLQのエントリも扱う。そのエントリの次の持ち主は、フィルを待つ前に要求を出し(これで古い答えが捨てられる)、それまでLSUはそのエントリへのフィルを受けない。バグ注入で、`dc_kill`で捨てるのは冗長とわかった(17.3)。

### 17.3 検証

- **`tb_iqpl`**: 乱数の書き込み(1サイクルに最大2つ、違う2つのエントリへ、読まれているエントリに寄せる)と、1サイクルに3つの許可を、配列と照合。4つのシードですべてPASS(それぞれ120万回の読み出し。うち218,000回はエントリが書き直されるサイクルでの読み出し、書くスロットが変わったのは266,000回)。

### 17.4 組み立てのときに残る点

1. **ヒットの経路のタイミング。** D$のタグRAM → ヒット → `d_hit_now` → LSUのM(フォワードの選択、整列) → `wb_data`、および → `ld_cancel` → 発行キューの次の状態。mmRISC-2の最長経路はすでにタグRAM → ヒット → `rob_data`(12段、+4.4 ns)で、LSUのMは13段(+6.265 ns)。最初の部分は`OOC_LSUDC`で測る。50MHzに入らなければ、直し方は結果を見て決める。
2. `d_resp_error`を報告しない(ロードのバスエラーはアクセス例外になるべき)。`STORE_ACK_LIMIT`より下では、メモリがエラーを返すことはない。
3. `MEM_BASE`より下(周辺)のロード: LSUは8バイトの語を投機的に読む。周辺はその大きさで、先頭でだけ読まなければならない(コアを組むときに、LSUとROBで)。
4. LSUの`dc_kill`はそのとき外せる。

- **ペイロードは711 LUT**: LUT RAM 384(2バンク × 読み出し3 × 96ビット、数えたとおり)と論理327で、論理はほとんどが3 × 96のバンクの選択。見積り(0.4k〜0.7k)をわずかに上回る。Wに比例し、1ビットあたり約7.4 LUT。
- **アダプタは227 LUT**で、見積り(0.3k〜0.6k)を下回った。このハーネスのLSUは3,004(単体では2,969、11.8): `dc_kill`とフィルの入力につながる部分の最適化が少し違う。

- コアを組むときに書き出しの経路が邪魔になれば、`dc_st_ready`をD$のレジスタの状態から作れる(ストアの書き出しが1サイクル遅れる)。モデルの上では費用はない(ストアはコミットのあとに書き出す)。

## 18. 制御の1つ目: ブランチマスク、ディスパッチ、回復(Phase 1の手順2、2026-10-27)

まだ書いていなかった最後のブロック(`Doc/UARCH_J.md` 4.3: ディスパッチ、分岐の解決、リダイレクト、コミットと例外、1.5k〜2.5k)。この1つ目は、どのµopがリネームからディスパッチへ進むか、予測ミスやトラップでどのµopを捨てるか、フェッチをどこから始め直すかを決める。

### 18.1 書く中でわかった、足りなかったもの

1. **予測ミスで発行キューが丸ごと空になっていた**(`flush`)。これでは、まだ待っている古いµopまで失う。選んで捨てる仕組みが要る。選んだのは**ブランチマスク**(チェックポイントごとに1ビット、6): µopは自分より古いチェックポイントを持ち、チェックポイントcの復元は、ビットcを持つµopをすべて捨てる(DSレジスタ、発行キュー、ユニットのパイプラインで)。予測どおりに解決した分岐は、そのビットをどこでも消す。別の方法(各エントリでROBの番号を、先頭からの相対で復元するものと比べる)は比較が多い。
2. **チェックポイントの番号は、ディスパッチではなくリネームで確かめなければならない。** `OOO_RENAME`は与えた番号に次のサイクルでRATを写すので、使用中の番号を取ることになるµopはリネームで待つ(番号の輪は順に使うので、まだ開いているものが1つあれば、後ろが空いていても止まる)。
3. ユニットは、マスクが`kill`に当たる処理中のものを捨てなければならない(発行キューが`iss_bm`を出す)。

### 18.2 ブロック(`RTL/CPU/OOO/OOO_CTRL`)

| 部分 | 内容 |
|---|---|
| D2(リネーム) | `r_go`: 出されたµopのうち、いまリネームする先頭からの並び: DSレジスタが空いているか出ていく、レジスタが空いている(`OOO_RENAME`のready)、回復がない、チェックポイントを取るµopならその番号が使われていない。マスクは生きているチェックポイント(スロット1はスロット0のものも)から、このサイクルに消えるものを引いたもの |
| DS(ディスパッチ) | DSレジスタのµopは一緒に、両方かどちらもなしで出る(`d_go`)。ROB、発行キュー、LQ、SQにすべての分の空きがあるとき。マスク(`d_bmask`)からはこのサイクルに消えるものを引く。チェックポイントを持つµopは表に書く: そのあとのLSUのtailと、そのフェッチブロック |
| 回復 | トラップ(flush_all、トラップベクタから)、次にリプレイ(flush_all、`replay_pc`から)、次に復元(ROBが選ぶいちばん古い予測ミスの分岐: 復元の番号、表のLSUのtailとFTQの番号、`kill` = そのビット、その分岐の正しい次のpcから)。復元したチェックポイントと、それより若いもの(マスクにそのビットを持つ)は空きに戻る |
| 消去 | `clr`: 予測どおりに解決した分岐。ただし、このサイクルの復元で捨てられるものは除く(その番号はまた与えられうる) |

- DSで両方かどちらもなしにするのは、スロット1をスロット0に動かす(ペイロード全体の選択)より簡単。空きがちょうど1つのとき1サイクル損しうる。まだモデルには入れていない。

### 18.3 ブランチマスクつきの発行キュー(`OOO_IQ`)

各エントリはマスク(`disp_bm`)を持つ。`kill`はマスクにそのビットを持つエントリを次の状態で空ける(そのサイクルの選択は変わらない: そのとき選ばれたµopは、`iss_bm`のマスクでユニットが捨てる)。`clr`はビットを消す。`flush`はflush_allだけ。

### 18.4 検証

- **`tb_ctrl`**: µopの乱数の流れ(4分の1が分岐、ロード、ストア)をリネームに出す。テストベンチは`OOO_RENAME`のチェックポイント番号の輪と、ROB(そのサイクルのいちばん古い予測ミスの分岐。ときどきトラップかリプレイ)を演じ、各キューの空きは乱数、解決も乱数で、その割合は500サイクルごとに変える(チェックポイントがときどき尽きるように)。毎サイクル、プログラム順のµopの帳簿と照合する: `r_go`、`ds_valid`、`d_go`、すべてのマスク(未解決の古い分岐とちょうど同じ)、`live`、`kill`、`clr`、復元の番号・tail・FTQの番号、リダイレクトのpc。4つのシードでPASS(それぞれ400,000サイクル: リネームした約207,000µop、復元6,600回、フラッシュ2,000回、チェックポイント番号での停止4,000回)。
- **マスクつきの`tb_iq`**: 開いている番号をプログラム順に持ち、µopはそれをマスクとし、ときどき1つ開く。killはそのサイクルにディスパッチなしで(`OOO_CTRL`が出すとおり)、消去もある。`iss_bm`を確かめる。6つのシードでPASS(1回の実行で約6,000回のkillと39,000回の消去)。
  - **`tb_iq`自身の穴が見つかった**: 乱数のデスティネーションのタグが、同じ組の古いµopが読むタグになりえた(若いµopへの依存)。killがなければ、2つは次のフラッシュまで互いを待っていた。killでそれが見えた。直したので、発行キューは1回の実行で100,000ではなく約278,000µopを発行する。
- **バグ注入**: 11件を加えた(`OOO_CTRL`に9件、`OOO_IQ`のマスクに2件)。すべて検出(合計191件)。

## 19. 制御の2つ目: 非投機のµop、コミット、FTQのpop(2026-10-27)

18.7の1と2。

### 19.1 したこと

| ブロック | したこと |
|---|---|
| `OOO_IQ` | エントリごとに非投機のビット(`disp_ns`: CSR、システム、AMO / LR / SC、cbo.zero)。そのエントリは、`ns_ok`があり、それより古い非投機のエントリがキューにないときだけ選べる(先頭のものがいちばん古い)。`iss_ns`でそれが出たことを知らせる。この条件はレジスタの状態と`ns_ok`だけで、wakeup-selectのループには載らない |
| `OOO_CTRL` | `ns_ok` = ROBの先頭がまだ実行していない非投機のµop(`head_ns`)で、その先頭になってから1つも出ていない(発行したCSRが実行している間も`head_ns`は立ったまま)。コミットの後始末: 古い割り当てをフリーリストへ(`free_*`)、LQ / SQの数。FTQのpop: いちばん新しくコミットしたµopのブロックより前のブロックを、1サイクルに2つまで。リプレイのあとはそのブロックも。トラップやリプレイのあと、後段は1サイクル遅れてフラッシュ(下) |
| `OOO_ROB` | ペイロードにµopのフェッチブロック(`disp_ftq` → `cmt_ftq`、3ビット) |

- **若いものの動きを変えるµop**(CSRの書き込み、FENCE.I、SFENCE.VMA、MRET)は、コミットのあとのリプレイの印つきで完了し、その後ろは取り直す: ROBにある仕組みで、ユニットとの約束であり、新しい論理はない。CSRの読み出しは`ns_ok`だけで足りる。
- **見つかったこと: リプレイが、ロードをコミットするサイクルにリネームをフラッシュしていた。** リネームはコミット状態に戻るが、そのサイクルのコミットはクロックの端でしか入らないので、ロードの割り当て(とフリーリストのコミットした先頭)が失われる。今は、前段はすぐにフラッシュし(`fe_flush`: FTQ、フェッチバッファ、`fe_pc`からフェッチ)、後段は1サイクル遅れてフラッシュする(`flush_all`: リネーム、LSU、発行キュー、ユニット)。その間は何もリネームもディスパッチもせず、ROBはもう空。トラップはそのサイクルに何もコミットしないが、同じ扱いにする。
- **失われる予測器の更新**: トラップやリプレイはFTQをフラッシュする。そのときまだpopしていないブロック(1サイクルに3つ以上のブロックが終わるときだけ)は、更新なしで消える。

### 19.2 検証

- **`tb_ctrl`**はさらに確かめる: `fe_flush`はすぐ、`flush_all`は1サイクル後で、どちらのサイクルにも何もリネーム・ディスパッチ・消去しない。`ns_ok`をbusyビットの自前のモデルと(`head_ns`と発行は乱数)。フリーリストとLQ / SQへの後始末。FTQのpopを、FTQの先頭の鏡と、ブロックがµopごとに0〜2進む乱数のコミットで。4つのシードでPASS(1回の実行で約200,000回のpop)。
- **`tb_iq`**: ALU0だけのµopとLSUのµopの8分の1を非投機にし、`ns_ok`は乱数。そのµopは`ns_ok`があり、キューでいちばん古い非投機のときだけ出る。`iss_ns`も確かめる。4つのシードでPASS(1回の実行で約17,000回)。
- **`tb_rob`**: コミットでのフェッチブロック。PASS。
- **バグ注入**: 9件を加え(`OOO_CTRL`に6件、`OOO_IQ`に2件、`OOO_ROB`に1件)、ROBの3件を書き直した(ペイロードのフィールドがずれた): 合計200件。

## 20. 制御の3つ目: ユニットがマスクで捨てること、DSレジスタのペイロード(2026-10-28)

18.7の3。

### 20.1 したこと

| ブロック | したこと |
|---|---|
| `OOO_STAGE`(新) | ユニットのパイプラインレジスタ1段: valid、ブランチマスク、Wビット。マスクにkillされたビットがあるµopは取り込まない(`in_bm & kill`)か、保持中(`en` = 0: 繰り返しの除算)なら去る。消去されたビットは、取り込むときも保持中もマスクから落ちる。`flush`で空になる。ALUのポートではIS(RR)、RR(EX)、EX(書き戻し)のあとに使う |
| `OOO_DSREG`(新) | DSレジスタのペイロード: 2つのµopのソースのタグ、use・readyビット、ディスパッチが書くほかのすべてのWビット。`ds_load`で取り込み、そうでなければ保持する。readyビットは毎サイクル、発行キューの前のサイクルのwakeupのタグを見張る(レジスタにしたタグどうしの比較で、リネームと発行キューの経路の外) |
| `OOO_LSU` | ポート2のµopはマスク(`iss_bm`)を持ち、EとMでkillされたビット(`kill`)があれば捨てる。古いものは、どのサイクルとも同じように復元を通る。LQから取り直すロードにはマスクがない: 回復のサイクルには始めず、Mのものは待ちに戻す(今までどおり) |
| `OOO_IQ` | wakeupのタグを外へ出す(`wk_valid` / `wk_tag`、6本)。遅れたwakeup(ロード、乗算)は、発行したサイクルにkillかフラッシュされたµopには出さない |
| `OOO_RENAME` | busyビットは、発行キューのwakeupのタグ(`wk_*`、6本)でそのサイクルの端に消す。3つの書き戻しポートではなくなった。同じサイクルに出したレジスタはbusyのまま |
| `OOO_CTRL` | `ds_load`: DSレジスタがリネームのµopを取り込む(空か、そのµopが今出る)。ペイロードのイネーブル |

- **見つけた: LSUは、復元のサイクルに発行された古いµopを失っていた。** どの復元でもEとMのものを全部捨てていた(マスクの前、予測ミスで発行キューが空になったころに書いたもの)。そのサイクルに発行された古いロードやストアは、発行キューがエントリを空けているので二度と完了せず、コアは永遠に待つ。`tb_lsu`は回復のサイクルに発行していなかった。いまは発行する(各µopより古い分岐のマスクつき)。古いコードは2,800サイクルでデッドロックする。
- **見つけた: リネームとディスパッチのあいだで、µopがwakeupを逃しうる。** busyビットは書き戻し(ALUの結果はwakeupの3サイクル後)で消していて、発行キューはµopがディスパッチされるサイクルのwakeupしか取らない。wakeupとその書き戻しのあいだにリネームされたµopはソースをbusyと読み、それを起こすものは二度と来ない。リネームと発行キューを一緒に持つ単体テストはなかった。`Doc/UARCH_J.md` 6.5はbusyビットがwakeupバスに従うことを前提にしていたが、3.4とRTLは書き戻しポートだった。いまはwakeupのあとにリネームされたµopはソースをreadyと読み、DSレジスタがリネームとディスパッチのあいだのwakeupを足す: 取り込んだサイクルのもの(次のサイクルに見る)と、保持しているすべてのサイクルのもの。
- **古いwakeup。** busyビットとDSレジスタがwakeupを取るので、出し直されたレジスタへのwakeupは新しいµopのソースをreadyにしてしまう。発行と同時にkillかフラッシュされたµopのレジスタは、早くても1サイクル後に出し直される: そのときに来うるのは遅れたwakeupだけで、発行キューはもうそれを出さない。外から起こすユニット(除算、AMO)への約束: 生きているµopのためだけ。
- **killのサイクルにユニットがすることは止めない**(`OOO_STAGE`): killされた分岐は何も消去せず(`OOO_CTRL`)、そのレジスタとROBのエントリが出し直されるのはもっとあと(リネームは復元の1サイクル後、ディスパッチは2サイクル後)なので、その書き込みと完了は生きているものに当たらない。
- **消去。** サイクルtで消去されたチェックポイントが次にkillされるのは早くてt + 5(リネーム、ディスパッチ、発行、読み出し、解決)なので、LSUの1サイクルのMに消去は要らない。`OOO_STAGE`は取り込むときも保持中も消去する: はじめ取り込むときの消去を抜いた。そのサイクルに消去されたビットを持って取り込まれ、そのあと保持する段(除算)ではビットが残り、その番号の次の分岐がそれをkillしてしまう(`tb_stage`、M250)。

### 20.2 検証

- **`tb_stage`**(新): 段を、保持しているµopの履歴(取り込み、kill、消去、フラッシュ)と照合。番号は閉じた次のサイクルに出し直し(コアより早い)、保持はまとめて。400,000サイクル、4シード。
- **`tb_dsreg`**(新): リネームのbusyビットを演じる(wakeupのサイクルの端で消す)。毎サイクル、保持しているµopのすべてのソースは、その生産者がこのサイクルより前にwakeupしたときにちょうどreadyでなければならない: 発行キューはディスパッチのサイクル自身のwakeupを取るので、それが要るもの。組の中のソース、20サイクルまでの保持、リネームの数サイクルから40サイクル後のwakeup。300,000サイクル、見張りでreadyになったソース162,492、4シード。
- **`tb_lsu` / `tb_dcad`**: 分岐はチェックポイントの番号を持ち、発行されるµopはそれより古い未解決の分岐のマスクを持ち、復元はその番号をkillし、回復のサイクルにも発行する: 分岐より若いものはSQに書かず完了もせず、古いものはどのサイクルとも同じように進まなければならない。
- **`tb_iq`**: 6本のwakeupバスを毎サイクルバスごとに照合(発行と同時にkillかフラッシュされたµopの遅れたものはない)。**`tb_rename`**: 6本のwakeupバスがbusyビットを消す。**`tb_ctrl`**: `ds_load`はµopがリネームされるときに1、DSレジスタが出ないµopを保持しているあいだは0。
- **バグ注入**: 新しく19件(M233〜M237、M240〜M253)、M38を書き直し。すべて検出。
- **確かめていないこと**: 復元でMの古いロードを待ちに戻すこと(以前のLSUのしかた)は値の誤りではなく、遅れてコミットのあとのリプレイになるだけで、テストはそれを受け入れる。その注入はリストに入れていない。

## 21. 制御の4つ目: フロントエンドの復元(2026-10-28)

18.7の4。

### 21.1 したこと

| ブロック | したこと |
|---|---|
| `OOO_FERS`(新) | サイクルRにリダイレクトの地点をレジスタに取り(復元: チェックポイントの表からのブロック、分岐を解決したポートの最後のパーセル、結果、call / return。トラップかリプレイ: ROBからのそのµopのブロックと最後のパーセル)、R + 1にそのブロックのFTQのエントリを読み、`OOO_FETCH`に再開を渡す: `fe_pc`、ブロックの履歴、地点までのスロットの分岐(それより前はnot taken、地点自身のスロットはその結果。トラップとリプレイは前のものだけ)、RASのスナップショット、地点自身のpush(callの次のパーセル)かpop |
| `OOO_FETCH` | `be_stop`(サイクルRの制御のリダイレクト): そのサイクルは要求もブロックも出さない。再開はR + 1の`be_redirect`で来る |
| `OOO_CTRL` | `restore_port`: 復元する分岐のALUポート(`fe_pc`の選択にも使う) |
| `OOO_ROB` | `rcv_ftq` / `rcv_end`: トラップ(先頭)かリプレイ(印のついたµop、先頭かその次)が戻るµopのブロックと最後のパーセル |

- **解決の1サイクル後に再開する**(D-15、作者の確認待ち)。履歴は、最初のフェッチがそれで表を読む前にTAGEのレジスタになければならない。解決から直接だと、分岐の比較、ROBのいちばん古い予測ミスの選択、制御、チェックポイントの表、FTQの読み出し、履歴へのpush、TAGEのブロックRAMのアドレスが1サイクルになる。R + 1のリダイレクトは予測ミスごとに1サイクル: モデルで−0.27% / −0.22% / −0.26%(-O2で6.260 → 6.243 CoreMark/MHz。千命令あたりの予測ミス1.44)。予測ミスはEXからEXまで10サイクル。
- **フロントエンドは今までどおりすぐ止まる。** 再開まで走り続けると、間違った道のブロックがR + 1にフェッチバッファかFTQ(Rで復元済み)に入り、リネームされうる。`be_stop`で両方を空に保つ: 要求もブロックも出さず、飛んでいるものは再開が捨てる。
- **µopのブロックは、その後ろ半分のブロック。** プリデコードは2つのラインにまたがる命令を、スロットと予測ごと2つ目のブロックに置き、フェッチバッファは前半のブロックを渡す。デコードは後段に2つ目のブロック(またがるときは+1)を渡さなければならず、チェックポイントの表、ROB(`disp_ftq`、FTQのpop)、復元はそれを使う。
- **テストで見つけた: トラップは分岐の上でも起こる**(そこにデバッグトリガ): トラップは分岐より前なので、そのスロットを履歴に入れてはいけない。解決した転送だけがスロットのパーセルで終わると思っていた。`tb_fers`はどの命令でもトラップを起こし、地点のスロットはいまは復元のときだけ数える。
- **簡単にした**: 地点より前のスロットの分岐は「予測どおり」ではなくnot takenで入れる: takenと予測したものがあれば、地点より前でブロックが終わっていたので、そこの予測はいつも0(「予測どおり → 0」のバグ注入は検出できなかった。入力をなくした)。
- **FTQの読み出しポート**: 3つ目(解決用)はR + 1の復元が使う。予測ミスを見るのに解決が要るjalrの予測先は、µopと一緒に運ぶ(ペイロード)か、4つ目の読み出しが要る: 組み立てのとき。

### 21.2 検証

- **`tb_fers`**(新): 命令から作るブロック(スロットの分岐はtakenと予測されるまで硬貨で予測しそこでブロックが終わる、スロットより後の分岐、call、return、ほかのjalr)、入れ替わる8つのFTQ。ブロックのどの命令でもリダイレクト(ポート0か1での予測ミスした転送の復元、もう一方は乱数。どの命令でもトラップかリプレイ)、2サイクル続けて起こすことも多い。次のサイクル: 読むブロック、pc、履歴、スロットの結果、RASのスナップショット、push / popとpushのアドレス。400,000サイクル、リダイレクト200,321、4シード。
- **`tb_fetch`**: 後段は、コアと同じく再開の1サイクル前にフェッチを止める。止めたサイクルとリダイレクトのサイクルには要求もブロックもない。11プログラム。
- **`tb_rob`**: すべてのトラップとリプレイで`rcv_ftq` / `rcv_end`。**`tb_ctrl`**: すべての復元で`restore_port`。
- **バグ注入**: 新しく13件(M254〜M266)、M128を書き直し(その行はいま`stop`で止める)。232件すべて検出。
