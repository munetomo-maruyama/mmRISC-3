# Phase 0-4: 融合構成のRTLブロックと、単体合成(OOC)の準備

- 実施日: 2026-10-24
- 目的: `ISSUES_J.md` 5章の手順3。融合構成(`Doc/STRATEGY_J.md` 4章)の中で、1サイクルに閉じる必要があるループと、構成を決めるコストを持つブロックをRTLで書く。単体で検証し、規模とタイミングを測る。タイミングの確定は作者のVivadoで行う
- 作業ファイル: `RTL/CPU/OOO/`(RTL)、`SIM/OOO_UNIT/`(単体テストとバグ注入)、`FPGA/OOO_OOC/`(VivadoのOOC合成、Yosysの見積り)

---

## 1. 結論

1. **融合構成の6ブロックをRTLにし、単体テストとバグ注入で検証した**。ブロックは2段ALU、融合、発行キュー、リネーム、物理レジスタ、uBTB。Verilatorの`-Wall`でlintは0件、6本の単体テストはすべてPASS、わざと入れた21件のバグはすべて検出された。
2. **融合のRTLはモデルどおりに組を作る**。CoreMarkの命令列を4命令の窓で流すと、`-O2`でモデルの組の99.99%(415,297 / 415,337)、最大最適化で411,999 / 412,000を作った。µop / 命令もモデルと同じ0.867 / 0.853。4命令の窓の端と、ロード / ストアのペアを静的なオフセットで判定することによる損失はない。
3. **テストで見つかったもの**:
   - RTLのバグ1件: リネームのチェックポイント番号が、無効なµopの要求でも進んでいた。
   - 書き方の問題: 実行時の値で添字を選ぶ表を、packedの多次元配列で書いていた。Yosysでは数万LUTの論理になっていた。表を配列にし、レジスタファイルのバンクを書き込みポートごとの配列にして直した(リネーム 57k → 9.2k、発行キュー 47.7k → 15.6k、レジスタファイル 94k → 4.9k + LUTRAM、YosysのLUT数)。
   - テストの穴1件: x0がゼロを返すかを、メモリの初期値0に頼って見逃していた。リセットのない状態をすべてランダムな値で始める方式にして塞いだ。
4. **最大の発見: レジスタファイルのポートが、資源の最大の項目になる**。融合した組がソース3本・書き込み2本を使うと、読み出し8〜9・書き込み5〜6ポートになる。Yosysの見積りではLUT + LUTRAMで1.7万〜1.9万となり、OoO本体の予算(16〜18k)をそれだけで使い切る。モデルで振ると、**融合する組をソース2本までに制限しても−1.7% / −1.1%**(読み出し6ポートで済む)。書き込みを1本までにすると−4.4% / −9.1%と高くつく。
5. **推奨(G0で確定)**: 融合する組はソース2本まで(読み出し6ポート)。書き込みは5ポート(組あたり2本)を基本とし、Vivadoでレジスタファイルが重すぎれば3ポート(組あたり1本)に下げる。どの組み合わせでも、モデルでは`-O2` 6.6〜6.9、最大最適化 6.9〜7.5で目標を超える。
6. 次は作者のVivadoでのOOC合成(6章)。2段ALUのタイミング、発行キューの規模、レジスタファイルの各ポート構成のLUTとタイミングを確定させる。

## 2. 作ったブロック

| ブロック | 内容 | 主なパラメータ |
|---|---|---|
| `OOO_ALU` | 整数ALU: RV64I + Zba / Zbb / Zbs / Zicond(mmRISC-2のCORE_EXUと同じ操作と符号) | — |
| `OOO_ALU2` | 発行ポートのALU: OOO_ALUを2段直列(融合したALU + ALUを1サイクル)+ 分岐の比較(単独、またはALU + 分岐で1段目の結果と) | — |
| `OOO_FUSE` | デコードした4命令から次の2 µopを作る(古い順に貪欲に組む) | `LEVEL`(1〜3) |
| `OOO_IQ` | 統合発行キュー: ソース3、2入 / 3出、wakeup-select 1サイクル、age matrix、レイテンシ2と外部のwakeup | `N`=16、`TAGW`=7 |
| `OOO_RENAME` | 2 µop / サイクル、ソース3・デスティネーション2、RAT、フリーリスト、busy、組の中の依存、チェックポイント | `NREG`=96、`NCKPT`=8 |
| `OOO_PRF` | 96 × 64、書き込みバンクごとのLUTRAM + LVT | `NW`、`NR` |
| `OOO_UBTB` | 32エントリの全連想next-line予測、1サイクルで次のフェッチアドレス | `NE`=32 |

OOC合成のための登録ハーネス(`FPGA/OOO_OOC/rtl/OOC_WRAP.sv`)は次のとおり。`OOC_ALU2`は、結果レジスタからバイパス(5入力)を経て2段ALUに戻る1サイクルのループをそのまま作る。`OOC_FUSE`、`OOC_PRF`、`OOC_RENAME`は入出力をフリップフロップで挟む。

## 3. 検証

| テスト | 方法 | 結果 |
|---|---|---|
| `tb_alu2` | 仕様から書いた参照(RV64I / Zba / Zbb / Zbs / Zicond)と、操作・オペランドの選び方・値(端の値に寄せる)をランダムに | 2,000,000件、不一致0 |
| `tb_fuse` | 規則の参照とランダムに。加えてCoreMarkの命令列を窓で流してモデルと比較 | 1,000,000組、不一致0。組の数はモデルの99.99% |
| `tb_prf` | 1サイクルに異なるレジスタへ最大5書き込み、8読み出しを配列と照合 | 2,400,000読み出し、不一致0 |
| `tb_rename` | 参照(RAT、フリーリスト、busy、チェックポイント)と、コミット・書き戻し・誤予測による復元を含めて照合 | 400,000サイクル、596,069 µop、復元25,489回、不一致0 |
| `tb_iq` | 値が使える時刻をキューとは独立に追い、「準備のできた最も古いµopが各ポートで発行されること」を毎サイクル照合(wakeupの時刻、連続発行、古い順、空きポートを残さないことを同時に確認) | 300,000サイクル、114,649 µop、フラッシュ147回、不一致0 |
| `tb_ubtb` | 参照の表と、更新・リダイレクト・停止をランダムに | 500,000サイクル、不一致0 |
| `mutate.py` | RTLを1行ずつわざと壊す21件(各ブロック2〜4件)。各行の結果を読む | **21件すべて検出**(NOT DETECTED / NOT APPLIEDなし) |

テストを書いているうちに、テストベンチ側の誤りも4件見つかって直した(参照の12ビットのマスク、Verilatorでリセットの立ち下がりが辺にならない、クロック後に出力を読んでいた、ソースが待っているタグの再割り当て)。いずれもRTLのせいではないことを、1サイクルずつ追って確かめてから直した。

## 4. 規模の第一見積り(Yosys、`FPGA/OOO_OOC/output/yosys_size.txt`)

Yosys(`synth_xilinx`)の値。**Vivadoとの比はモジュールごとに0.4〜1.4倍と大きく違い**(`REDUCE_J.md` 3章。mmRISC-2のCORE_EXUは0.44倍)、遅延は出ない。そのため、規模の目安と、ブロック間の比較にだけ使う。

| ブロック | LUT | LUTRAM | FF | 最長経路(セル数) | 読み方 |
|---|---|---|---|---|---|
| OOC_ALU2(2段ALU + バイパス) | 8,225 | 0 | 682 | 1,423 | CORE_EXUの比0.44を当てると約3.6k。経路のセル数が多いのは、clz / ctz / cpopの64段のループ(mmRISC-2と同じ書き方)をYosysがそのまま並べるため。VivadoはmmRISC-2で同じ書き方を50MHzに収めた |
| OOC_FUSE | 207 | 0 | 158 | 22 | 小さく、浅い |
| OOC_RENAME | 9,168 | 0 | 2,884 | 146 | FFの多くはチェックポイント(8 × 224ビット) |
| OOO_IQ | 15,595 | 0 | 1,056 | 713 | **大きい**。Vivadoでの確認が必要。下げる手段は7章 |
| OOO_UBTB | 5,041 | 0 | 2,635 | 390 | 32エントリの全連想。モデルではuBTBなしでも−0.9%なので、重ければ外す |
| OOC_PRF 書き3 / 読み8 | 4,936 | 3,456 | 976 | 24 | |
| OOC_PRF 書き5 / 読み8 | 11,006 | 5,760 | 1,216 | 30 | |
| OOC_PRF 書き6 / 読み9 | 12,009 | 6,912 | 1,359 | 29 | 融合構成をそのまま実装した場合 |
| **OOC_PRF 書き3 / 読み6** | 3,600 | 2,304 | 834 | 21 | ソース2本・書き込み1本に制限 |
| **OOC_PRF 書き5 / 読み6** | 6,899 | 3,840 | 1,074 | 24 | ソース2本に制限(推奨の基本形) |

- レジスタファイルのバンクには`ram_style = "distributed"`を付けた。付けないと、読み出しアドレスがレジスタのときにツールがブロックRAMを選び、RAMB36を24個使った(空きは26.5タイルしかない)。
- RAM64M(4 LUTで64 × 1ビット、3読み出し)から見積もると、Vivadoでのレジスタファイルは、書き3 / 読み6で約4k、書き5 / 読み6で約6.5k、書き6 / 読み9で約11.5k LUTになる(LUTRAMを含む)。

## 5. レジスタファイルのポートと性能の取引(サイクルモデル)

`Plan/model`の`ooo`(`fuse_2src`、`fuse_1w`を追加)。CoreMark/MHz。

| 融合の制限 | `-O2` | 最大最適化 | 読み / 書きポート |
|---|---|---|---|
| 融合なし | 6.07 | 6.57 | 6 / 3 |
| 融合(制限なし) | 7.06 | 7.59 | 8〜9 / 5〜6 |
| **ソース2本まで** | **6.94**(−1.7%) | **7.51**(−1.1%) | **6 / 5** |
| 書き込み1本まで | 6.75(−4.4%) | 6.90(−9.1%) | 8〜9 / 3 |
| ソース2本・書き込み1本まで | 6.62 | 6.87 | 6 / 3 |
| ALU + 分岐まで・ソース2本・書き込み1本 | 6.37 | 6.83 | 6 / 3 |

ソースの制限はほとんど性能を落とさずに読み出しポートを3分の2にでき、書き込みの制限は最大最適化で9%落ちる。そのため、**ソース2本までを採用し、書き込みポートはVivadoの結果で決める**のが妥当と判断した。

## 6. 作者にお願いするVivadoの実行

```
cd FPGA\OOO_OOC
synth_ooo.bat
```

`OOC_ALU2`、`OOC_FUSE`、`OOC_RENAME`、`OOO_IQ`、`OOO_UBTB`と、レジスタファイル5構成(書き3 / 読み8、書き5 / 読み8、書き6 / 読み9、書き3 / 読み6、書き5 / 読み6)を、50MHz、配置配線までOOCで実行する。結果は`output\<top>\summary.txt`(LUT、WNS、レジスタ間の余裕と論理段数)と、`timing_reg2reg.rpt`。

| 結果 | それで決まること |
|---|---|
| OOC_ALU2のレジスタ間の余裕 | 2段ALUの連結(chain = 1)が50MHzで閉じるか。閉じなければ、2段目の操作を絞る(clz / ctz / cpop / 回転 / orc.b / rev8は融合の2段目に現れない)か、ALU + ALUの融合を外して、ALU + 分岐とアドレス計算 + ロードに絞る(`MODEL_J.md`、融合2: −6%) |
| OOO_IQのLUTと余裕 | wakeup-selectが1サイクルで閉じるか、規模が予算に入るか |
| OOC_PRFの5構成のLUT | 書き込みポートの数(D-4の細目) |
| OOC_RENAME、OOO_UBTB、OOC_FUSE | 1サイクルで閉じるか。uBTBは重ければ外す |

## 7. 次の作業

1. 作者のVivado結果を受けて、D-4の細目(ソース2本、書き込みポート数、2段目の操作)を決め、`OOO_FUSE`に制限を入れる(ソースの数え方は`Plan/model/ooo.h`の`fuse_2src`と同じにする)。
2. 発行キューが大きすぎた場合の手段: 発行するµopの読み出しを、番号に符号化してから選ぶ方式からone-hotのAND-ORにする。wakeupのタグバスを減らす(ポート1はレイテンシ2のµopを出さないので遅延側のバスは要らない。デスティネーション2本はALUポートだけ)。キューを分割する(ALU 12 + LSU 6など)。
3. G0の仕様書: このRTLの範囲を含めたマイクロアーキテクチャの凍結(`ISSUES_J.md` 5章の手順5)。
