

### 29.97 手順1.8 K1: PMUのイベント、設計(2026-11-21)

作者の指示(「Start K1」)。29.96で言ったとおり、まずイベントの一覧と番号を作り、作者が確認する。

**今あるもの**: `CORE_CSR`(mmRISC-2のもの、その`CPU_CORE_SPEC.md`の決定69)はPMUを全部持っている: mhpmcounter3からの`HPM_COUNTERS`個のカウンタ(G0b L1からここでは2つ、`Doc/UARCH.md` 6.3)、それぞれのmhpmevent(5ビットのイベント番号。SscofpmfのOF / MINH / SINH / UINH)、mcountinhibit、mcounteren / scounteren、scountovf、オーバーフロー割り込みLCOFI(13、委譲できる)、Smcntrpmf(mcyclecfg / minstretcfg)。コアはイベントとサイクルごとに1ビットを渡し(`hpm_ev`)、`CORE_CSR`がレベルと一緒に一度レジスタに入れて(`hpm_ev_q`)、1サイクル遅れで数える。`OOO_CORE`は`hpm_ev`を0に固定している。ロックステップはカウンタとmhpmeventの読み出しですでにコアの値を取る。SpikeのISA文字列にはSscofpmfとSmcntrpmfがある。I1でSpikeはコアが取った割り込みを取るようになった。

**4ワイドのコアに要るもの**: 1サイクルに最大4µopをリネーム、ディスパッチ、コミットする(命令では8、融合したペアは2と数える)ので、イベントとサイクルごとに1ビットでは数えられない。**`hpm_ev`をイベントごとの数にする**(`HPM_EVW` = 4ビット、0〜8)。カウンタは選んだイベントの数を足し(minstretが`instret_inc`を足すのと同じ)、OFは加算の桁上がりで立てる(すべて1を通らずに一周することがある)。`CORE_CSR`のPMUのほかは変えない。

**リネームでのスロット**: 1サイクルにリネーム(D2 → DS、`OOO_CTRL`が`r_go`を決めるところ)のスロットが4つあり、各スロットはちょうど1つの分類に入る:
- **使用**: リネームしたµop(`r_go`)。
- **回復**: リストアまたはトラップ / リプレイ(`restore_k`、`fe_flush`)から、リネームが再びµopを取るまでのサイクルで、使わなかったスロット(リダイレクト後のフロントエンドの再充填はここに入る、Top-Downと同じ)。
- **バックエンド**: それ以外で、出されたのにリネームしなかったµop(`r_valid`から`r_go`を引いたもの: ディスパッチがROB、キュー、LQ / SQを待ってDSレジスタが満杯。物理レジスタまたはチェックポイントの不足)。
- **フロントエンド**: それ以外で、µopが出されなかったスロット。

どの実行でも足すと4 x サイクル(ベンチで検査)。リタイアしたµopと合わせてTop-Downの第1レベルになる: リタイア = リタイアしたµop、誤投機 = リネームしたµop − リタイアしたµop + 回復、フロントエンド、バックエンド。2026-11-05からの尺度であるCoreMark/MHzがどこで失われているかが分かる。

**イベント**(番号はmhpmeventで選ぶもの。**太字**: mmRISC-2と意味が同じなので、そのスクリプトとデバイスツリーのrawイベントがそのまま使える):

`HPM_EVENTS`は31。mmRISC-2の11(MAがD$を待つ)、12(フロントエンドが空)、13(ロードユース)、14(MDU / FPU)、17(バックエンドが詰まる)、20〜26、29はインオーダーのパイプラインの段の意味だった。ここではOoOコアで代わりにあるもの(11 / 14はROBの先頭、12 / 17 / 20 / 21はリネーム、23〜26 / 29はバックエンドの理由)。

**数の行き先**: 各イベントは起きるところで作り、そこでレジスタに入れ(スロットの分類ごとに3ビットの数、4つのポップカウント)、その後は前と同じく`CORE_CSR`の`hpm_ev_q`: 2サイクル遅れ。CSR命令はROBの先頭で非投機に実行するので、2回の読み出しの差は正確。コアの外からの4つの入力(7、8、18、19)は`OOO_CPU`から来る。`tb_core`のモデルがそれを駆動する(7、8は`ICacheModel` / `DMissModel`から。18、19はコアのベンチでは0、`OOO_CPU`のベンチでは本物)。

**テスト**:
- **毎サイクルのベンチの検査**(`tb_core`): 12 + 17 + 20 + 21 = 1サイクルに4。2と22をベンチが見るコミットと。3 / 4をリタイアするのが見えるロードとストアと。15 / 16をトラップと。最後に、ベンチが自分で数えられるものは各イベントの合計をそれと。
- **`b4/dir/pmu.S`**(新規): 既知のコード片の前後でmhpmcounter3と4に各イベント(2〜4と22は正確に、残りは範囲で)。MINH / SINH / UINHとmcountinhibit。終わり近くに書いたカウンタ: OF、MでのLCOFIとSへの委譲、scountovf、OFのクリア。mcounteren / scounteren(SやUでのhpmcounterの読み出しがトラップ)。mcycle / minstretのSmcntrpmfのフィルタ。ロックステップ: scountovfの読み出しはコアの値を取る(カウンタと同じ)。
- run_core、CoreMarkは不変(サイクル単位で: イベントは何を実行するかを変えない)、ユニットの回帰。各イベントと数についてのミューテーション(桁上がりを失う、多数を1と数える、レベルのフィルタ)。

**OpenSBIとperf**(29.76の癖: Smcntrpmfはある。デバイスツリーのイベント1 / 2を固定カウンタに、rawイベントをmhpmcounter3 / 4に。OpenSBIの停止 / RESETのパッチ、mmRISC-2の`LitexSystem/software/boot/opensbi_patches/0001`): ベンチにOpenSBIが要り、それはL1が持ってくる。Linuxの`perf stat`の前に、そこで`pmu-sbi`のようなペイロードで確かめる。

**コスト**: `CORE_CSR`で+1の代わりに数を足すことと、2つのカウンタそれぞれに4ビットの31方向の選択、`hpm_ev_q`のFF 124。`OOO_CORE`のイベントのロジックとレジスタ(リネームとコミットのポップカウント、回復のフラグ): **LUT約+0.4k、FF約+0.2k**(29.76の計画は+0.3k)。タイミング: どのイベントも作るところでレジスタに入れるので、コアの経路はレジスタのファンアウト以外長くならない。
