# Phase 1のステップ4: 整数コアの組み立て(G1までの計画)

[English](CORE.md)

- 日付: 2026-10-29
- 目的: `Doc/UARCH_J.md` 8章のステップ4。`RTL/CPU/OOO`と`RTL/CPU/CORE`のブロックは書け、単体でテストされ、Vivadoで測られている(`Plan/OOC_J.md` 1〜25)。この計画はそれらを整数のアウトオブオーダーコア(Mモード、ベアメタル、`Doc/STRATEGY_J.md`のPhase 1)に組み立て、**G1**まで立ち上げる。`Plan/OOC_J.md`と`Doc/UARCH_J.md`に残した「組み立てへの約束」を1か所に集め、まだ書くものと、その順を言う。

## 1. コアのトップ(`OOO_CORE`)

```
            +---------------------------- フロントエンド ---------------------+
  I$ <----> | OOO_FETCH (uBTB, PREDEC, TAGE, BTB, RAS) --> OOO_FTQ            |
            |      |  be_stop / be_redirect <-- OOO_FERS <-- FTQ (rsポート)   |
            |      v                                                          |
            |   OOO_FBUF --> OOO_DEC x4 --> OOO_FUSE (µop 2つ)               |
            +--------------------------------|--------------------------------+
                                             v
   D2  OOO_RENAME  <--- r_go --- OOO_CTRL (マスク、進行、回復、コミット、ns_ok)
                                             |
   DS  OOO_DSREG (ペイロード、readyの見張り) ---> OOO_ROB、OOO_IQ + OOO_IQPL、OOO_LSU (LQ / SQ)
                                             |
   IS  OOO_IQ: ポート0 (ALU0、CSR、MUL、MDU、システム)、ポート1 (ALU1)、ポート2 (LSU)
   RR  OOO_STAGE + OOO_PRF (読み出し6) + OOO_IQPL (読み出し3)
   EX  ポート0: OOO_ALU2 (フル) / OOO_CSRU / OOO_PMUL / OOO_MDUP / OOO_SYS
       ポート1: OOO_ALU2 (FULL = 0)      ポート2: OOO_LSU (E、M) -- OOO_DCAD -- D$
   WB  レジスタファイルの書き込み3つ(ポート0、ポート1、LSU)、OOO_ROBへの完了
   CM  OOO_ROB (1サイクルに2つ) -- OOO_TRAP (例外、割り込み、MRET) -- CTRL (フリーリスト、LQ / SQ、FTQのpop)
```

| ブロック | 個数 | 何か(`Plan/OOC_J.md`の章) |
|---|---|---|
| `OOO_FETCH` | 1 | uBTB、プリデコード、TAGE-S、BTB、RASつきのF0〜F2(14)。`be_stop`(21) |
| `OOO_FTQ` | 1 | 16ブロック(D-18)、それぞれフロントエンドの状態312ビット(TAGE 270、RAS 42)(13、21) |
| `OOO_FERS` | 1 | フロントエンドの復元(21) |
| `OOO_FBUF` | 1 | 4ブロック、4命令を出す(13) |
| `OOO_DEC` | 1(4スロット) | スロットごとにCORE_DECOMP + CORE_DEC(16) |
| `OOO_FUSE` | 1 | 4命令 → µop 2つ、レベル2(7、16) |
| `OOO_RENAME` | 1 | レジスタ64、チェックポイント6、busyビットはwakeupで消す(10、20) |
| `OOO_CTRL` | 1 | ブランチマスク、進行、回復、ns_ok、コミットの後始末、FTQのpop(18〜22) |
| `OOO_DSREG` | 1 | DSレジスタのペイロード、readyの見張り(20) |
| `OOO_ROB` | 1 | 24 µop、完了ポート4つ(12、19、21、22) |
| `OOO_IQ` + `OOO_IQPL` | 1 + 1 | 10エントリ、発行3つ。ペイロードの記録(15、17、23) |
| `OOO_PRF` | 1 | 64 × 64、書き込み3 / 読み出し6(9) |
| `OOO_STAGE` | 6〜8 | ポートのパイプラインレジスタ(RR、EX、WB)(20) |
| `OOO_ALU2` | 2 | ポート0はフル、ポート1は`FULL = 0`(8。L7: `Doc/UARCH_J.md` 6.12) |
| `OOO_CSRU` | 1 | CORE_CSR(HPMカウンタ2つ)(23) |
| `OOO_PMUL`、`OOO_MDUP` | 1 + 1 | mul / mulwはパイプライン。残りはCORE_MDU(23、24) |
| `OOO_SYS`、`OOO_TRAP` | 1 + 1 | システムのµop。例外と割り込み(22、23) |
| `OOO_LSU` + `OOO_DCAD` + `DCACHE` | 1 + 1 + 1 | LQ / SQ 8、アダプタ、mmRISC-2のD$(11、17) |
| I$ | 1 | 16バイトに広げたmmRISC-2のICACHE(まだこのリポジトリにない)、またはモデル(5章) |

## 2. ブロックのあいだの形式

### 2.1 融合からディスパッチまでのµop

リネームとDSレジスタが2つのµopそれぞれについて受け取るもの。ほとんどは、`OOO_FUSE`の`u*_slot` / `u*_kind`で選んだ、そのµopの命令のデコードのフィールド(`OOO_DEC`)。

| フィールド | ビット | どこから | どこへ |
|---|---|---|---|
| valid | 1 | FUSE | RENAME、CTRL(`r_valid`) |
| use、src(アーキテクチャ) | 2 + 2 × 5 | ペアの半分ずつのDEC。後半が前半のrdを読むものは除く | RENAME |
| wr、dst | 1 + 5 | 書く方の半分(W1: 多くて1つ) | RENAME、ROB |
| ckpt | 1 | µopに条件分岐かjalrがある(jalは予測ミスにならない) | RENAME、CTRL |
| pc | 38 | FTQのブロックのpc(`rd_pc`) + 前半のパーセル | ROB(`disp_pc`)、pcの配列(3.2) |
| len | 3 | µopのハーフワード数(1〜4) | ROB |
| ftq | 3 | **後ろ半分のブロック**(命令がラインをまたぐときは+1: `Plan/OOC_J.md` 21.1) | ROB、CTRL(`ds_ftq`) |
| exc、cause、tval | 1 + 5 + 64 | デコード: 不正命令(tvalは命令のビット)、フェッチの障害、ECALL(要因はレベルで)、EBREAK | ROB(`disp_exc`)、OOO_TRAPの`tv_*`(ディスパッチのポート) |
| port、lat2、ext_ans、ns、md | 2 + 1 + 1 + 1 + 1 | FUSEの`u*_port`。DEC。`md` = 外から答えるMDUのµop | IQ |
| fused | 1 | `u*_kind` ≠ 0 | ROB(instretで2と数える)、OOO_TRAP(`head_fused`) |
| ld、st | 2 | µopにロード / ストアがある | LSU、CTRL、ROB |
| 記録 | W(2.2) | RRとEXが読むものすべて | IQPL |
| insn ×2 | 64 | 命令のビット(シミュレーションだけ) | トレース(3.9) |

- ディスパッチはIQのエントリに`disp_wr` = キューがwakeupする枠(レイテンシ1か2)で書く、で書く。外から答えるµop(MDUの長いもの、のちにAMO)は`disp_wr` 0でディスパッチし、`ext_*`で起きる。
- スロット1〜3のまれな種類(スロット0だけでデコード)はフェッチバッファのグループを終える: デコードではなく`OOO_RARE`が最初のパーセルから見分ける(`Plan/OOC_J.md` 26: フェッチバッファのループにあったデコードの`cut`は50 MHzに届かなかった)。不正な命令はすべてのスロットで出す。

### 2.2 ペイロードの記録(`OOO_IQPL`、Wビット)

記録はDSで書き、RRでエントリで読む。ポート2は下位W2ビットだけ読む(`Plan/OOC_J.md` 17.1、G0bのG3)。決める配置(17.1で数えたとおり約96ビット。費用はWに比例):

| ビット | フィールド | ポート |
|---|---|---|
| 下位(W2 = 48) | rob 5、lq 3、sq 3、オフセット12、サイズ2、符号1、メモリのコマンド5(ロード / ストア / AMO / cbo)、ペアの種類2(ALU + ロード、ストアのペア)、ALU + ロードの演算6、ftq 3、ckpt 3 | 2(と共通のもの) |
| 上位 | imm 32(ALUの即値、分岐のオフセット)、alu_op 6、a_uw、a_shift 2、a1_sel 2、b1_imm、word_op、is_br、br_op 3、br_fused、br_res1_a、br_o_sel 2、is_jal、is_jalr、call、ret、pred_taken、ブロックの中のオフセット3(pc、3.2)、mdu_op 4、CSRのフィールド(addr 12、op 2、immの選択)またはsysのop 3 | 0、1 |

- pcは記録に入れない(38ビット): RRでpcの配列から来る(3.2)。jalrの予測先はターゲットの配列から来る(3.4)。
- csr_addrは即値と上位ビットを共有する(CSRのµopにはALUの即値がない)。

### 2.3 ROBのディスパッチのフィールド

`disp_pc`、`disp_wr`、`disp_arch`、`disp_new` / `disp_old`(リネームから)、`disp_ld` / `disp_st`、`disp_fused`、`disp_ns`、`disp_len`、`disp_ftq`、`disp_exc` / `disp_cause`。完了ポート(NCMP 4): ポート0の書き戻し、ポート1の書き戻し、LSUのロード、LSUのストア。

## 4. 途中で決めること(推奨。2026-10-29に承認)

| # | 項目 | 推奨 | 理由 |
|---|---|---|---|
| 4.1 | EXでのµopのpc | RRで読み出し2つのpcの配列(FTQのブロックのpc) + オフセット。記録に38ビットは入れない | 10エントリ × 2バンク × 読み出し3に38ビット足すかわりに、小さなLUTRAMの読み出し2つ(数十LUT) |
| 4.2 | PRFに書くとき | 結果が書き戻しのレジスタに入る端(書き戻しのレジスタは次のサイクルのバイパスの入力)。OOO_LSUはそのためにMの結果を出す | 測った4入力のバイパスを保つ。代わりの書き戻しのレジスタの2段目は、ALUのループの5つ目の入力になる。LSUのM → PRFの書き込みの経路は測る(そのMはOOC_LSUDCの最悪の経路、+0.820 ns) |
| 4.3 | OOO_SYSの完了 | ポート0の完了の枠が空いたときに(OOO_MDUPの`slot_busy`の規則) | ROBの5つ目の完了ポートはエントリごとに比較がかかる。システムのµopはまれで、先頭にある |
| 4.4 | ポート2のペア(ALU + ロード、ストアのペア) | 融合を切ってコアを立ち上げ、次にALUポートの種類(lui + addi、auipc + x、slli + srli、ALU + 分岐)を入れ、それから2つのLSUのペアを書き、残す前にモデルでその得を測る | 新しいLSUの論理が要る種類はこの2つだけ |
| 4.5 | jalrの予測先 | RRで読み出し1つのターゲットの配列(FTQのブロックの次のアドレス、8 × 38) | FTQの3つ目の読み出しポートはOOO_FERSのもの |
| 4.6 | 立ち上げのI$ | はじめはモデル(ヒットで2サイクル、OOO_FETCHが期待するとおり)。CoreMarkの前に16バイトに広げたmmRISC-2のICACHE | キャッシュの前にフェッチとデコードを立ち上げられる |

### 5.1 B0: テストベンチ(2026-10-29に完了)

`SIM/CORE`(詳しくはそのREADME): コアのテストベンチのC++の側。コアより先に書いた。

| 部分 | 何か |
|---|---|
| `Memory` | 参照のRAMの領域の上の疎な4 KBのページ。ベンチ自身のELFの読み込み(すべてのシンボル: `tohost`、`fromhost`、シグネチャの範囲)で満たす。コアのポートのモデルが読み書きし、HTIFはフックで書き込みを見る |
| `Htif` | 終了とコンソールは**コミットしたストア**から。`tohost`は**メモリの側**で0に戻す: 0でない値にする書き込みがメモリに届いたとき |
| `TraceSlot` | 3.9のコミットのトレースのポート、サイクルに2スロット: pc、1つか2つの命令、`pair`、トラップと原因、ただ1つの書き込み(`rd`、`rd_val`、`wr_first`: 書き込みが前半のもの、ALU + 分岐)、それぞれの半分のストア。書き込みもストアもしない前半は`rd_skip`になる |
| `Bench` | 命令ごとの`SIM/LOCKSTEP`とのロックステップ、ウォッチドッグ、**アーキテクチャのメモリ**(ELFにコミットしたストアを加えたもの: B4のriscv-arch-testのシグネチャはここから取り、ライトバックのD$の後ろからは取らない)、失敗したときは最後の16コミットを逆アセンブルして出す |

代役のコアでテストした: ベンチのメモリの上の2つ目のSpikeで、`tohost`のページへのストアは、SQとD$の後ろにあるように、キューで0〜24サイクル待つ(フォワーディングつき)。コミットはトレースのポートを通り、サイクルに0〜2スロット、組の書き込み1本が許すところで融合する。riscv-testsの`-p-` 175本とg14のCoreMarkの2ビルドで: すべてが参照と同じ終了コードとコンソールで通り、アーキテクチャのメモリは代役のものと等しく、当てはまったポートの壊し2,019個をすべて検出した(`SIM/CORE/results/standin.txt`)。ベンチへのバグ注入は18の変更をすべて検出した(`SIM/CORE/results/mutate.txt`)。

ここから3つの規則が出た:

1. **`tohost`をポーリングするループは、コアのほうがSpikeより多く回る**(文字のストアがメモリに届くのが遅い)。`SIM/LOCKSTEP`は、カウンタと同じく、`tohost`と`fromhost`のロードにコアの値を参照へ与えるようにした。参照も同じループを回る(CoreMark: そういうロードが2つのビルドで3,667回と6,715回)。
2. **`tohost`のラインをD$に残さない**(B3でD$とともに行う): 本物のライトバックのD$では、コアが自分の文字をいつまでも読み返す。ベンチはそのラインをコアにとってキャッシュしない領域にする(D$のアダプタがそのロードとストアをメモリへ送る。`ifdef`のもとでのベンチのパラメータ)。B1〜B3のポートのモデルはメモリに直接書く。
3. **アーキテクチャのメモリはアドレス変換なしで成り立つ**: ストアは仮想アドレスでコミットする。Phase 2(MMU)でトレースに物理アドレスも加える。

### 5.2 B1: フロントエンドだけ(2026-10-29に完了)

`RTL/CPU/OOO/OOO_FRONT`がフロントエンドをD1 / D2のレジスタまで組み上げる(つなぎ3.8)。`SIM/CORE/tb_front`がそれで実際のプログラムをフェッチ・デコードし、Spikeの経路と照合する(`SIM/CORE/README_J.md`)。

途中で決めたこと:

### 5.3 コミットでのTAGEの更新と、履歴の遅れ(2026-10-29)

B1はモデルより25〜73 %多く条件分岐の予測ミスをする(5.2)。原因がコミットでの更新かどうかを調べた。それは小さな部分で、大半は**フェッチのタイミングで変わる履歴の遅れ**である。

モデルに加えたもの(`Plan/model`、`tagedelay.sh`による`results/tagedelay.txt`):

- `tage.h`: `predict()`と`update()`を分け、更新は予測のときに読んだエントリから計算してエントリを丸ごと書く(OOO_TAGEがコミットで行うこと)。`step()`は変えない(分岐だけで4,404、以前と同じ)。
- `ooo.h`: `upd=1`、各分岐の更新をそのコミットで(+ `upd_lag`サイクル、popの書き込み)。`stale`。
- `tageblk.h`: `delay`、ブロックの更新をその予測のそれだけ後のブロックで(予測は読んだ行から)。
- `model tageref`: **OOO_TAGE自身のアルゴリズム**(`SIM/OOO_UNIT/tage_ref.h`、`tb_tage`がRTLと照合するミラー)を同じブロックに。履歴の遅れ、更新の遅れ(とそのばらつき)、フェッチの停止つき。
- `SIM/CORE/tb_front`: ブロックのpushからその更新までにpushされるブロック(どのモードでも本当の経路で6.4〜6.6)と、分岐ごとの予測ミス(`FRONT_BYPC`)。

予測ミスした条件分岐(かっこ内はサイクルモデルのCoreMark/MHz):

| | g14 -O2 | g14 sf + -flto |
|---|---|---|
| `ooo.h`、分岐ごとのTAGEをすぐに更新(G0b、D-16) | 4,393 (6.193) | 3,291 (6.680) |
| `ooo.h`、分岐のコミットで / その4サイクル後に更新 | 4,436 (6.191) / 4,516 (6.188) | 3,393 (6.675) / 3,498 (6.670) |
| `tageblk.h`、すぐに / 8 / 16ブロック後に更新 | 4,752 / 4,985 / 5,583 | 4,153 / 4,209 / 4,317 |
| OOO_TAGEのアルゴリズム、遅れ2、すぐに更新 | 4,576 | 3,935 |
| 同じもの、6ブロック後に更新(B1の距離) / 6 ± 3 | 5,279 / 5,418 | 4,526 / 4,569 |
| 同じもの、ブロックの10 / 30 / 50 %で遅れ0(フェッチの停止) | 7,177 / 9,643 / 8,789 | 6,225 / 7,295 / 7,019 |
| **B1**(D2がランダム / 全速) | **6,582 / 8,426** | **5,742 / 6,106** |

1. **コミットでの更新の損は小さい**: 分岐ごとのTAGEでCoreMark/MHzの−0.03〜−0.15 %。OOO_TAGEのブロックごとの行でB1の距離なら、予測ミス+700 / +600。
2. **履歴の遅れ**: OOO_TAGEはF0でそのサイクルの履歴で表を読む。そこにはF1とF2にあるブロックが入っていない: フェッチが流れているあいだは2ブロック、停止(FTQかフェッチバッファが満杯、I$のミス、上書き、復元)のあとはそれより少ない。同じ分岐が別の履歴、別の行を読むことになる。1回が1ブロックのループ(`core_bench_list`の0x80000f18)では、出口と途中の1回を毎回はずす: B1で1,788(takenを912、not takenを876)、モデルで停止30 %なら1,687、遅れが一定ならほとんどなし。
3. **損失**: B1はG0bのモデルより+2.2k〜+4.0k(-O2)、+2.5k〜+2.8k(sf + -flto)多い。モデルの予測ミス1回あたり10.2サイクル(予測ミスのあとのディスパッチの停止)で、**サイクルの+1.4〜+2.5 % / +1.7〜+1.9 %**: 6.193 / 6.680が約6.04〜6.11 / 6.56になる。G1の±5 %の内だが、損である。
4. **直し方(D-17として提案、`Doc/UARCH_J.md` 9): 一定の2ブロックの遅れで読む。** インデックスは、読むブロックの前の2ブロックのビットを、すでに入っているかどうかにかかわらず除いた履歴を使う(フェッチはいくつ飛んでいるかを知っている)。ハードウェア: 最後にpushした2ブロックのビット数(2 × 2ビット)、畳み込みの前に70ビットの履歴を0〜6ずらす(レジスタから早く決まる7:1の選択、約0.15k LUT、F0からブロックRAMのアドレスへの経路上)、復元のためにFTQの各エントリに前のブロックのビット数(+2ビット)。見込み: B1の値ではなくモデルの5,279 / 4,526、**予測ミス約−1.2k〜−3.1k、CoreMark +0.8〜+2.0 %**。
5. **B6のために**: それでもOOO_TAGE(ブロックごと、コミットで更新)は`ooo.h`の分岐ごとのTAGEより+0.9k / +1.2k多い(サイクルの+0.6 % / +0.8 %)。B6で両者を比べる前に、G1のためのモデルの基準にOOO_TAGEの構造とコミットのタイミングを入れる(`ooo.h`に`tage_ref.h`を)。

### 5.6 ストアの書き出しがロードで止められないようにした(2026-10-31)

5.5で、ロードの流れがコミット済みのストアを止めることが分かった: `OOO_LSU`はEにロードがないサイクルでしかストアを流さない。

- **5.5の提案の後半だけにした理由**: D$は1サイクルに1つの要求しか受けない。`OOO_DCAD`はEのロード、待っているロード、ストアの順に送り、Eまたは待ちにロードがあるあいだはストアを受けない。別の8バイトのワードへのロードの横でストアを流すには1サイクルに2つの要求が要るので、本物のD$では起こりえない。これはしなかった。
- **したこと**(`OOO_LSU`、パラメータ`DRAIN_WAIT` = 8): Eのロードがいちばん古いコミット済みのストア(アドレスあり)を止めたサイクルを数える。D$が忙しくて待ったサイクルは数えない。`DRAIN_WAIT`に達したらストアがD$のポートを取る: Eのロードは要求を出さず、古いストアのアドレスがないときと同じくMで待ちに入り(ポート2からのロードなら`ld_cancel`: 印つきで完了し、コミットのあとでやり直す、D-12)、ストアが出たあとにLQからD$を読み直す。フリップフロップ数個とゲート。
