# Phase 0-2: CoreMarkのトレース解析(命令ミックス・分岐予測・SFB・融合・限界モデル)

- 実施日: 2026-10-24
- 目的: 2命令幅のOoOで目標(`-O2`で5.0、最大最適化で6.0 CoreMark/MHz)に届くか、何が効くかを、RTLを書く前に命令トレースで調べる(`Doc/STRATEGY_J.md` 5.2節の手順1〜2の前半)
- 作業ファイル: `Plan/trace/`(`trace.sh`、`capture.py`、`analyze.py`、`results/`)
- 前提: 測定用コンパイラはGCC 14.2(Debian 13)、`-O2`はZba/Zbb/Zbs/Zicond込み(2026-10-24決定、`ICOUNT_J.md`)

---

## 1. 結論

1. **分岐予測はTAGEで解決する**。mmRISC-2のgshareは1000命令あたり9.4回のミス(MPKI)だが、TAGEなら**0.9〜1.4**に下がる(1/7〜1/10)。CoreMarkは毎回同じデータを処理するので、長い履歴を持つ予測器がほぼ学習しきる。小さなTAGE(62 kbit、BRAM 2〜3個)でもMPKI 1.4で、大きなTAGEとの差は性能で1%未満と見込まれる。
2. **予測ミスが消えると、2命令幅の限界は「幅」そのもの**になる。理想化したモデル(後述、校正前)では、完全予測でもIPC 1.86で頭打ちになる。実行ユニットを増やしても(ALU 3本、LSU 2本)、ROBを32 → 128に増やしても、変わらない。
3. **幅の壁を越える手段は命令融合**。隣り合う依存命令の組を1 µopにすると、µop数は最大13〜15%減り、モデルのIPCは**+15%(1.84 → 2.11)**。最も効くのは「ALU命令 + その結果を使うALU命令」(1000命令あたり64組)で、50MHzの1サイクルに2段のALUを直列に入れる構成になる。その89%は中間結果が捨てられる組なので、レジスタへの書き込みは1回で済む。
4. **taken分岐のたびに1サイクルの泡が出ると−19%**。taken分岐は1000命令あたり125回(平均8命令ごと)ある。**0バブルのnext-line予測は必須**。
5. **SFB(短い前方分岐の述語化)はCoreMarkにはほぼ効かない**。対象になる分岐は条件分岐の2%、TAGEでのミスの2%以下。GCC 14はZicondで短い分岐をすでに消している。`STRATEGY_J.md` 2章の順位3から外す。
6. **保守的なメモリ依存(古いストアのアドレス確定までロードを待たせる)の損失は0%**。CoreMarkのストアのアドレスは早く決まる。最初のLSQは保守的な方式でよい。ただし、ロードの11%は直前64命令以内のストアのデータを読むので、**ストアからロードへのフォワーディングは必要**。
7. **load-useを2 → 3サイクルにすると−3〜4%**。ロードの38%は次の命令がすぐ使う。
8. 理想化した上限は、`-O2`で**5.9/MHz(TAGE)→ 6.8/MHz(TAGE + 融合)**、最大最適化で**6.5 → 7.5/MHz**。実際のコアはここから10〜25%落ちると見込まれる(要校正)。その場合は`-O2`で5.1〜5.7、最大最適化で5.6〜6.4。**融合なしでは`-O2`の5.0がぎりぎりで、最大最適化の6.0は届かない**。2命令幅で目標に届かせるには、融合が前提になる。

## 2. 方法

### 2.1 トレース
| 項目 | 内容 |
|---|---|
| ビルド | `ICOUNT_J.md`のg14 / o2 / zbsc(`-O2`の本命)、g14 / sflto / zbsc(最大最適化)、g13 / o2 / zb(mmRISC-2の条件)、g13 / o2 / gc(gshareの校正用)。いずれも10回 |
| 取得 | Spike `-l --log-commits`の出力から、計測区間(2回の`minstret`読み出しの間)だけを`capture.py`で切り出す。命令数は`icount.sh`と1命令差で一致 |
| 解析 | `analyze.py`。命令の種類は逆アセンブルのニーモニックで、読むレジスタはオペランドで、書くレジスタはコミット行で決める。SFBの判定には静的なコード(objdump)を使う |

### 2.2 分岐予測器(条件分岐、トレース駆動)
| 名前 | 構成 | 容量 |
|---|---|---|
| bimodal-4K | 2ビットカウンタ4096個 | 8 kbit |
| gshare-m2 | mmRISC-2のgshare(decision 63): PHT 8192 × 2ビット、条件分岐の向き12ビットをインデックスの上位側にXOR、初期値weakly taken | 16 kbit |
| TAGE-S | ベース4K + タグ付き4表 × 1K、履歴5 / 12 / 30 / 70 | 62 kbit |
| TAGE-M | ベース8K + タグ付き6表 × 2K、履歴4〜200 | 196 kbit |
| TAGE-L | ベース16K + タグ付き8表 × 4K、履歴4〜640 | 560 kbit |

予測器は分岐ごとに即座に更新する(実ハードの遅れた更新より楽観的)。戻り先はリターンアドレススタックで全部当たるとし、それ以外の`jalr`は前回の飛び先で予測する。

**校正**: g13 / o2 / gcの条件分岐は**582,985回で、mmRISC-2のSIM_SYS(BENCH.md 9章)と完全に一致**。gshare-m2のミス率は**5.28%**で、mmRISC-2の実測5.4%(31,435回)との差は2%。mmRISC-2では、BTBにエントリを持つ分岐だけが履歴に入る。この違いの範囲で、予測器のモデルは実機を再現している。

### 2.3 限界モデル(校正前、上限と感度を見るためのもの)
理想化したOoOコア。パラメータは次のとおり。
- 幅W(dispatch / commit)、ROB R、ポート(ALU 2 / LSU 1 / MUL 1)
- レイテンシ: ALU・分岐1、ロード2、乗算2
- 予測ミスのペナルティP(分岐の実行から正しい経路の最初の命令の実行まで)
- taken分岐でdispatchのグループが切れる(泡は0、オプションで1)
- 融合した組は1つのdispatch / issue / commit枠とポートを使う。各半分は組のissueからそれぞれのレイテンシで完了する(add + loadならロードは2サイクル、依存するALU 2つは1サイクル)

**入っていないもの**: I$ / BTBのミス、予測器の読み出し遅延、発行キューとPRFの容量、wakeupの遅れ、リネームの詰まり、RVC命令の整列によるフェッチの制約、メモリ依存の予測ミス。したがってIPCは上限で、実コアとの比は次の作業(校正したサイクルモデル)で決める。

## 5. 注意点

- 限界モデルは**校正していない**。2命令幅で完全予測なのにIPC 1.86という値は、dispatchとcommitの幅の制約だけから出たもの。実際のコアでは、フロントエンドの整列、予測器の読み出し遅延(BRAMのTAGEは2サイクル)、発行キューとwakeupの制約、リネームの詰まりが加わる。
- 「10〜25%落ちる」は経験則による仮置き。次の作業で、mmRISC-2のインオーダー8段(CPI 1.103)を再現できるサイクルモデルを作り、この比を詰める。
- 予測器は即時更新のトレース駆動なので、実ハード(投機的な履歴更新と修復、遅れた更新)より少し良く出る。
- ALU 2段の連結は、タイミングとPRFの読み出しポート(3ソース)のコストを伴う。どの組を採るかは、融合率だけでなく、LUTとタイミングで決める。
