# Phase 0の残りの検討項目(課題と対策)

- 作成日: 2026-10-24
- 位置づけ: G0(マイクロアーキテクチャの凍結、`Doc/STRATEGY_J.md` 7章)までに検討すべき項目を、課題と対策の形で整理する。`ICOUNT_J.md`と`TRACE_J.md`の結果、およびmmRISC-2 Rev.02の資源の実測(本書2章)を受けたもの。
- 進捗に合わせて更新する(mmRISC-2の`ROADMAP.md`に相当)。

## 0. 要約

1. **現在地**: 必要なIPCは`-O2`の5.0で1.56、最大最適化の6.0で1.69(`ICOUNT_J.md`)。トレース解析の限界モデルでは、TAGE + 0バブルのフロントエンド + 命令融合で`-O2` 6.8、最大最適化 7.5/MHz(`TRACE_J.md`)。ただし校正していないので、実際のコアの損失(仮に10〜25%)を詰めないと、目標に届くかは判断できない。
2. **最優先は「校正したサイクルモデル」**(3.1節)。以降の判断のほとんどがこのモデルの数字に依存する。
3. 構造上の急所は3つある。
   - **0バブルのフロントエンドとBRAMのTAGEの両立**(3.2節): taken分岐1回ごとに泡が1つ出ると−19%。
   - **命令融合を50MHz・-1グレードで実現できるか**(3.3節): ALU 2段の連結、4命令デコード、例外の扱い。
   - **LUT予算**(3.4節): 実測ではLiteXは4.8k LUTと小さく、FPUが8.8k LUTで、コア内で最大のブロックだった。**FPUの扱いが資源配分の最大のレバー**になる。
4. 進め方: サイクルモデル(Claude Code)と、小さなブロックの先行OOC合成(RTLはClaude Code、Vivadoは作者)を並行して進める。その結果でG0の仕様書をまとめる。

### 予算の見直し(`STRATEGY_J.md` 3章の見積りを訂正)

| 項目 | 見積り(STRATEGY) | 実測にもとづく値 |
|---|---|---|
| LiteX SoC | 11〜13k | **4.8k** |
| コア以外のCPU_TOP(キャッシュ、L2、デバッグ、MMIO、DMA) | 約9k | 12.6k |
| コアに使える分(全体を約52kまでとして) | 約30k | **約34.6k**(mmRISC-2のコアは32.9k) |
| OoOと無関係に必要な部分(CSR、MMU、MDU、FPU、FRF) | 約15k | **21.7k**(うちFPU 8.8k) |
| OoOエンジン + フロントエンド + ALU + LSUに残る分 | 1.5〜1.6万 | **約12.9k**(FPUを縮小すると、その分だけ増える) |

- **FPUがコアの27%を占める**。マルチサイクルのFPUに戻すと数k LUT空く見込み。ただし、パイプライン化前のFPUの規模はmmRISC-2の記録からは確定できない(当時は境界をまたぐ最適化で、FPUの一部がLSUに数えられていた。TIMING.md)。OOC合成で測る。NaxRiscv RV64(整数のみで約18k)と同程度の枠を確保するには、FPUの縮小がほぼ前提になる。
- BRAMの空きは26.5タイル。TAGE-S〜M(3〜8)、BTB(2〜4)、ROBのペイロード(1〜2)は空きで収まる。足りなければ、L2を256 → 128KBにすると32タイル空く(CoreMarkには影響しない。Linuxの負荷には影響する)。
- スライス使用率93%(mmRISC-2)が配線遅延の主因だったので、LUTの上限は同程度(約52k)とする。

## 3. 検討項目(課題と対策)

### 3.1 校正したサイクルモデル【最優先】

| | 内容 |
|---|---|
| 課題 | 限界モデルは、フロントエンドの整列、予測器の読み出し遅延、発行キューの容量、wakeupの遅れ、リネームの詰まり、ロードのヒット予測の失敗を含まない。実コアとの差(10〜25%と仮置き)が詰まらないと、目標に届くか、何を作るべきかが決まらない |
| 対策 | 同じトレースを入力にしたC++のサイクルモデル。段ごとのパイプラインを明示的に持ち、構成をパラメータにする。**まずmmRISC-2のインオーダー8段を再現させて校正する**: CoreMark CPI 1.103(SIM_SYS)、予測ミス5.4%、load-use待ち、乗算待ち(BENCH.md 8〜9章、13章の内訳)。その後、同じ部品でOoO 2幅を組む |
| 完了条件 | インオーダーでCPIが±3%以内、待ちの内訳が実測と同じ順位。OoO構成でCoreMark/MHzと各要因の寄与の表 |
| 注意 | トレース駆動では誤った経路の命令を実行しない(予測器やI$の汚染がない)。CoreMarkはキャッシュに収まるので影響は小さいが、限界として記録する |
| 担当 | Claude Code |

### 3.2 フロントエンド: 0バブルとTAGEの両立

**2026-10-24追記**: OoOのサイクルモデル(`MODEL_J.md` 6章)では、16バイトのフェッチをバッファでdispatchから分離すれば、takenのたびの泡はほとんど吸収された(uBTBなしでも−0.9%)。効くのはフェッチ幅(8バイトで−3.8%)。下の課題の重さはこの結果で読み替える。

| | 内容 |
|---|---|
| 課題 | taken分岐は1000命令に125回あり、1回ごとに泡が1つ出ると−19%。一方、TAGEとBTBをBRAMに置くと読み出しに2サイクルかかり、1サイクルで次のPCを出せない。さらにRVCが46%あるので、命令境界の判定と、16Bのフェッチブロックをまたぐ32ビット命令(3〜9%)の扱いが要る |
| 対策 | **2段の予測**: 1サイクルで次のPCを出す小さなnext-line予測器(uBTB、LUTRAM)で泡をなくし、TAGEとBTBは2サイクル目に結果を上書きする(食い違ったときだけ1〜2サイクルの損失)。uBTBの大きさの根拠: CoreMarkでtakenになる命令は184〜206個で、**64エントリで87〜93%、128エントリで98〜99.6%を覆う**(本書のための追加測定)。16Bのフェッチ + 16ビット単位のフェッチバッファ、I$にプリデコードビット。FTQで予測とフェッチを分離する |
| 確認 | サイクルモデルで、uBTBのサイズ、上書きの頻度と損失、フェッチ幅を振る。uBTBの次PC経路は早期にOOC合成する |
| 関連 | mmRISC-2で、ワードをまたぐ分岐が予測ミスの54%を占めていた経験(CPU_CORE_SPEC 4.2)。境界の扱いは最初から仕様に入れる |

### 3.3 命令融合の実現性

| | 内容 |
|---|---|
| 課題 | (1) **タイミング**: ALU + ALUの融合は、1サイクルに64ビットALUを2段直列に入れる。バイパスとwakeupを含めて50MHz(-1グレード)で閉じるか。(2) **幅**: 2 µopに最大4命令を詰めるには、1サイクルに4命令をデコードする必要がある(デコーダとRVC展開器が4組、LUTが増える)。(3) **正しさ**: 融合した組の途中で起きる例外(アドレス計算 + ロードのページフォールト)、デバッグの1命令ステップ、トリガ、`minstret`とPMUの数え方。(4) **PRFのポート**: 組のソースが3つになる |
| 対策 | (1) 2段ALUの小さなRTLをOOC合成して、遅延を実測する。閉じなければ、ALU + 分岐(比較 + 分岐、書き込みなし)とアドレス計算 + ロード(AGUに加算を1つ足す)に絞る。(2) 4命令デコードのLUTを見積もる。融合は同じフェッチブロック内の隣接ペアに限る。(3) 例外・デバッグ中は**融合を解いて1命令ずつ再実行する**(よく使われる方法)。シングルステップ中とトリガ設定中は融合を止める。`minstret`は命令数で数える。(4) 中間結果が捨てられる組(ALU + ALUの89%)を優先し、書き込みポートは増やさない |
| 確認 | サイクルモデルで、融合の組ごとの効果とレイテンシの仮定(1サイクルで連結 / 2サイクル)を比べる。OOC合成でタイミングを測る |
| 担当 | RTLの断片とモデルはClaude Code、Vivadoは作者 |

### 3.4 資源配分

| | 内容 |
|---|---|
| 課題 | OoOのエンジンに残るのは約12.9k LUT(FPUそのまま)。NaxRiscv RV64の整数コア(約18k)より小さい。D$も7.5kと大きく、OoOのLSUとつなぐと増える |
| 対策 | **FPUを縮小する**(マルチサイクル、またはインオーダーのサイドパイプ。`PRESTUDY_MMRISC2_J.md` 5.A節の案3 / 案4): 数k LUT空く見込み(規模はOOC合成で確認)。CoreMarkは浮動小数点を使わない。Debianのlp64dにはF/Dが必要なので、機能は残す。その他の削減候補はPMP 16 → 8(OpenSBIの挙動を確認)、トリガ4 → 2、MDUのZbc(clmul)の共有。大きな表はBRAM / LUTRAMに置き、FFでは作らない |
| 決めること | FPUの方式(D-1)、L2の容量(D-2)、Ethernetを残すか(D-3)。**削減案の一覧は`REDUCE_J.md`**(2026-10-24。機能も性能も失わない案だけで約3.5〜5k LUT) |
| 確認 | 主要ブロックのOOC合成でLUTを積み上げ、G0で予算表にする |

### 3.5 50MHz(-1グレード)のタイミングの急所

| | 内容 |
|---|---|
| 課題 | mmRISC-2は、インオーダー7段で最初に−20.4nsだった(8段にして閉じた)。OoOには1サイクルで閉じるべきループがいくつもある: wakeup-select、リネーム(4命令の組の中の依存の検出 + 融合)、次PCの生成(uBTB)、2段ALU、PRFのLVT読み出し |
| 対策 | **G0の前に、各ループの小さなRTLをOOC合成する**(mmRISC-2のFPU_OOC / L2_OOCと同じ方法)。閉じないループは仕様で段を分ける。最後の手段はALUの2サイクル化(NaxRiscvの知見で約−15%。サイクルモデルで確認) |
| 担当 | RTLの断片はClaude Code、OOC合成は作者 |

### 3.6 LSUとメモリ系

| | 内容 |
|---|---|
| 課題 | load-useを2サイクルに保つには、ロードのヒットを予測して後続を投機的にwakeupし、ミスしたらリプレイする仕組みが要る(load-useが3サイクルだと−3〜4%)。ロードの11%は直前のストアのデータを読むので、ストアからロードへのフォワーディングが必須。mmRISC-2のD$はインオーダーのLSU 1本を前提にしたインターフェース |
| 対策 | 保守的なメモリ依存(損失0%を確認済み)で、LQ / SQとフォワーディング(同一アドレス・同一サイズから)を作る。ストアはコミット後にD$へ書く。D$はmmRISC-2のもの(ノンブロッキング、MSHR 2)を使い、OoO側にタグ付きの要求 / 応答のアダプタを置く。CPU_CACHE_SPECのインターフェースを読み直し、変更点を洗い出す |
| 確認 | サイクルモデルで、ヒット予測の失敗とリプレイの損失、SQの深さを見る |

### 3.7 Linuxのための受け口(非投機化)

| | 内容 |
|---|---|
| 課題 | OoOでLinuxが動かなくなる典型は副作用の扱い: MMIOのロード、CSR、AMO / LR / SC、SFENCE.VMA / FENCE.I、PTWのA/Dビット更新、精密例外、デバッグ、トリガ、PMU(`PRESTUDY_MMRISC2_J.md` 4章)。Phase 1をCoreMark先行(M-modeのみ)にすると、後から足したときに壊れる恐れがある |
| 対策 | Phase 1の仕様に「ROB先頭で直列化して実行する命令の一覧」と「精密例外の受け口」を入れておく(実装は簡単な形で、最初から全部通す)。PTWのA/D更新の投機性は特権仕様で確認する |
| 確認 | G0の仕様書に一覧があること |

### 3.8 検証の基盤

| | 内容 |
|---|---|
| 課題 | OoOの不具合はインオーダーより見つけにくい。mmRISC-2の資産(SIM_CORE / SYS / BIOS、riscv-tests、バグ注入)は、命令単位の比較を前提にしていない |
| 対策 | **Spikeとのコミット単位のlock-step比較**を初日から入れる(Spikeは導入済み。mmRISC-2の拡張: Sstc、Zicboz、Smcntrpmf、Sdtrig、PMPなどにどこまで対応しているかを確認する)。RVFI相当のコミットトレースのI/F、Konata形式のパイプライン表示、サイクルモデルとのサイクル比較(性能バグの検出)、ランダム命令列、例外の注入、リネームやLSQへのバグ注入 |
| 確認 | Phase 1の最初の成果物が「lock-step比較の枠組み」であること |

### 3.9 ボード上の測定方法

| | 内容 |
|---|---|
| 課題 | ボード上のCoreMarkはLinux上のposixポート(glibc)。ベアメタルでの命令数と完全には一致しない。最大最適化のオプション(sf + `-flto`かsfか)は、命令数ではなくサイクルで決める必要がある |
| 対策 | ボード用のCoreMarkも、GCC 14.2(ホストのqemu-user、またはボード上のgcc)でビルドする手順を固める。最大最適化のオプションは、サイクルモデルとRTLのシミュレーションで比べて決める |

### 3.10 NaxRiscvの実測(優先度を下げる)

| | 内容 |
|---|---|
| 課題 | 当初は、OoOがArtyに入るかの上限値を知る手段として計画した(`STRATEGY_J.md` 5.2節の5)。mmRISC-2の実測で予算の多くが分かったので、価値は「OoOエンジンのLUTの参考値」に下がった |
| 対策 | 予算が際どいと分かった時点で行う。LiteXの`--cpu-type naxriscv --xlen 64`で作り、作者がVivadoで合成する |

## 6. リスクと撤退ライン(見直し)

| リスク | 兆候 | 対策・撤退 |
|---|---|---|
