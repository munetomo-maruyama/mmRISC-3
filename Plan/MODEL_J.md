# Phase 0-3: サイクルモデル(1) 枠組みとmmRISC-2による校正

- 実施日: 2026-10-24
- 目的: `ISSUES_J.md` 3.1節と5章の手順1。トレースを入力にしたC++のサイクルモデルの枠組みを作り、mmRISC-2のインオーダー8段で校正する。次の手順2では、同じ枠組みでOoO 2幅を組む
- 作業ファイル: `Plan/model/`(`mktrace.py`、`model.h`、`pred_mm2.h`、`inorder.h`、`model.cpp`、`calib.sh`、`results/calib.txt`)

---

## 1. 結論

1. **mmRISC-2のインオーダー8段を、CoreMarkの5つの実測点すべてで±0.3%以内に再現した**。自由なパラメータは1つ(予測ミスの解決からIF1までのサイクル数 `redirect = 2`)だけで、5点を同時に合わせた。
2. 待ちの内訳も実測と一致した: 乗算の待ち(281,880 / 93,960)は完全に一致、load-useの待ちは203,282 / 67,982(実測203,281 / 67,982)、MRで解決する分岐は135,300回(実測135,299)。予測ミス1回の損失は4.16サイクル(実測4.12)。
3. これで、モデルの基本部分(トレースの読み方、依存の取り方、フェッチの模擬、mmRISC-2の予測器)が実機の数字と整合していることを確認できた。OoO 2幅は、この枠組みに部品を足して組む(手順2)。

### 2.1 インオーダーモデル(`inorder.h`)

| 要素 | 模擬の仕方 | mmRISC-2での根拠 |
|---|---|---|
| フェッチ | IF1で1サイクルに8バイトを1語。命令は最後のパーセルを含む語のIF1から`fetch_to_ex = 3`サイクル後にEXへ入れる | IF1 → IF2 → ID → EX(CPU_CORE_SPEC 3.2) |
| 正しく予測したtaken | 次のサイクルに飛び先の語をIF1で読む(泡なし) | BTBはIF1で引く(4.2) |
| 予測ミス | 解決したサイクルtから`t + redirect`で飛び先がIF1に入る。**`redirect = 2`が唯一の調整値** | EXから修正する経路(決定46) |
| 乗算 | EXを1サイクル止める(MULH系は2) | 決定61 |
| load-use | ロードの次の命令がその値を読むと、EXで1サイクル待つ。条件分岐は待たずにMRで解決する(ミスなら1サイクル遅い) | 3.2節、決定64 |
| キャッシュ | 常にヒット | CoreMarkのミスは1000命令あたりI$ 0.49、D$ 0.16(ボード) |

## 3. 校正の結果

mmRISC-2が10月にSIM_SYSで測ったCoreMark(10回、GCC 13.2、`-O2`)のうち、ハードウェアを1つずつ変えた5つの時点(`LitexSystem/docs/BENCH.md`)。

| 点 | mmRISC-2の状態 | 実測(サイクル) | モデル | 差 |
|---|---|---|---|---|
| P1 | A2の後(6章): 乗算の待ち3、BTBの2ビットカウンタ | 4,312,829 | 4,314,572 | +0.04% |
| P2 | 決定61(7章): 乗算の待ち1 | 4,124,913 | 4,126,652 | +0.04% |
| P3 | 決定63(9章): gshare | 4,033,497 | 4,044,524 | +0.27% |
| P4 | 決定64(10章): MRで解決する分岐 | 3,908,766 | 3,911,568 | +0.07% |
| P5 | 同じハードウェアでZba / Zbbのビルド(11章) | 3,513,870 | 3,518,805 | +0.14% |

| 内訳 | 実測 | モデル |
|---|---|---|
| 乗算の待ち(P1 / P2) | 281,880 / 93,960 | 281,880 / 93,960 |
| load-useの待ち(P1 / P4) | 203,281 / 67,982 | 203,282 / 67,982 |
| MRで解決した分岐 / うちミス(P4) | 135,299 / 2,321 | 135,300 / 2,344 |
| 予測ミスの損失(P1) | 5.6%(約241.5k)、1回あたり4.12 | 240,165、1回あたり4.16 |
| 条件分岐のミス: 2ビット(P1)/ gshare(P3) | 54,001 / 31,435 | 52,069 / 32,529 |
| `jal` / `jalr`のミス(P1) | 1,028 / 3,559 | 2,691 / 2,962 |

- 条件分岐のミス数は±4%で一致した。`jal`と`jalr`の内訳はずれているが、合計(4,587と5,653)は近く、サイクルへの影響は小さい。差の原因は、mmRISC-2の「語をまたぐ分岐のテールエントリ」と「ミスフェッチの検出」を簡略化したことと考えられる(`pred_mm2.h`の冒頭)。
- `redirect`を1にすると、全点で約1〜1.3%少なく出る。2で5点が同時に合うので、パラメータの取り方は妥当と判断した。

## 4. 限界

- トレース駆動なので、誤った経路の命令を実行しない(予測器やキャッシュの汚染がない)。CoreMarkは誤った経路でもキャッシュに収まるので、影響は小さい。
- キャッシュは常にヒットとした。mmRISC-2のSIM_SYSのメモリは即答する設定で、ボードとの差(実測でCoreMark/MHz 2.85 → 2.79)はここに入らない。OoOの比較は、同じ前提の上で行う。
- 校正したのはインオーダーの部品(フェッチ、予測器、依存、乗算)だけ。OoOに固有の部品(リネーム、発行キュー、wakeup、ROB、LSQ、TAGE、uBTB、融合)は、校正の基準になる実機がない。そのため、手順2では各部品のタイミングを仕様として明示し、限界モデル(`TRACE_J.md`)との差を部品ごとに説明できる形にする。

## 5. 次の作業(手順2)

2026-10-24に実施した。結果は6章。

同じ枠組みで、OoO 2幅のモデル(`ooo.h`)を作る。

1. フロントエンド: uBTB(0バブル)+ TAGE / BTBの上書き(2サイクル目)、FTQ、16バイトのフェッチ、RVCの整列と語をまたぐ命令。
2. 中核: デコード / リネーム(2 µop、融合で最大4命令)、ROB、発行キュー(容量とwakeup-select)、ALU 2本 / LSU 1本 / MUL、load-use 2サイクル(ヒット予測)、予測ミスの回復(解決から次の実行までのサイクル数を段数から計算)。
3. LSU: 保守的なメモリ依存、ストアからロードへのフォワーディング、コミット後のストア。
4. 出力: CoreMark/MHzと、損失の内訳(フロントエンド、予測ミス、依存、構造)。構成を振る表を`MODEL_J.md`の続き(手順2の章)にまとめる。

## 6. サイクルモデル(2) OoO 2幅(手順2、2026-10-24)

作業ファイル: `Plan/model/ooo.h`(モデル本体)、`tage.h`(TAGE)、`sweep.sh`(パラメータを1つずつ振る表、`results/sweep.txt`)

### 6.1 結論

1. **2幅のOoOで、融合なしでも目標に届く見込みになった**。基準構成で`-O2` **6.07**、最大最適化 **6.57** CoreMark/MHz。小さな構造・遅いパイプライン・load-use 3サイクルを全部重ねた悲観的な構成でも、`-O2` 5.61、最大最適化 6.05。
2. **融合を入れると余裕ができる**: ALU + ALUまで含めると基準構成で7.06 / 7.59、悲観的な構成でも6.41 / 6.88。ただし、効果を出すには4命令デコードが要る(2命令デコードでは+3%にとどまる)。
3. **限界モデル(`TRACE_J.md`)の「takenごとの泡で−19%」は、OoOのフロントエンドを分離すると起きない**。16バイトのフェッチがバッファを通して2命令/サイクルのdispatchより速いので、takenのたびの泡はほとんど吸収される。uBTBを持たず、takenのたびに上書きで1サイクル失う構成でも−0.9%。代わりに**フェッチ幅が効く**(8バイトにすると−3.8%)。
4. 効く要素(基準からの変化): 予測器(gshare −13%、TAGE-S → M +0.9%)、load-use 3サイクル −5.9%、フォワーディングなし −4.3%、ALU 1本 −36%、チェックポイント4個 −1.8%、LSU 2本 +1.6%。
5. ほとんど効かない要素: ROB(32〜96)、発行キュー(16以上)、パイプラインの段数(1段ごとに約−0.3%。予測ミスが少ないため)、uBTBの大きさ(16〜128)、保守的なメモリ依存、乗算のレイテンシ、ALU 3本、1サイクルの発行数を3に制限すること、MULをALUポートと共有すること。
6. **検算**: (a) 予測を完全にし、フェッチ・キューの制約を外すと、IPCは1.9507で、限界モデルの「グループ切れなし」1.951と一致。(b) C++のTAGEは、Pythonのトレース解析とミス数が完全に一致(S / M / L)。(c) NaxRiscvに近い構成(gshare、load-use 3)で、mmRISC-2の条件のビルドが4.83。NaxRiscv RV64の公表値4.94に近い(コンパイラとISAは異なるので、目安としての比較)。

### 6.2 モデルの仕様(基準構成)

| 項目 | 基準 | 意味 |
|---|---|---|
| 幅 | dispatch / commit 2 µop、デコード4命令、発行は全体で3 / サイクル | `w`、`dec_w`、`issue_w` |
| 実行ユニット | ALU 2(分岐を含む)、LSU 1、MUL / DIVはALUポートを共有 | `alu`、`lsu`、`mul_shared` |
| フロントエンド | フェッチ16バイト(整列)/ サイクル、takenで次のブロックへ、フェッチバッファ16命令 | `fetch_bytes`、`fb` |
| 予測 | uBTB 64(全連想、LRU、2ビットカウンタ、戻りはRAS)が0バブルで次PCを出し、TAGE-S + BTB + RAS 16がF0から2サイクル目に上書き | `ubtb`、`pred`、`override_at` |
| 段数 | F0 → デコード3、デコード → dispatch 2、dispatch → 発行1、発行 → EX終了2、解決 → F0 1。**予測ミスの損失はEXからEXまで9サイクル** | `fe_depth`、`dec_depth`、`iss_to_ex`、`redirect` |
| 窓 | ROB 64、発行キュー24(統合、発行で空く)、LQ 16 / SQ 16、チェックポイント無制限 | `rob`、`iq`、`lq`、`sq`、`ckpt` |
| レイテンシ | 発行から依存命令の発行まで: ALU 1、ロード2(ヒット)、MUL 2 | `lat_*` |
| メモリ | 保守的なメモリ依存、SQからのフォワーディング、ストアはコミット後。ストアをデータと一緒に発行する(そのときアドレスが分かる: `OOO_LSU`、Plan/CORE_J.md 5.8) | `mem_cons`、`fwd`、`st_data_issue` |
| 融合 | なし(1: アドレス計算 + ロード、ペア、lui / auipc。2: + ALU + 分岐。3: + ALU + ALU、1サイクルで連結) | `fusion`、`chain` |

### 6.4 これで変わること(提案)

| 項目 | これまで | モデルの結果を受けて |
|---|---|---|
| フロントエンド | 0バブルのuBTBが必須(`ISSUES_J.md` 3.2) | **16バイトのフェッチと、dispatchとの分離(バッファ)が本質**。uBTBは16〜32エントリで足り、なくても−1%。次PCの1サイクルのループが閉じなければ、uBTBは外してよい |
| 融合 | 効果+15%、4命令デコードの費用は0.7k LUT | 効果は**+16%(基準)/ +14%(悲観的)**。4命令デコードは必須。D-4は「ALU + 分岐」(+9%)を最低線とし、ALU + ALUは2段ALUのタイミング次第 |
| 構造の大きさ | ROB 48〜64、IQ 16〜24 | **ROB 32、IQ 16、LQ / SQ 12〜16、チェックポイント8で十分**(−0.3%)。LUTの節約に回せる |
| load-use | 2サイクル(−3〜4%) | 2サイクルを守る価値は**約6%**。ヒット予測と投機的wakeupは必須 |
| LSU | 1本 | 2本で+1.6%。資源に余裕があれば候補 |
| 予測器 | TAGE-S〜M | TAGE-S(62 kbit)で十分(TAGE-Mとの差は0.9%) |

### 6.5 限界(このモデルに入っていないもの)

- **キャッシュのミスとボードのメモリ**: 常にヒット。mmRISC-2では、ボードがシミュレーションより約2%低かった(2.79 vs 2.85)。同程度を差し引いて見る。
- **誤った経路の命令**: 実行しない。誤った経路のµopがROB / IQ / ポートを占める分、実際は少し悪い(予測ミスは1000命令に1.4回と少ないので、影響は小さいと見込む)。
- **発行の選択**: 古い順で理想的に選ぶ。実際のselectの近似、ポートの割り当ての制約は入っていない。
- **PRFの容量とポート**: 制約なし(PRF 96本、ROB 64なら足りる計算)。発行3 / サイクルなら読み出しは6ポート。
- **タイミングの実現性**: 各段の仮定(wakeup-select 1サイクル、2段ALUの連結、TAGEの2サイクル上書き)が50MHzで閉じるかは、OOC合成で確認する(`ISSUES_J.md` 3.5節)。
- **融合の正しさの扱い**: 例外時に融合を解いて再実行するコストは入っていない(CoreMarkでは例外は起きない)。
