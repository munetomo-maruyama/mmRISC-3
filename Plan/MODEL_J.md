# Phase 0-3: サイクルモデル(1) 枠組みとmmRISC-2による校正

- 実施日: 2026-10-24
- 目的: `ISSUES_J.md` 3.1節と5章の手順1。トレースを入力にしたC++のサイクルモデルの枠組みを作り、mmRISC-2のインオーダー8段で校正する。次の手順2では、同じ枠組みでOoO 2幅を組む
- 作業ファイル: `Plan/model/`(`mktrace.py`、`model.h`、`pred_mm2.h`、`inorder.h`、`model.cpp`、`calib.sh`、`results/calib.txt`)

---

## 1. 結論

1. **mmRISC-2のインオーダー8段を、CoreMarkの5つの実測点すべてで±0.3%以内に再現した**。自由なパラメータは1つ(予測ミスの解決からIF1までのサイクル数 `redirect = 2`)だけで、5点を同時に合わせた。
2. 待ちの内訳も実測と一致した: 乗算の待ち(281,880 / 93,960)は完全に一致、load-useの待ちは203,282 / 67,982(実測203,281 / 67,982)、MRで解決する分岐は135,300回(実測135,299)。予測ミス1回の損失は4.16サイクル(実測4.12)。
3. これで、モデルの基本部分(トレースの読み方、依存の取り方、フェッチの模擬、mmRISC-2の予測器)が実機の数字と整合していることを確認できた。OoO 2幅は、この枠組みに部品を足して組む(手順2)。

## 2. モデルの構成

| ファイル | 内容 |
|---|---|
| `mktrace.py` | `../trace/`のトレース(テキスト)を、1命令32バイトの固定長レコードにする。命令の解読は`../trace/analyze.py`と共通(同じ命令を同じように見る) |
| `model.h` | レコードの定義(pc、メモリアドレス、長さ、種類、フラグ、ソース3つ、デスティネーション、ベース、融合用の操作の種類)、読み込み、`key=value`の引数 |
| `pred_mm2.h` | mmRISC-2の分岐予測: 8バイト語ごとの直接マップのBTB(256、所有者つき、takenのときだけ作る)、gshare(PHT 8192、12ビットの履歴を上位ビットに折り込み)またはBTBの2ビットカウンタ、リターンアドレススタック(8) |
| `inorder.h` | mmRISC-2のインオーダー8段のタイミング |
| `model.cpp` | 本体(`model inorder <trace.bin> [key=value ...]`) |
| `calib.sh` | 校正の5点を流して、実測と並べる(`results/calib.txt`) |

### 2.1 インオーダーモデル(`inorder.h`)

| 要素 | 模擬の仕方 | mmRISC-2での根拠 |
|---|---|---|
| フェッチ | IF1で1サイクルに8バイトを1語。命令は最後のパーセルを含む語のIF1から`fetch_to_ex = 3`サイクル後にEXへ入れる | IF1 → IF2 → ID → EX(CPU_CORE_SPEC 3.2) |
| 正しく予測したtaken | 次のサイクルに飛び先の語をIF1で読む(泡なし) | BTBはIF1で引く(4.2) |
| 予測ミス | 解決したサイクルtから`t + redirect`で飛び先がIF1に入る。**`redirect = 2`が唯一の調整値** | EXから修正する経路(決定46) |
| 乗算 | EXを1サイクル止める(MULH系は2) | 決定61 |
| load-use | ロードの次の命令がその値を読むと、EXで1サイクル待つ。条件分岐は待たずにMRで解決する(ミスなら1サイクル遅い) | 3.2節、決定64 |
| キャッシュ | 常にヒット | CoreMarkのミスは1000命令あたりI$ 0.49、D$ 0.16(ボード) |

## 3. 校正の結果

mmRISC-2が10月にSIM_SYSで測ったCoreMark(10回、GCC 13.2、`-O2`)のうち、ハードウェアを1つずつ変えた5つの時点(`LitexSystem/docs/BENCH.md`)。

| 点 | mmRISC-2の状態 | 実測(サイクル) | モデル | 差 |
|---|---|---|---|---|
| P1 | A2の後(6章): 乗算の待ち3、BTBの2ビットカウンタ | 4,312,829 | 4,314,572 | +0.04% |
| P2 | 決定61(7章): 乗算の待ち1 | 4,124,913 | 4,126,652 | +0.04% |
| P3 | 決定63(9章): gshare | 4,033,497 | 4,044,524 | +0.27% |
| P4 | 決定64(10章): MRで解決する分岐 | 3,908,766 | 3,911,568 | +0.07% |
| P5 | 同じハードウェアでZba / Zbbのビルド(11章) | 3,513,870 | 3,518,805 | +0.14% |

| 内訳 | 実測 | モデル |
|---|---|---|
| 乗算の待ち(P1 / P2) | 281,880 / 93,960 | 281,880 / 93,960 |
| load-useの待ち(P1 / P4) | 203,281 / 67,982 | 203,282 / 67,982 |
| MRで解決した分岐 / うちミス(P4) | 135,299 / 2,321 | 135,300 / 2,344 |
| 予測ミスの損失(P1) | 5.6%(約241.5k)、1回あたり4.12 | 240,165、1回あたり4.16 |
| 条件分岐のミス: 2ビット(P1)/ gshare(P3) | 54,001 / 31,435 | 52,069 / 32,529 |
| `jal` / `jalr`のミス(P1) | 1,028 / 3,559 | 2,691 / 2,962 |

- 条件分岐のミス数は±4%で一致した。`jal`と`jalr`の内訳はずれているが、合計(4,587と5,653)は近く、サイクルへの影響は小さい。差の原因は、mmRISC-2の「語をまたぐ分岐のテールエントリ」と「ミスフェッチの検出」を簡略化したことと考えられる(`pred_mm2.h`の冒頭)。
- `redirect`を1にすると、全点で約1〜1.3%少なく出る。2で5点が同時に合うので、パラメータの取り方は妥当と判断した。

## 4. 限界

- トレース駆動なので、誤った経路の命令を実行しない(予測器やキャッシュの汚染がない)。CoreMarkは誤った経路でもキャッシュに収まるので、影響は小さい。
- キャッシュは常にヒットとした。mmRISC-2のSIM_SYSのメモリは即答する設定で、ボードとの差(実測でCoreMark/MHz 2.85 → 2.79)はここに入らない。OoOの比較は、同じ前提の上で行う。
- 校正したのはインオーダーの部品(フェッチ、予測器、依存、乗算)だけ。OoOに固有の部品(リネーム、発行キュー、wakeup、ROB、LSQ、TAGE、uBTB、融合)は、校正の基準になる実機がない。そのため、手順2では各部品のタイミングを仕様として明示し、限界モデル(`TRACE_J.md`)との差を部品ごとに説明できる形にする。

## 5. 次の作業(手順2)

同じ枠組みで、OoO 2幅のモデル(`ooo.h`)を作る。

1. フロントエンド: uBTB(0バブル)+ TAGE / BTBの上書き(2サイクル目)、FTQ、16バイトのフェッチ、RVCの整列と語をまたぐ命令。
2. 中核: デコード / リネーム(2 µop、融合で最大4命令)、ROB、発行キュー(容量とwakeup-select)、ALU 2本 / LSU 1本 / MUL、load-use 2サイクル(ヒット予測)、予測ミスの回復(解決から次の実行までのサイクル数を段数から計算)。
3. LSU: 保守的なメモリ依存、ストアからロードへのフォワーディング、コミット後のストア。
4. 出力: CoreMark/MHzと、損失の内訳(フロントエンド、予測ミス、依存、構造)。構成を振る表を`MODEL_J.md`の続き(手順2の章)にまとめる。
