# 論理規模の削減案

- 作成日: 2026-10-24
- 位置づけ: 作者の決定(2026-10-24、`Doc/PROMPT_J.md` 11番)を受けて、Ethernetを残し、FPUをパイプラインのまま始めたうえで、LUTを空ける案を並べる。どの案も、mmRISC-2から流用するブロック、またはmmRISC-3で作るブロックに関するもの。
- 作業ファイル: `Plan/reduce/`(`synth.sh`、`sweep.sh`、`results/sweep.txt`)

---

## 0. 要約

1. **CoreMarkにもLinuxの性能にも影響しない案だけで、LUT 約3.5〜5k、FF 約7〜8kが空く見込み**(1.1節のA1〜A5)。トリガ2本(A1)とPMP 4本(A2)はパラメータの変更だけで済み、合わせて約1.3k LUT(実測)。残りの3つは作り方の変更(FFの表をLUTRAMへ)で、見積り。
2. これで、FPUをパイプラインのまま残しても、OoOの本体に回せるLUTは約12.9k(`ISSUES_J.md` 2章)から**約16〜18k**に増える。NaxRiscv RV64の整数コア(約18k)に近づく。
3. まだ足りなければ、Linuxの機能か性能と引き換えの案(B群)、その次にFPUの案(C群、作者の決定によりG0で再検討)の順に使う。
4. 実測はYosysで行った(Vivadoは作者の環境にしかないため)。差分だけを使い、Vivadoとの比で換算している。CSRの差分は、合成のたびに±0.2k程度ぶれるので範囲で示す。

---

## 1. 削減案の一覧

LUTとFFはVivado相当に換算した値。「実測」はYosysの差分から換算したもの、「見積り」は構造から見積もったもの。

### 1.1 A群: CoreMarkにもLinuxの性能にも影響しない(G0から採用を推奨)

| # | 案 | LUT | FF | 根拠 | 影響・注意 |
|---|---|---|---|---|---|
| A1 | **Sdtrigのトリガ 4 → 2本** | 約0.3k(0.1〜0.55k) | 0.15k | 実測(CORE_CSR) | gdbのハードウェアブレークポイント / ウォッチポイントが同時に2つまで。開発には十分 |
| A2 | **PMP 8 → 4エントリ** | 約0.95k | 0.45k | 実測(CSR 0.24k + MMUの比較器 0.72k) | OpenSBI v1.9が使うエントリ数をSIM_BIOSで確認する(ファームウェアの保護と全域許可で数本のはず) |
| A3 | **D$のラインバッファをFF → LUTRAM**(フィル、ライトバック、MSHRごとのストアデータ。いずれも512ビット) | 0.8〜1.5k | 約3k | 見積り | 1語ずつ書き、1語ずつ読む使い方なのでLUTRAMに向く。mmRISC-2のBTBをFF → LUTRAMにして3,060 LUT / 7,936 FF減った前例と同じ考え方。D$はOoO用のアダプタで手を入れるので、そのときに行う |
| A4 | **TLBをLUTRAMのセットアソシアティブにする**(容量はITLB 16 / DTLB 32のまま) | 約1k | 3〜4k | 見積り(現行は全連想でFF。MMUのFFは4.6k) | ヒット率がわずかに変わる。代案: 小さなL1 TLB(FF)+ 大きなL2 TLB(LUTRAM / BRAM)。mmRISC-2のROADMAPにあった2段目のTLBと同じで、Linuxにはむしろ有利 |
| A5 | **書き換えの少ない64ビットCSRをLUTRAMに置く**(mscratch、mepc、mtval、sscratch、sepc、stval、dpc、dscratchなど) | 0.5〜1k | 約0.6k | 見積り(CSRの読み出しマルチプレクサが小さくなる) | LUTRAMは書き込みポートが1つ。トラップでmepc / mcause / mtvalを同時に書く部分は、数サイクルに分ける。OoOではCSR命令とトラップがROB先頭で直列に実行されるので、性能には影響しない |
| | **A群の合計** | **約3.5〜5k** | **約7〜8k** | | FFが大きく減るので、スライスの混雑(mmRISC-2で93%)も緩む |

### 1.2 B群: Linuxの機能か性能と引き換え(CoreMarkには影響しない)

| # | 案 | LUT | FF | 根拠 | 失うもの |
|---|---|---|---|---|---|
| B1 | HPMカウンタ 4 → 2本 | 約0.65k(0.4〜0.9k) | 0.15k | 実測 | `perf`で同時に数えられるイベントが2つになり、測定の回数が倍になる(mmRISC-2の`perf.sh` / `workload.sh`) |
| B2 | Zbc(clmul)を外す | 0.3〜0.6k | 小 | 見積り | Linuxのcrc32が遅くなる。CoreMarkの`-march`(Zba / Zbb / Zbs / Zicond)には入っていないので、CoreMarkには影響しない **採らない(作者、2026-10-24): 命令セットは維持する** |
| B3 | TLB 16 / 32 → 8 / 16エントリ | 約1.2k | 約2.2k | 実測 | mmRISC-2 Rev.01の大きさに戻る。ユーザーモードの負荷が11〜20%遅くなる(BENCH.md 26章)。A4を採るなら不要 |
| B4 | PMPなし(0エントリ) | 約1.9k | 0.9k | 実測 | M-modeの保護がなくなる。OpenSBIがPMPなしで起動するかの確認が要る |
| B5 | HPMカウンタなし(Sscofpmfなし) | 約1.2k | 0.33k | 実測 | Linuxの`perf`が使えなくなる。mmRISC-2で性能の議論の土台だったので、勧めない |

### 1.3 C群: FPU(作者の決定: 当初はパイプラインのまま。論理規模を見てG0で再検討)

| # | 案 | LUT | 根拠 | 内容 |
|---|---|---|---|---|
| C1 | **FPUの内訳を取る** | — | — | FPU_PIPE(Vivadoで8.8k)の内訳を、乗算、加算、整列、正規化、丸め、変換、反復除算に分けてOOC合成で取る。丸め器(FPU_ROUND)は全体の約23%(実測、Vivado換算で約2.1k)。C2以降の判断の材料 |
| C2 | 乗算器をMDUとFPUで共有する | 0.5〜1k(+ DSP 16) | 見積り | OoOでは、MUL / DIVとFPUを同じ発行ポートに置ける。64 × 64の整数乗算と53 × 53の仮数乗算の部分積の和を1組にする。乗算のスループットが下がる(CoreMarkの乗算は1000命令に30。モデルで確認) |
| C3 | FMAだけパイプラインに残し、変換・比較・符号操作などを別の小さな反復ユニットへ | C1の結果次第 | — | 性能に効くFMA / 加算 / 乗算は毎サイクル受け付けたまま、頻度の低い操作の論理を減らす |
| C4 | マルチサイクルのFPU(当初の推奨) | 数k | 見積り | 最後の手段。浮動小数点の性能は大きく下がる。CoreMarkには影響しない。**G0: mmRISC-2の多サイクルのFPUは9,757 LUTで、FPU_PIPEの9,060より大きい。小さくなるのは新しい幅の狭い設計だけ(`Doc/UARCH_J.md` 5章)** |

### 1.4 D群: SoC側

| # | 案 | LUT | 内容 |
|---|---|---|---|
| D1 | LiteXの不要な周辺を外す | 0.2〜0.5k(見積り) | LiteX全体は4.8k。LEDやボタン、識別子、使っていないタイマなど。LiteXのオプションで外せるものを洗い出し、作者のVivadoで確認する |
| D2 | PLICの割り込み源を減らす | 小 | PLICはVivadoで0.46k。Yosysでは源を31 → 8にしても減らず、結果が一貫しなかったので数えない |
| D3 | Ethernet | — | 作者の決定により残す |
| D4 | L2を外す | 1.26k + BRAM 68 | 勧めない。Linuxの負荷が1.2〜1.7倍遅くなる(mmRISC-2の実測) |

### 1.5 E群: mmRISC-3の作り方そのもの

削減案ではないが、OoOの部分を小さく作るための原則。

| # | 原則 | 内容 |
|---|---|---|
| E1 | 大きな表はFFで作らない | RAT、PRF(書き込みバンク + LVT)、ROBのペイロード、FTQ、発行キューのペイロードはLUTRAM、予測器はBRAM。FFのCAMは避ける |
| E2 | デコーダは安い | mmRISC-2のCORE_DECは278 LUT、CORE_DECOMPは78 LUT。融合のための4命令デコードで増えるのは0.7k程度の見込み。融合(+15%)の費用としては小さい |
| E3 | ALUを非対称にする | ALU0は全機能(Zba / Zbb / Zbs / Zicond、分岐)、ALU1は加減算・論理・比較・分岐だけ。mmRISC-2のCORE_EXUは1.67k |
| E4 | FPUの制御を簡単にする | mmRISC-2のFPU_PIPEにある、コアのパイプラインと連動して止める / 消す制御(hold / kill)は、OoOではROBのタグによる消去に置き換わる |

## 2. 効果の見通し

| 段階 | OoOの本体に回せるLUT | 内容 |
|---|---|---|
| 現状の見積り(`ISSUES_J.md` 2章) | 約12.9k | FPUはパイプライン、mmRISC-2のブロックをそのまま流用 |
| + A群 | **約16〜18k** | 機能も性能も失わない |
| + B1、B2 | 約17〜19k | perfの同時カウント数とLinuxのcrc32を引き換え |
| + C群(G0で判断) | さらに数k | FPUの内訳しだい |

NaxRiscv RV64の整数コアは約18k(FPUなし、CSR・MMUを含む)。mmRISC-3のOoO本体(フロントエンド、リネーム、ROB、発行キュー、ALU、LSU)を16〜18kで作れるかは、G0までのOOC合成の積み上げで確認する(`ISSUES_J.md` 3.4節、5章の手順3)。

## 3. 測定の方法と限界

- `Plan/reduce/synth.sh`: mmRISC-2のRTLをコピーし、対象モジュールのパラメータの既定値を書き換えてから、sv2vで変換し、Yosys(0.56、`synth_xilinx -family xc7 -flatten`)で単独に合成する。sv2vの後に`chparam`で変えると、sv2vが導出した幅と矛盾することがあるので、変換の前に書き換える。
- `Plan/reduce/sweep.sh`: 1章の実測の全条件(`results/sweep.txt`)。
- **Vivado換算**: 既定のパラメータでの、Vivado(mmRISC-2の配置後の階層別レポート)とYosysの比を差分に掛けた。CORE_CSRは1.43、CORE_MMUは0.53、FPU_PIPEは0.79、DCACHEは0.67。モジュールの境界をまたぐ最適化があるので、比はモジュールごとに大きく違う。
- **ばらつき**: CORE_CSRのLUTは、同じ条件でも変換の仕方で3,214〜3,450とぶれた(YosysのABCによる配線の当てはめが、小さな構造の違いに敏感なため)。そのため、CSRの差分は2回の平均と範囲で示した。FFの差分は毎回一致した。MMUの結果は安定していた。
- **確定はVivado**: 採用する案は、mmRISC-3のRTLができた段階で、作者のVivadoのOOC合成で確定する。
